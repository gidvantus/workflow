# Многопроектная система ролей

Что сделано: значения проекта (репозиторий, базовая ветка, рабочая копия, клон
человека, имя compose-проекта, порты, метки, расписание отдела) вынесены из
пресетов и хост-плагинов в один реестр — `~/.dsh/projects.json`. Проект
определяется по рабочей области сессии, поэтому один набор пресетов обслуживает
все проекты машины, и **у каждого проекта свой отдел разработки**.

## Как добавить проект

Дописать объект в `~/.dsh/projects.json`:

```json
{
  "default": "vahta",
  "projects": {
    "brain": {
      "title": "Brain",
      "repo": "owner/brain",
      "base": "main",
      "workspace": "D:\\Agents\\brain",
      "humanClone": "D:\\Development\\VideCoding\\Brain",
      "composeProject": "brain-agent",
      "frontendPort": 8090,
      "apiPort": 8011,
      "department": {
        "enabled": true,
        "windows": [{ "start": "10:00", "stop": "19:00" }],
        "maxRework": 3,
        "maxAttempts": 4,
        "stuckAfterMinutes": 30
      }
    }
  }
}
```

### Данные проекта

| Поле | Смысл | По умолчанию |
|---|---|---|
| `repo` | `owner/name` на GitHub | обязателен |
| `base` | базовая ветка: PR идут в неё, от неё ветвятся задачи | `main` |
| `workspace` | рабочая копия отдела — каталог, в котором работают роли | обязателен |
| `humanClone` | защищённый клон человека (не трогать) | нет |
| `composeProject` | имя `docker compose -p …` | `id` проекта |
| `frontendPort` / `apiPort` | порты стенда отдела | `8080` / `8001` |
| `artifacts` | каталог артефактов тестировщика, вне клона | `<workspace>-artifacts` |
| `labels` | метки конвейера, если в репозитории они другие | стандартные |
| `telegram` | свой бот проекта: `{ "token": "...", "chatId": 123, "voiceLang": "ru" }` | нет — события остаются в GUI |
| `title` | отображаемое имя | `id` |

### Отдел разработки (`department`)

| Поле | Смысл | По умолчанию |
|---|---|---|
| `enabled` | работает ли отдел в этом проекте | `true` |
| `windows` | своё расписание; нет — берётся общее из `dev-department.json` | общее |
| `maxRework` | сколько раз тикет может вернуться из теста | общее |
| `maxAttempts` | сколько раз задачу можно выдать без сдвига | общее |
| `stuckAfterMinutes` | сколько тишины считать зависанием хода | общее |

`~/.dsh/dev-department.json` содержит **только общие значения по умолчанию** для
проектов, которые своё не задали:

```json
{
  "windows": [{ "start": "13:00", "stop": "04:00" }, { "start": "07:00", "stop": "09:00" }],
  "maxRework": 3,
  "maxAttempts": 4,
  "stuckAfterMinutes": 30
}
```

Инструмент `dev_department_status` по каждому проекту показывает, откуда взялось
расписание — `windowsSource: "проект"` или `"общее"`.

### Что легко забыть

1. **Рабочие области не должны совпадать.** Две сессии в одном каталоге портят
   работу друг другу, а резолв проекта становится неоднозначным — диспетчер
   сообщит об этом отдельной проблемой.
2. **Клон отдела должен существовать и быть git-репозиторием.** Диспетчер больше
   не создаёт каталог сам: проект без клона он пропускает с причиной — иначе
   падал бы на этом каждый тик, а агент всё равно не смог бы ни ветвиться, ни
   коммитить.
3. **Проект без расписания не обслуживается.** Если отдел включён, а расписания
   нет ни у проекта, ни в общих настройках — проект пропускается с объяснением,
   а не работает по случайному окну 00:00–06:00.
4. **Файл должен быть без BOM.** Чтение BOM-устойчиво, но лишний невидимый символ
   лучше не плодить: редакторы Windows умеют его добавлять.
5. **У проекта может не быть репозитория.** Тогда `repo` не задаётся вовсе:
   `project_info` отдаёт `repo: null`, а инструменты `gh_*` отказывают с внятной
   причиной вместо похода на `/repos//issues/…`. Это нормальный режим для рабочего
   каталога, не связанного с GitHub (`brain`).
6. **Клон человека может отсутствовать.** Если `humanClone` не задан, защищённого
   клона у проекта нет: рабочая область **и есть** каталог человека, и работать в
   ней — норма. Так устроен `brain`.

## Своя смена у каждого проекта

У каждого проекта свой отдел: **своё расписание, свой старт и завершение смены,
свои счётчики попыток и доработок, своя сводка в Telegram**. Проекты не делят ни
смену, ни очередь, ни стенд — смена одного проекта не мешает другому.

- Расписание — независимые диапазоны, каждый может переходить полночь
  (`23:00–03:30`). Пока открыт диапазон, задачи берутся; в промежутке смена
  завершается со сводкой, со следующим диапазоном начинается новая.
- Правило «один тикет за раз» действует **на проект**, не на машину.
- Смена проекта не начинается дважды за сутки (ключ смены свой у каждого).
- Взятая задача доводится до конца, даже если окно закрылось.

## Боты Telegram

У каждого проекта может быть **свой бот** — тогда переписка, запросы разрешений и
вопросы модели по этому проекту идут только в его чат:

```json
"brain": {
  "telegram": { "token": "123456:AA...", "chatId": 987654321 }
}
```

- `~/.dsh/telegram.json` — бот **по умолчанию**. Общим он становится только
  тогда, когда его токен не принадлежит ни одному проекту: тогда он обслуживает
  все проекты без своего бота. Если тот же токен указан у проекта, общего бота
  нет вовсе: события проектов без бота остаются в GUI, а в лог уходит
  предупреждение. Иначе они молча уходили бы в чужой чат.
- **Один токен — один поллер.** Токен, указанный у двух проектов, опрашивается
  один раз: владельцем становится первый по порядку реестра. Два поллера на
  одном токене перехватывали бы друг у друга обновления.
- **Маршрутизация по проекту сессии.** Три глобальных хука (`session/event`,
  `approval/request`, `user-questions/request`) регистрируются один раз на
  процесс и выбирают мост по рабочей области сессии. Иначе при нескольких ботах
  каждый запрос разрешения ушёл бы во все чаты сразу. Если проект сессии не
  опознан — событие уходит общему боту, а при его отсутствии остаётся в GUI.
- **У проекта два корня, а не один.** Сессия опознаётся и по `workspace` (рабочая
  копия отдела), и по `humanClone` (каталог человека): сессия, открытая в каталоге
  человека, принадлежит тому же проекту. Раньше учитывался только `workspace` —
  из-за этого сессия CloudPass в `D:\Development\VideCoding\CloudPass` не
  опознавалась, и её события уходили чужому боту.
- **Мост видит только сессии своего проекта.** Активный диалог выбирается среди
  своих сессий; без этого сообщение, отправленное боту CloudPass, уходило бы в
  первую попавшуюся сессию процесса — например в вахту. `/new` в боте проекта
  тоже целится в рабочую область своего проекта, а не в проект по умолчанию.
- **Секрета в исходниках нет.** Зашитый в код токен уезжает вместе с плагином,
  поэтому запасная константа убрана: нет настроенного бота — нет моста, и об
  этом пишется в лог.
- Проект со своим ботом получает и **сводку отдела** в свой чат.

## Где живут данные проекта

Краткая сводка того, что уже не в пресетах, а в `~/.dsh/projects.json`:

| Что | Поле проекта | Куда уходит |
|---|---|---|
| Репозиторий | `repo` | инструменты `gh_*`, персоны, `project_info` |
| Базовая ветка | `base` | ветвление, PR, возврат рабочей копии |
| Рабочая копия отдела | `workspace` | `cwd` сессий, резолв проекта по области |
| Клон человека | `humanClone` | запрет трогать |
| Имя compose-проекта | `composeProject` | стенд отдела |
| Порты стенда | `frontendPort`, `apiPort` | `project_info` |
| Каталог артефактов | `artifacts` | тестировщик |
| Метки конвейера | `labels` | переходы ролей |
| Бот проекта | `telegram` | мост и сводки отдела |
| Отдел | `department` | включён ли, расписание, лимиты |

## Как это работает

- **Пресеты** (`analyst`, `dev`, `tester`, `devops-delivery`, `security-review`)
  больше не содержат имён и путей. В персоне и скиллах стоят заполнители
  `<repo>`, `<base>`, `<workspace>`, `<composeProject>`, `<humanClone>`,
  `<frontendPort>`, `<apiPort>`, `<artifacts>`, `<id>`; расшифровку даёт
  инструмент `project_info`, который резолвит проект по `cwd` сессии.
- **`github.mjs`** в каждом пресете резолвит проект на каждом вызове инструмента
  (`exec.agent` → сессия → `header.cwd` → проект). Пресет общий для всех сессий,
  поэтому проект нельзя «запечь» при регистрации инструментов.
- **Сессия в рабочей области, не совпавшей ни с одним проектом**, при нескольких
  проектах в реестре получает явную ошибку, а не чужой репозиторий. Если проект
  в реестре один, он берётся как проект по умолчанию.
- **Диспетчер** ведёт конвейер по каждому проекту отдельно; ошибка одного проекта
  не останавливает остальные.

## Откат

Каждый изменённый файл рядом с собой имеет копию `.bak-multiproject` (самая
первая, до всех правок):

```
~/.dsh/.agent-presets/<роль>/agent.cordis.yml
~/.dsh/.agent-presets/<роль>/skills/<скилл>/SKILL.md
~/.dsh/.agent-presets/<роль>/github.mjs
~/.dsh/profiles/desktop/plugins/dev-department.mjs
~/.dsh/profiles/desktop/plugins/tg-bridge.mjs
~/.dsh/dev-department.json
~/.dsh/projects.json
```

Откат — вернуть нужный файл на место из копии и перезапустить DSH Desktop.
`tg-bridge.mjs` и диспетчер имеют две копии: `.bak-multiproject` — состояние до
всех переделок, `.bak-multibot` — до перехода на нескольких ботов.

## Обязательный перезапуск

Плагины профиля и композиции пресетов читаются при старте процесса. До
перезапуска DSH Desktop работает прежний код.
