# workflow

Кастомная надстройка над DeepSeek Harness: **отдел разработки** — ролевые агенты
(аналитик, разработчик, тестировщик и другие) и процессы, которые их запускают,
ведут по конвейеру GitHub-задач и отчитываются в Telegram.

Здесь лежит ровно то, что написано руками: агенты, хост-плагины, их конфигурация
и инструменты проверки. Всё стандартное — сам DSH, его бандлы и встроенные
пресеты — в репозиторий не входит и не копируется.

Каталог `D:\Development\VideCoding\Workflow` — единственный дом этой надстройки:
раньше пакет лежал в `VideCoding\dsh-department`, а процессные файлы — в рабочей
области продукта Brain. Теперь и агенты, и документы процесса, и инструменты, и
история сборки отдела живут здесь.

Репозиторий — это **bundle-пакет DSH** `dsh-dev-department`: в корне лежит
`package.json` с полем `dsh.bundle.patch`, а сам слой композиции профиля —
`plugins/cordis.patch.yml`. Одна команда
`dsh plugin add github:gidvantus/workflow#<commit>` ставит его зависимостью профиля,
и после перезапуска DSH в профиле появляются четыре хост-плагина отдела и десять
ролей — без раскладки файлов руками.

В репозитории две директории: `plugins/` — сам пакет отдела и всё его
обслуживание (документация, инструменты, настройки), `app/` — продукт, который
отдел делает на заказ.

Репозиторий обслуживает сам себя: в реестре проектов отдела
(`~/.dsh/profiles/desktop/dsh-dev-department/projects.json`, см. «Где живёт
состояние отдела») он записан как
проект `workflow` (`gidvantus/workflow`, рабочая копия отдела `D:\Agents\Workflow`,
клон человека — этот каталог) с включённым отделом.

### Инструменты распознавания речи

`plugins/profiles/desktop/plugins/voice-input/` и `plugins/tg-bridge.mjs` распознают
голос через ffmpeg + whisper.cpp.
Сами бинарники и модель — это ~640 МБ установленного софта, поэтому в git они не
едут: они лежат в `.voice-tools/` рядом с репозиторием (каталог в `.gitignore`), а
разведка и установщик пакета — в `.voice-research/`.

```powershell
node .voice-research/install.mjs    # разложить пакет voice-input в профиль desktop
```

Плагины берут путь из переменной `DSH_VOICE_TOOLS`, а без неё — из
`D:/Development/VideCoding/Workflow/.voice-tools`. Пути к рабочей области продукта
в них больше нет: раньше инструменты лежали в Brain.

## Две плоскости

DSH собирается из композиций Cordis. Здесь их две, и файлы нельзя путать местами:

- **Хост-плоскость** (`plugins/*.mjs`, а в легаси-раскладке
  `plugins/profiles/<профиль>/`) — плагины и их подключение. Живёт
  в процессе DSH и обслуживает все сессии. `cordis.patch.yml` — слой правок поверх
  бандлов: строки оттуда применяются *раньше*, чем бандлы публикуют сервисы,
  поэтому каждый вставленный плагин обязан сам объявить `inject` — иначе Cordis
  запустит его в пустом окружении и тот молча ничего не сделает. Ставится этот
  слой пакетом: `plugins/cordis.patch.yml` — патч бандла, а
  `plugins/profiles/<профиль>/cordis.patch.yml` — та же раскладка прежним способом
  (`plugins/sync.mjs`), и вместе они не нужны: две строки диспетчера — два тикера
  на одни тикеты.
- **Агент-плоскость** (`plugins/agent-presets/<id>/`) — то, что одна сессия добавляет в
  реестры: персона, скиллы, инструменты роли. Один каталог — один пресет:
  `preset.yml` (имя и описание для списка), `agent.cordis.yml` (композиция),
  `skills/` (скиллы роли). Своего клиента GitHub у роли больше нет: доступ к
  репозиторию даёт штатный MCP-сервер строкой `mcp-github` в `agent.cordis.yml`,
  а инструменты видны модели как `mcp__github__*`. Копировать каталоги в
  `~/.dsh/.agent-presets` не нужно: патч бандла объявляет `agent-presets/` внутри
  пакета корнем пресетов с trust `system`.

Подробности конвейера — в [plugins/docs/ARCHITECTURE.md](plugins/docs/ARCHITECTURE.md), процесс с
ролями и метками — в [plugins/docs/DEPARTMENT-PROCESS.md](plugins/docs/DEPARTMENT-PROCESS.md).

## Установка на новой машине

1. Запустить DSH Desktop один раз: он создаёт профиль `~/.dsh/profiles/desktop`.
   Профиль — это каталог с манифестом `package.json`; пакет ставится в него.
2. Поставить надстройку одной командой из терминала DSH (трей → терминал: он
   подставляет активный профиль и `DSH_HOME`):

   ```powershell
   dsh plugin add github:gidvantus/workflow#<commit>
   ```

   Команда кладёт пакет `dsh-dev-department` зависимостью профиля
   (`~/.dsh/profiles/desktop/node_modules/dsh-dev-department`) и дописывает его в
   `dsh.profile.bundles`. Дальше DSH применяет его патч: четыре хост-плагина
   отдела и корень пресетов — каталог `plugins/agent-presets/` внутри пакета.

   Терминал DSH подставляет активный профиль и `DSH_HOME` сам. Если команду
   запускают из обычного системного терминала, профиль надо назвать явно:
   `dsh plugin --profile desktop add …` — иначе команда отработает «успешно», но
   в профиль человека ничего не попадёт.

   Проверить, что слой собрался: `dsh --profile desktop --dump-config` — в выводе
   есть блок `# == dsh-dev-department` с четырьмя строками и строка
   `agent-presets` с нашим `roots`. Установка из локального клона — то же командой
   `dsh plugin add <путь к клонированному репозиторию>`.
3. Перезапустить DSH Desktop: композиция профиля перечитывается на старте. В
   списке пресетов должны появиться десять ролей отдела, а
   `~/.dsh/.agent-presets` — оставаться пустым: роли приезжают из пакета.
4. Общие настройки отдела — расписание смен и лимиты — живут в
   `~/.dsh/profiles/desktop/dsh-dev-department/dev-department.json` и в пакет не
   входят (это настройки человека, а не
   содержимое надстройки): разложить их из репозитория можно командой
   `node plugins/sync.mjs apply` или написать файл руками.
5. Создать `~/.dsh/profiles/desktop/dsh-dev-department/projects.json` по образцу
   `config/projects.example.json` и
   заполнить своими значениями: репозиторий, базовая ветка, каталог рабочей копии
   отдела и каталог клона человека, имя compose-проекта, порты, каталог артефактов.
   Каталог состояния отдела создаёт сам отдел — при первом запуске (перенос
   состояния и журнал смены) или командой `node plugins/sync.mjs apply`. Если
   пишете файл руками на чистой машине, сначала создайте каталог:
   `New-Item -ItemType Directory -Force "$env:USERPROFILE\.dsh\profiles\desktop\dsh-dev-department"`.
   Затем проверить, что в репозиториях есть все метки конвейера:
   `node plugins/tools/pipeline-labels-probe.mjs` (см. раздел «Метки конвейера»).
6. Положить секреты — в репозитории их нет и быть не должно:

   | Файл | Что внутри |
   |---|---|
   | `~/.dsh/mcp/github-mcp-server/token` | токен GitHub для MCP-сервера (fine-grained; Issues, Contents, Pull requests read+write на нужные репозитории) |
   | `<каталог состояния>/projects.json` | `telegram.token` и `telegram.chatId` каждого проекта |

   Бот задаётся только в `projects.<id>.telegram` — та же тройка полей
   `token`/`chatId`/`voiceLang`; у проекта без бота Telegram нет и это не ошибка.
   `chatId` — это id **пользователя**, а не чата: мост отсеивает чужие сообщения
   сравнением `from.id` с этим значением, поэтому бот слушает ровно одного
   человека (в приватном чате id пользователя и id чата совпадают) и строковое
   значение вроде `"294292338"` не совпадёт с числом — все сообщения будут молча
   отброшены. **`chatId: 0` считается незаданным** (ложное значение): такая
   запись молча не поднимает бота, как и пустой `token`. `voiceLang`
   необязателен: это язык распознавания голосовых, по умолчанию `auto`.

7. Поставить MCP-сервер GitHub — единственный путь к GitHub для диспетчера и ролей:
   нативная сборка `github/github-mcp-server` (Windows x86_64, без Docker) в
   `~/.dsh/mcp/github-mcp-server/`:

   ```powershell
   $dir = "$env:USERPROFILE\.dsh\mcp\github-mcp-server"
   New-Item -ItemType Directory -Force $dir | Out-Null
   Invoke-WebRequest -OutFile "$dir\gh-mcp.zip" `
     https://github.com/github/github-mcp-server/releases/latest/download/github-mcp-server_Windows_x86_64.zip
   Expand-Archive "$dir\gh-mcp.zip" -DestinationPath $dir -Force
   Remove-Item "$dir\gh-mcp.zip"
   "# пересоздать токен: https://github.com/settings/personal-access-tokens/new" | Out-Null
   Set-Content -Encoding ascii "$dir\token" "<fine-grained PAT>"
   ```

   Машинная настройка человека — строка `mcp-github` и строка Playwright MCP —
   живёт в `plugins/profiles/desktop/cordis.patch.yml` и в пакет не входит: пути к
   установленному бинарнику и к браузеру у каждой машины свои. Выражение `!!js`
   читает токен прямо из этого файла, поэтому второй копии в конфиге нет. Нет
   файла — строка не поднимется (у неё `failOnStartupError: false`), и инструменты
   `mcp__github__*` просто исчезнут из сессий: диспетчер в этом случае пишет
   «состояние GitHub не прочитано». Тулсеты сервера — `default,labels`: конвейер
   живёт в метках.

8. Перезапустить DSH Desktop ещё раз (если ставили что-то после шага 3).
   `dev_department_status` должен ответить. Не отвечает — смотреть причину в
   журнале `~/.dsh/profiles/desktop/dsh-dev-department/dev-department.log`.

### Что остаётся человеку

Установка пакета ставит только саму надстройку. За её пределами остаются вещи,
которые пакет знать не может:

| Что | Где | Почему не в пакете |
|---|---|---|
| Реестр проектов | `~/.dsh/profiles/desktop/dsh-dev-department/projects.json` | адреса, ветки, порты и каталоги — свои у каждой машины |
| Расписание смен и лимиты | `~/.dsh/profiles/desktop/dsh-dev-department/dev-department.json` | решение человека, а не содержимое надстройки |
| Токен GitHub | `~/.dsh/mcp/github-mcp-server/token` | секрет |
| Бот Telegram | `projects.<id>.telegram` | секрет |
| Метки конвейера | репозитории проектов | их создаёт `plugins/tools/pipeline-labels-create.mjs` по токену |
| MCP GitHub и Playwright MCP | `plugins/profiles/desktop/cordis.patch.yml` | машинная настройка: пути к бинарникам и браузеру |
| Перезапуск DSH | — | композиция профиля читается только на старте |

Пресеты системного корня — только чтение: `agentPresets.copy()` для них не
работает. Правка роли идёт через git: меняешь `plugins/agent-presets/<id>/` в репозитории,
ставишь новый commit и повторяешь `dsh plugin add`.

### Переход с прежней раскладки

Если надстройка уже была разложена `node plugins/sync.mjs apply`, после установки пакета
в `~/.dsh` остаются вторые копии: четыре модуля в
`~/.dsh/profiles/desktop/plugins/`, десять каталогов в `~/.dsh/.agent-presets/` и
строки отдела в живом `~/.dsh/profiles/desktop/cordis.patch.yml`. Их снимает
человек — это файлы установки, а не данные (диалоги
`~/.dsh/profiles/desktop/dsh-dev-department/dev-department-dialogs.json`, книга
токенов, журнал и сессии не трогаются).
Иначе в композиции окажутся две строки диспетчера, то есть два тикера на одни
тикеты.

## Где живёт состояние отдела

Всё изменяемое состояние отдела — реестр проектов, общие настройки, карта диалогов,
книга учёта токенов и журналы — лежит в одном каталоге профиля:

```
~/.dsh/profiles/desktop/dsh-dev-department/
  projects.json                  реестр проектов (в т.ч. токены Telegram)
  dev-department.json            расписание смен и лимиты
  dev-department-dialogs.json    карта диалогов роль↔тикет
  dev-department-usage.json      книга привязок «сессия → тикет»
  dev-department.log             журнал смены
  dev-department-mcp.log         журнал транспорта MCP
  role-sessions.log              журнал role-sessions
  role-permissions.log           журнал role-permissions
```

Почему не рядом с модулями: `dsh plugin add` переустанавливает пакет, и файл внутри
`node_modules` исчезает вместе с прежней версией — а в `projects.json` лежат токены и
рабочие области. Почему не в корне `~/.dsh`: корень принадлежит DSH (`mcp/`,
`sessions/`, `storages/`, `.agent-presets`), и отдел не должен его засорять. Каталог
профиля pnpm не трогает — это компромисс, который переживает установку и не спорит
с DSH.

Путь, имена файлов и правило переноса собраны в одном модуле —
`plugins/state-paths.mjs`. Его спрашивают все: плагины пишут через него, инструменты
`plugins/tools/` читают через него. Свой `path.join(dshHome(), …)` для этих восьми
файлов не собирает никто: иначе перенос каталога разошёлся бы у плагинов и у
инструментов молча.

Переход со старого места однократный и без потери данных: первый вызов
`stateFile()` переносит легаси-файл из корня `~/.dsh` в каталог состояния
(`rename`); если `rename` не удался (`EXDEV` — другой диск, `EPERM` — чужое право),
файл копируется, старый остаётся, а в `dev-department.log` пишется строка «миграция:
скопировано, старое оставлено». Чтение старое место понимает всегда, поэтому ручной
возврат файла в корень не оставляет отдел без реестра.

## plugins/sync.mjs

Установка — не этот скрипт: надстройка ставится bundle-пакетом (см. «Установка на
новой машине»). За `plugins/sync.mjs` остались сбор правок и перенос файлов, путь которых в
каталоге установки не совпадает с путём в репозитории. Каталоги пресетов
зеркалятся целиком: `collect` не только копирует новые файлы, но и **удаляет** из
репозитория те, которых в каталоге установки уже нет, — иначе переименованная роль
или выброшенный скилл остаются в репозитории навсегда и их видно в дереве файлов.
Черновики (`*.bak-*`), логи, песочницы тестов, архив `_skills-archive/` и секреты не
синхронизируются никогда и в репозиторий не приезжают. Скрипт на Node, а не на
PowerShell: на этой машине выполнение `.ps1` запрещено политикой, и `node` надёжнее
переносится между системами.

Списки не ведутся руками: роли — это каталоги `plugins/agent-presets/<id>/` в репозитории,
хост-файлы — файлы `profiles/<профиль>/…`. Забытая строка в прежних массивах
означала роль, которая есть в репозитории, но никуда не раскладывается, поэтому
массивы убраны.

Увидев в профиле установленный пакет, `status` и `apply` называют его и
**не предлагают раскладку**: плагины хоста и роли приезжают из пакета, а вторая
копия в каталоге установки подняла бы второй диспетчер. Считаются тогда только
файлы вне пакета — сейчас это одни общие настройки отдела. `collect` продолжает
работать в любой раскладке: он собирает правки из каталога установки в репозиторий.

Общие настройки отдела лежат в репозитории как `plugins/config/dev-department.json`, а в
каталоге установки — как
`~/.dsh/profiles/desktop/dsh-dev-department/dev-department.json`: `apply`
раскладывает их,
`collect` собирает обратно. Файлы профиля (`profiles/<имя>/…`) раскладываются
только в **существующий** профиль: каталог `profiles/<имя>` — это профиль DSH с
манифестом `package.json`, и половина профиля (патч с плагинами без манифеста) —
не рабочая установка, а профиль, который DSH покажет недоступным. Нет профиля в
каталоге установки — его файлы из репозитория не берутся, `status` показывает их
строкой «профиля нет».


```powershell
node plugins/sync.mjs collect     # из ~/.dsh в репозиторий (режим по умолчанию)
node plugins/sync.mjs apply       # из репозитория в ~/.dsh (без пакета — и хост-плоскость)
node plugins/sync.mjs status      # что расходится; при установленном пакете — только вне пакета
```

Каталог установки берётся из `$env:DSH_HOME`, если он задан, иначе `~/.dsh`;
переопределяется параметром `--dsh-home <путь>`.

Корень репозитория специально **не зашит** в код: по умолчанию это каталог на
уровень выше самого `plugins/sync.mjs`, то есть корень репозитория, — поэтому
переезд всей папки (так переехали из `VideCoding\dsh-department`
в `VideCoding\Workflow`) ничего не ломает. Переопределяется ключом
`--repo <путь>` или полем `repo` в локальном файле `sync.local.json` (в git не
попадает):

```json
{ "repo": "D:\\Development\\VideCoding\\Workflow" }
```

Без этого файла скрипт тоже работает — берёт свой каталог.

`plugins/docs/` и `plugins/tools/` — документация процесса и инструменты проверки, а не надстройка
каталога установки: в `~/.dsh` они не кладутся, и обратно `apply` их не
раскладывает. Раньше их источник задавался полем `toolsSource` в `sync.local.json`;
теперь источник у них один — этот репозиторий, и поле больше не нужно.

Отдельно `collect` проверяет, не попал ли в репозиторий настоящий секрет: читает
`mcp/github-mcp-server/token`, токены проектов из `projects.json`, `typesafe.token`
и `telegram.json`, если такой файл на машине ещё остался, и сообщает, если такая
строка встречается в файлах репозитория.

## Проверки

Наборы работают на **боевых** модулях — `plugins/dev-department.mjs`
в рабочей копии репозитория, в установленном пакете
(`<DSH_HOME>/profiles/<профиль>/node_modules/dsh-dev-department/…`) или в старой
раскладке `<DSH_HOME>/profiles/…`. Какой именно — решает помощник
`plugins/tools/plugin-paths.mjs`: набор не должен знать, где модуль лежит на этой
машине. Дальше — поддельный MCP-сервер GitHub, часы и сервисы. HTTP к GitHub
больше не перехватывается: диспетчер говорит с GitHub только по MCP, и тест
подменяет `spawn` поддельным сервером, который отвечает на те же инструменты
(`list_issues`, `issue_read`, `add_issue_comment`, `list_pull_requests`,
`issue_write`). Реальный GitHub и Telegram тесты не трогают.

```powershell
cd plugins/tools/tests
node dev-department-dialogs.test.mjs    # конвейер, диалоги, сбой модели, сторож зависших
node dev-department-windows.test.mjs    # расписание окон смен
node github-probe.test.mjs              # github-probe.mjs: PATCH комментария, право и побайтовый возврат тела
node usage-ledger.test.mjs              # книга учёта токенов, правило повтора, счёт по стенограмме
node dev-department-usage.test.mjs      # привязка при выдаче роли, карточка usage в статусе, сводка смены
node issue-tokens.test.mjs              # plugins/tools/issue-tokens.mjs: таблица по тикету, сверка, непривязанные сессии
node state-paths.test.mjs               # модуль путей состояния: каталог, восемь имён, однократный перенос
node plugin-manifests.test.mjs          # манифесты хост-плагинов: без name+version каждый ход падает с REQUEST_EXTENSION
node plugin-paths.test.mjs              # сам помощник раскладок: порядок поиска, приоритет, отказной сценарий
```

Запускать из `plugins/tools/tests`: четыре набора адресуют модули от текущего каталога,
поэтому из корня репозитория они падают на `ERR_MODULE_NOT_FOUND`, хотя путь ищется
помощником (это не регрессия пакета, а поведение самих наборов).

`node plugins/tools/yaml-block-check.mjs` без аргументов проверяет разметку блоков в
патче бандла, патчах профилей и композициях пресетов разом — это и есть проверка
«YAML не сломан после правки руками».

Живая проба GitHub (`plugins/tools/github-probe.mjs`) — единственный инструмент набора,
который **пишет**: третий сценарий повторяет тело своего же самого давнего
комментария и потому двигает у него дату правки. Первые два сценария ничего не
меняют. Нечитаемый реестр проектов — отказ с кодом 2, а не запасной список
репозиториев.

Диагностика по стенограммам (`~/.dsh/sessions`):

```powershell
node plugins/tools/session-errors.mjs 24     # ходы, завершившиеся ошибкой, за сутки
node plugins/tools/session-tail.mjs <часть-id-сессии> [сколько событий]
node plugins/tools/issue-tokens.mjs workflow 14   # токены по тикету: роли, сессии, итоги
```

## Метки конвейера

Конвейер двигается метками GitHub, а не памятью диспетчера — значит все
метки набора должны **существовать в репозитории**. Поставить метку, которой в
репозитории нет, GitHub не даёт (`422`), и шаг конвейера падает на первом же
тикете. Это первое, что стоит проверить на новом проекте.

```powershell
node plugins/tools/pipeline-labels-probe.mjs    # что есть и чего не хватает, по всем проектам
node plugins/tools/pipeline-labels-create.mjs   # создать недостающее (существующее не трогает)
```

Оба читают реестр проектов отдела и токен из `~/.dsh/mcp/github-mcp-server/token`.
`probe` только читает; `create` создаёт недостающие метки во всех проектах
реестра, у которых задан `repo`, а также снимает с тикетов и удаляет из
репозитория метки выведенных маршрутов (`ready-for-design`).

Полный набор:

| Метка | Кто ставит |
|---|---|
| `needs-mockup` | аналитик (метка через `mcp__github__issue_write`) или человек: постановке нужен макет |
| `mockups-ready` | дизайнер, когда макет лёг в ветку и скриншоты ушли в issue |
| `ready-for-dev` | человек: этим он берёт тикет в работу и принимает макет |
| `area:backend` / `area:frontend` / `area:fullstack` | диспетчер по тексту постановки (или человек) |
| `ready-for-frontend` | диспетчер: бэкенд-половина полного стека прошла ревью |
| `phase:frontend` | диспетчер: фронтенд-фаза полного стека начата |
| `in-progress` | диспетчер в момент выдачи задачи исполнителю |
| `for-code-review` | исполнитель после PR |
| `ready-for-test` | код-ревьюер, принявший изменение |
| `tested` | тестировщик, если проверка прошла |
| `test-failed` | тестировщик, если не прошла |
| `merged` | DevOps-инженер после слияния PR |

Две ступени стоят до разработки. `needs-mockup` — постановка требует макета:
дизайнер рисует статичный прототип в `mockups/<номер>/` и прикладывает
скриншоты; пока нет `mockups-ready`, тикет в разработку не уходит, даже если
`ready-for-dev` уже стоит. `area:*` — маршрут: полный стек проходит двумя
половинами в одной ветке, и каждая половина ревьюится отдельно. Перед слиянием
DevOps удаляет `mockups/<номер>` из ветки: артефакты постановки остаются в
истории git, но не копятся в базовой ветке.

## Что сюда намеренно не входит

- `~/.dsh/plugins/dsh-relay-src` — отдельный проект со своим `.git`, README и CI.
- Стенограммы сессий, логи, `node_modules`, черновики `*.bak-*`.
- Любые токены, ключи и учётные данные.
