# APP — приложение «Проекты» с задачами и отделами проекта

Стенд из трёх сервисов, который поднимается одной командой: раздел «Проекты» (список,
создание, правка и мягкое удаление) и страница проекта с тремя вкладками — «Задачи»
(список и создание задачи), «Отделы» (список, создание, правка и мягкое удаление
отдела; окна времени работы «с/по» и набор ролей из справочника) и «Расходы» (журнал
расхода смен: итог проекта, смены и их сессии), — и их общее API.

Отдел живёт **внутри проекта**: отдельного пункта меню у отделов нет, вход один —
вкладка на странице проекта, а страница правки открывается из строки списка.

Отдел создаётся **выбором вида** из справочника (`GET /api/department-kinds`:
«Разработка» и «Маркетинг»), а не вводом полей: имя отдела — это название вида, а
расписание, роли, репозиторий, рабочее пространство, артефакты, compose-проект, лимит
возврата и уведомления заполняются на отдельной странице правки (задача #51). Какие
блоки этой страницы видит вид, решает его поле `fields`.

| Сервис | Что это | Порт на хосте |
|---|---|---|
| `db` | PostgreSQL 16 | не публикуется, доступен только внутри compose-сети |
| `api` | FastAPI на Python 3.12 (uvicorn) | `API_PORT`, по умолчанию `8096` |
| `web` | React на Vite под nginx, проксирует `/api/` в `api` | `FRONTEND_PORT`, по умолчанию `8095` |

Поднимать можно и по частям — например, только базу с API:

```bash
docker-compose -p workflow-agent up -d --build db api
```

## Как поднять

```bash
cd APP
docker-compose up -d --build
```

Именно `docker-compose`, а не `docker compose`: на этой машине плагин не работает
(`docker: unknown command: docker compose`), работает отдельный `docker-compose.exe`.

Первая сборка тянет pip и npm — это несколько минут. Дальше слои переиспользуются.

Проверки:

```bash
docker-compose -p workflow-agent ps                     # db healthy, api и web Up
curl.exe -s http://localhost:8096/api/health            # напрямую в api
curl.exe -s http://localhost:8095/api/health            # через nginx
curl.exe -s -o NUL -w "%{http_code}" http://localhost:8095/   # страница отдаётся, 200
docker-compose -p workflow-agent exec api alembic current   # 0006_department_kinds (head)
docker-compose -p workflow-agent exec web nginx -t          # конфиг nginx валиден
```

Остановить стенд, сохранив данные базы:

```bash
docker-compose -p workflow-agent stop
```

Снести вместе с томом базы:

```bash
docker-compose -p workflow-agent down -v
```

## Настройки и второй стенд

Значения по умолчанию лежат в `.env.example`; `.env` — личная копия, он в git не едет:

```bash
copy .env.example .env      # Windows
cp .env.example .env        # bash
```

Имя compose-проекта и порты у каждого стенда **свои**. Второй стенд того же
compose-файла (например клон человека) с общими значениями пересоздаст чужие
контейнеры и займёт чужие порты — ему в `.env` нужны, например,
`COMPOSE_PROJECT_NAME=workflow-local`, `FRONTEND_PORT=8091`, `API_PORT=8092`.

Секретов в репозитории нет: в `.env.example` только локальные заглушки. Одна из них —
`REGISTRY_TOKEN`: общий токен ручек `/api/registry`. Он уезжает в `.env` стенда и в
`registry.token` настроек отдела (`dev-department.json`); без него ручки отвечают
`401`, потому что в документе реестра лежат токены телеграм-ботов.

## Маршрут по каталогам

Каталог `app/` не входит ни в одну половину работы из реестра проекта (`areas`:
backend = `tools/`, frontend = `agent-presets/`, `docs/`, `profiles/`). Постановки #32,
#34, #36, #42, #51 и #54 называли файлы обеих половин (`.py` и `.tsx`/`.css`), поэтому
маршрут был `area:fullstack` с двумя ступенями: сначала бэкенд, затем фронтенд. У #54
фронтенд-половины в `app/` нет вовсе — ручки реестра разбирает плагин диспетчера,
поэтому второй ступенью шли `plugins/agent-presets/` и `plugins/docs/`.

| Ступень | Где лежит | Что это |
|---|---|---|
| бэкенд | `app/backend/` | `models/`, `schemas/`, `api/`, миграции, тесты |
| фронтенд | `app/frontend/src/` | `api/`, `components/`, `App.tsx`, `index.css` |
| шов | `app/README.md` | описание ручек, экранов и soft delete |

Остальное в репозитории (`tools/`, `plugins/`, `profiles/`, `agent-presets/`, `docs/`,
`sync.mjs`) — не часть приложения `app/` и в этих задачах не менялось.

## API

Тридцать ручек: `GET /api/health`, четыре ручки проектов, четыре ручки отделов
(список и создание — внутри проекта, правка и удаление — по id отдела), справочник
видов отделов `GET /api/department-kinds`, четыре ручки ролей и четыре ручки скиллов
ролей (правка и удаление скилла — по id скилла, `/api/skills/{id}`), две ручки задач
проекта, три ручки реестра проектов отдела (`GET`, `PUT`, `POST /rebuild`), три
машинные ручки пресетов (`GET /api/presets`, `GET` и `PUT /api/presets/{code}`) и
четыре ручки журнала расхода смен (`POST /api/usage/shifts`, два чтения по проекту и
смене, `GET /api/usage/projects`) под тем же токеном надстройки.

### Живость сервиса

`GET /api/health` — единственная ручка каркаса.

```json
200 {"status":"ok","db":"ok","version":"0.1.0"}
503 {"status":"degraded","db":"fail","version":"0.1.0","message":"База данных недоступна"}
```

`503` — это контракт, а не сбой: база проверяется запросом `SELECT 1` с таймаутом
подключения 2 с, недоступность базы не роняет процесс и не даёт 500. Текст поля
`message` показывается пользователю дословно.

### Проекты

| Метод и путь | Тело запроса | Успех |
|---|---|---|
| `GET /api/projects` | нет | `200 [{id, name, description, repo_url, code, price_input, price_output, price_cache_read, price_cache_write, created_at, updated_at}]` — только живые, порядок по `id` |
| `POST /api/projects` | `{name, repo_url, description?, code?, price_input?, price_output?, price_cache_read?, price_cache_write?}` | `201` тот же объект |
| `PATCH /api/projects/{id}` | любое непустое подмножество `{name, description, repo_url, code, price_input, price_output, price_cache_read, price_cache_write}` | `200` тот же объект |
| `DELETE /api/projects/{id}` | нет | `204` без тела (мягкое удаление) |

Отказы — часть контракта: экран показывает их текст дословно и своих формулировок не
добавляет.

| Код | `detail` | Когда |
|---|---|---|
| `409` | `Проект с таким названием уже есть` | имя занято живым проектом (сравнение без учёта регистра) |
| `409` | `Код проекта уже занят` | код занят живым проектом (сравнение без учёта регистра) |
| `404` | `Проект не найден` | проекта нет или он уже удалён — в том числе для `PATCH` |
| `422` | `Укажите название проекта` | имя пустое после `strip()` |
| `422` | `Название длиннее 200 символов` | имя длиннее 200 символов |
| `422` | `Укажите адрес репозитория` | адрес пустой после `strip()` |
| `422` | `Адрес репозитория должен быть ссылкой или вида owner/repo` | адрес не подходит под формат или длиннее 500 символов |
| `422` | `Описание длиннее 2000 символов` | описание длиннее 2000 символов |
| `422` | `Код проекта указывается латиницей, цифрами и дефисом` | код не подходит под `^[A-Za-z0-9][A-Za-z0-9-]*$` |
| `422` | `Код проекта не может состоять только из цифр` | код из одних цифр |
| `422` | `Код проекта длиннее 32 символов` | код длиннее 32 символов |
| `422` | `Код проекта не меняется` | `PATCH` прислал `code`, отличный от заданного, или пустой `code` у проекта с кодом |
| `422` | `Цена указывается числом, например 0.27` | цена не подходит под формат: `дорого`, `0.1234567`, `1 250`, пустая строка |
| `422` | `Цена не может быть отрицательной` | цена с минусом: `-0.27`, `-0,5` |
| `422` | `Нет полей для изменения` | `PATCH` с пустым телом |


Остальные отказы (`5xx`, `422` от невалидного JSON) контрактом не считаются.

**Цены за токены.** У проекта четыре цены — вход, выход, кэш-чтение и кэш-запись, — в
долларах США за **1 000 000 токенов**. По ним журнал расходов считает суммы записей.

| Где | Что видно | Когда |
|---|---|---|
| в базе | `Numeric(18, 6)`, `NOT NULL`, умолчание `0` | `0` — «не тарифицируется», а не «неизвестно» |
| в запросе | строка с точкой или запятой, до десяти знаков до разделителя и не больше шести после | принимаются `"0.27"`, `"0,27"`, `"1"`, `" 0.0049 "` |
| в ответе | строка ровно с шестью знаками — `"0.270000"` | `"0,27"` → `"0.270000"`, без цен → `"0.000000"` |
| на экране | `0,27 $ за 1 млн` | хвостовые нули обрезает фронтенд, сам цену не считает |

Цены необязательны и при создании проекта, и в `PATCH`: поле, которого нет в теле, не
меняется. Все четыре нуля — допустимое состояние проекта: цены сохранятся, а запись в
журнал сервер отклонит текстом `Цены проекта не заполнены`. Минус — отдельный отказ,
мусор и лишние знаки после разделителя — отказ про формат. Пробелы по краям снимаются,
пробелы внутри значения (`1 250`) — нет.

**`total_cost` в схемах проекта нет.** Итог проекта живёт только в ответе журнала
(`GET /api/projects/{id}/expenses`), чтобы его нельзя было случайно взять из другого
ответа и чтобы сумма строк на экране и итог считались одним и тем же числом. Присланное
в `PATCH` поле `total_cost` отбрасывается: один только `total_cost` в теле — пустая
правка, отказ `Нет полей для изменения`.

**Код проекта.** `code` — стабильный человеческий идентификатор проекта (`workflow`,
`CRMDormitory`). Он же становится `id` проекта в документе реестра отдела: файл реестра
держится на слагах, а склейка `plugins/registry.mjs` сопоставляет проекты по `id`, и
числовой `str(id)` расходился с ними. Задаётся код **один раз**, дальше он неизменяем —
смена кода сменила бы идентификатор проекта в реестре, поэтому ошибка в коде означает
новый проект. Стереть заданный код тоже нельзя. Пустой `code` (`""` или `null`) значит
«не задан»: у проекта без кода такой `PATCH` ничего не меняет, у проекта с кодом —
отказ. Код необязателен: пока он не задан, `id` проекта в реестре остаётся числовым, а
миграция `0010_project_codes` коды не бэкфиллит — нужные слаги знает человек, а не база.

**Soft delete.** `DELETE` не удаляет строку: он ставит `deleted_at = now()`, и строка
остаётся в таблице `projects` навсегда. В списке её больше нет, повторный `DELETE` и
`PATCH` по ней отвечают `404`, восстановить проект через интерфейс нельзя. Имя и код
удалённого проекта свободны — их можно занять заново. Физического удаления строк в
приложении нет, и очистки таблицы в задаче тоже нет: она растёт, политики хранения
пока не существует.

### Роли

Роль — она же пресет DSH: её `code` становится именем каталога в `agent-presets/`, поэтому
справочник из веба стал управляемым. Пути раздела раздвоены намеренно: роль читается и
создаётся по `/api/roles` (скиллы вложены в роль), а правка и удаление скилла — по id
скилла (`/api/skills/{id}`), потому что скилл адресуем сам по себе, а не только парой
«роль — скилл».

| Метод и путь | Тело запроса | Успех |
|---|---|---|
| `GET /api/roles` | нет | `200 [{id, code, title, description, skill_count, updated_at}]` — только живые, порядок по `id` |
| `POST /api/roles` | `{code, title, description?}` | `201` тот же объект |
| `PATCH /api/roles/{id}` | непустое подмножество `{title, description}` | `200` тот же объект |
| `DELETE /api/roles/{id}` | нет | `204` без тела (мягкое удаление) |

`description` у роли необязательно: отсутствие и пустая строка значат одно — «описания
нет», в колонке лежит пустая строка, а не `NULL`. `skill_count` считается на чтении по
живым скиллам роли; отдельной колонки под него нет, поэтому число в списке всегда свежее.

**Код не меняется.** `code` роли — имя каталога пресета: задаётся при создании и дальше не
меняется. `PATCH` с `code` в теле получает `422 Код роли не меняется`, а не молчаливое
игнорирование. Код мягко удалённой роли тоже занят навсегда: `_role_code_taken` смотрит и
на удалённые строки.

| Код | `detail` | Когда |
|---|---|---|
| `409` | `Роль с таким кодом уже есть` | код занят живой или мягко удалённой ролью (сравнение без учёта регистра) |
| `409` | `Роль стоит в отделах: сначала уберите её из них` | `DELETE` роли, на которую ссылается живой отдел |
| `409` | `Роль не удалось сохранить: одновременная правка` | гонка по уникальному индексу между чтением и записью |
| `404` | `Роль не найдена` | роли нет или она уже удалена — в том числе для `PATCH` и `GET .../skills` |
| `422` | `Укажите код роли` | код пуст после `strip()` |
| `422` | `Код роли указывается латиницей, цифрами и дефисом` | код не подходит под `^[a-z0-9][a-z0-9-]*$` |
| `422` | `Код роли длиннее 50 символов` | предел кода роли |
| `422` | `Код роли не меняется` | `PATCH` с `code` в теле |
| `422` | `Укажите название роли` | название пустое после `strip()` |
| `422` | `Название роли длиннее 100 символов` | предел названия роли |
| `422` | `Описание роли длиннее 2000 символов` | предел описания роли |
| `422` | `Нет полей для изменения` | `PATCH` с пустым телом |

Порядок проверок фиксирован — обязательность, длина, формат, — чтобы на теле с двумя
ошибками ответ был предсказуемым. Остальные отказы (`5xx`, `422` от невалидного JSON)
контрактом не считаются.

**Soft delete.** `DELETE` не удаляет строку: он ставит `deleted_at = now()`, и строка
остаётся в таблице `roles` навсегда вместе со своими скиллами. В списке её больше нет,
повторный `DELETE` и `PATCH` по ней отвечают `404`, восстановить роль через интерфейс
нельзя. Код удалённой роли свободным не становится.

**Сид.** Таблица `roles` наполняется сидом миграции `0003_departments` из константы
`DEFAULT_ROLES` (`backend/app/models/role.py`) — десять ролей в порядке таблицы
постановки. Сид остаётся: база, поднятая до этой задачи, уже имеет эти роли, и повторять
их `POST`-ом нельзя — код занят. Роли, заведённые из веба, живут рядом с сидовыми строками
и ничем от них не отличаются.

Отдел ссылается на роль по `id`, поэтому новая роль — это новая строка, а не правка
существующей: добавление роли не двигает уже сохранённые отделы. Отдельная ревизия нужна
и потому, что применённая ревизия не переигрывается: правка `DEFAULT_ROLES` на
существующей базе ничего не добавит.

### Скиллы ролей

Скилл — файл `skills/<code>/SKILL.md` в пресете роли: `title` — заголовок `#`,
`description` — frontmatter `description`, `sections` — заголовки `##` с их markdown.

| Метод и путь | Тело запроса | Успех |
|---|---|---|
| `GET /api/roles/{id}/skills` | нет | `200 [{id, code, title, description, sections, created_at, updated_at}]` — только живые, порядок по `id` |
| `POST /api/roles/{id}/skills` | `{code, title, description, sections}` | `201` тот же объект |
| `PATCH /api/skills/{id}` | непустое подмножество `{title, description, sections}` | `200` тот же объект |
| `DELETE /api/skills/{id}` | нет | `204` без тела (мягкое удаление) |

**Разделы** — упорядоченный массив `{"title", "body"}`. Порядок массива и есть порядок
заголовков `##` в файле, поэтому `PATCH` заменяет массив целиком: перестановка на экране —
это «Выше»/«Ниже» в том же теле, а не отдельная ручка над одним элементом. Пустой `body`
разрешён (заголовок без текста — законный раздел), пустой `title` — нет. `body`
сохраняется как прислан, без обрезки: markdown чувствителен к переводам строк и пробелам
внутри блока кода; `title` обрезается по краям. Принимается только массив: объект, строка
или `null` — отказ `Разделы должны быть массивом`, иначе «сохранил, а разделы пропали».
Значит и `POST` без этого поля — отказ: массив обязателен. Пустой массив допустим.

**Код скилла не меняется** — это имя каталога скилла и frontmatter `name`. Код уникален в
пределах роли, а не всего справочника.

| Код | `detail` | Когда |
|---|---|---|
| `409` | `Скилл с таким кодом у роли уже есть` | код занят живым или мягко удалённым скиллом этой роли |
| `404` | `Скилл не найден` | скилла нет или он уже удалён |
| `404` | `Роль не найдена` | роль для `GET`/`POST .../skills` удалена |
| `422` | `Укажите код скилла` | код пуст после `strip()` |
| `422` | `Код скилла указывается латиницей, цифрами и дефисом` | код не подходит под слаг |
| `422` | `Код скилла длиннее 64 символов` | предел кода скилла |
| `422` | `Код скилла не меняется` | `PATCH` с `code` в теле |
| `422` | `Укажите название скилла` | название пустое |
| `422` | `Название скилла длиннее 200 символов` | предел названия скилла |
| `422` | `Укажите описание скилла` | описание пустое — у скилла оно обязательно, иначе модель не видит скилл в каталоге |
| `422` | `Описание скилла длиннее 1000 символов` | предел описания скилла |
| `422` | `Название раздела не задано` | пустой `title` раздела |
| `422` | `Название раздела длиннее 200 символов` | предел заголовка раздела |
| `422` | `Текст раздела длиннее 20000 символов` | предел текста раздела |
| `422` | `Текст раздела должен быть строкой` | `body` пришёл объектом или числом — приведение `str()` уехало бы в `SKILL.md` мусором |
| `422` | `Разделов больше 50` | больше 50 разделов |
| `422` | `Разделы должны быть массивом` | `sections` не массив |
| `422` | `Нет полей для изменения` | `PATCH` с пустым телом |

Пределы — правило обеих половин: сервер отказывает `422`, фронт не даёт перейти предел
(`maxLength` на поле, неактивная кнопка «Добавить раздел» на пятидесятом). Код мягко
удалённого скилла тоже занят навсегда.

**Soft delete.** `DELETE` ставит `deleted_at`; строка остаётся в таблице `role_skills`, из
ответов исчезает. Восстановления через интерфейс нет.

### Пресеты для harness

Три машинные ручки — то, из чего плагин отдела раскладывает `agent-presets/<code>/`:
`GET /api/presets` (манифест), `GET /api/presets/{code}` (документ роли) и
`PUT /api/presets/{code}` (сохранить документ). Все три закрыты токеном надстройки в
заголовке `X-Registry-Token` — тем же, что у реестра проектов; незаданный в окружении
`REGISTRY_TOKEN` — не «пускать всех», а отказ.

```json
200 {"revision":"a3f19c2e7b10","roles":[{"code":"frontend","title":"Фронтенд","revision":"5b1d0c77e2a4","skill_count":3}]}
401 {"detail":"Токен реестра не принят"}
```

**Ревизия считается на чтении.** Дат в ней нет: ревизия документа — первые 12 hex символов
SHA-256 канонического JSON, ревизия набора — то же от строк `код:ревизия`, отсортированных
по коду. Отсюда два свойства, на которые опирается harness: повторное сохранение того же
документа ревизию не двигает (`changed: false`), а изменение любого поля двигает и её, и
ревизию набора.

**Документ роли** — единственная форма, из которой рендерятся `preset.yml` и `SKILL.md`:
`code`, `title`, `description`, `skills[]` с `sections[]`. Скиллы в документе идут по коду,
а не по `id`: порядок в теле `PUT` — достояние вызывающего, совпадение документа считается
по содержимому. Список скиллов в браузерных ручках (`GET /api/roles/{id}/skills`) остаётся
по `id`.

**Веб для роли авторитетен.** Роль, которая есть в вебе, живёт по документу из веба: скилл,
которого в документе нет, при `PUT` мягко удаляется. Роли, которой в вебе нет, harness не
трогает вовсе — поэтому пустая база не стирает пакетные скиллы. Заливка пакета в веб — это
`plugins/tools/presets-import.mjs`, а не экран: браузеру `PUT` не нужен и не выдан.

### Виды отделов

`GET /api/department-kinds` → `200 [{id, code, title, fields}]`, порядок по `id`.

Справочник видов живёт в таблице `department_kinds` и наполняется сидом миграции
`0006_department_kinds` из константы `DEFAULT_DEPARTMENT_KINDS`
(`backend/app/models/department_kind.py`): «Разработка» (`development`) и «Маркетинг»
(`marketing`). Управляющих ручек у видов нет — ни `POST`, ни `PUT`, ни `PATCH`, ни
`DELETE` не заведены и отвечают `405`: новый вид — это новая строка сида, новая ревизия
и правка фронта, а не правка применённой миграции.

`fields` — какие блоки страницы правки показывает вид, и порядок ключей здесь тоже
часть контракта: страница рисуется по этому списку, а не по своим константам.

| `code` | `title` | `fields` |
|---|---|---|
| `development` | `Разработка` | `enabled`, `schedule`, `roles`, `repo_path`, `base_branch`, `workspace`, `human_workspace`, `artifacts_dir`, `compose_project`, `max_rework`, `notifications` |
| `marketing` | `Маркетинг` | `repo_path`, `base_branch`, `workspace`, `human_workspace` |

Неизвестный `code` (строка в базе, под которую код не обновляли) получает `fields: []`:
справочник не падает и не отдаёт `500`, страница просто не показывает блоков.

То же поле `fields` есть и в ответе отдела — по виду этого отдела. Дублируется оно
намеренно: страница правки получает его из ручки отдела, не дожидаясь второго запроса.

Флаг работы отдела (`enabled`) стоит в наборе полей «Разработки» первым: выключенный
отдел диспетчер не обслуживает вовсе, и человек читает это до расписания и ролей. У
«Маркетинга» этого поля нет: конвейер обслуживает только отдел разработки.

### Отделы проекта

Отдел живёт внутри проекта: список и создание вложены в проект, правка и удаление
адресуются отделу. Плоских `GET /api/departments` и `POST /api/departments` больше нет —
это принятая смена контракта, а не регрессия.

Создание выбирает **только вид**: имя отдела — название вида (`Разработка`,
`Маркетинг`). Расписание приезжает пустым набором окон (`windows: []`), роли — `[]`,
строковые поля — `null`, лимит `3`, работа отдела `enabled: true`, уведомления
`false`, — всё это заполняется на странице правки. Работа отдела включена по
умолчанию: выключенный отдел перестаёт брать задачи, и `false` из ниоткуда остановил
бы работу после выкатки. Имя отдела не редактируется — оно следует за видом.

Отдельного признака «этот вид уже заведён» нет: занятость проверяется по **имени**, как
и до задачи. Для отделов, созданных этим контрактом, разницы не видно — имя всегда равно
названию вида, и повторное создание того же вида в проекте получает `409`. У отделов,
переживших миграцию `0006`, имя осталось прежним (`Поддержка` при виде `Разработка`, кадр
6 макета), поэтому такой проект может получить рядом ещё один отдел «Разработка»: две
строки одного вида в одном проекте спецификации не противоречат, а переименовывать
существующие отделы задача запрещает. Поэтому вид нельзя менять у существующего отдела
(`PATCH` его не принимает), а список проекта показывает вид у каждого отдела.

| Метод и путь | Тело запроса | Успех |
|---|---|---|
| `GET /api/projects/{project_id}/departments` | нет | `200` массив отделов — только живые отделы этого проекта, порядок по `id`, роли в порядке `id`; пустой проект — `[]` |
| `POST /api/projects/{project_id}/departments` | `{kind_id}` — обязателен и только он | `201` созданный отдел |
| `PATCH /api/departments/{department_id}` | любое непустое подмножество полей страницы правки (ниже) | `200` тот же объект; `role_ids` и `windows` заменяют набор целиком |
| `DELETE /api/departments/{department_id}` | нет | `204` без тела (мягкое удаление) |
| `GET /api/departments/{department_id}/process` | нет | `200 {document, defaults, roles, guards}` — `document: null`, если своего процесса у отдела нет; `defaults` — документ по умолчанию, `roles` — коды живых ролей, `guards` — каталог `[{id, title}]` |
| `PUT /api/departments/{department_id}/process` | документ процесса целиком (`version`, `labels`, `steps`) — не `PATCH` и не `{document: …}` | `200 {revision, document}` — `revision` это номер ревизии реестра, созданной сохранением |

**Процесс отдела — отдельный документ.** Таблица переходов, по которой диспетчер
исполняет конвейер, живёт в колонке `process` строки `departments` (миграция
`0014_department_process`; `NULL` — своего процесса нет, диспетчер работает на
умолчаниях) и читается/пишется **двумя** ручками выше, а не полем страницы правки:
таблица ступеней и имена 14 меток меняются только вместе. `PUT` проверяет документ
целиком и пишет колонку, потом пересобирает реестр — поэтому `revision` в ответе это
ревизия реестра, и `GET /api/registry` сразу отдаёт тот же `process` у отдела (ключ
есть всегда: `null` значит «своего процесса нет», иначе снятая таблица осталась бы в
кеше диспетчера). Порядок проверок и точные тексты `422` — в `app/schemas/process.py`;
формат документа и каталог стражей описаны в `plugins/docs/DEPARTMENT-PROCESS.md` §11.

Отдел в ответе — двадцать одно поле:

```json
{"id":277,"project_id":451,"name":"Разработка",
 "kind":{"id":1,"code":"development","title":"Разработка"},
 "fields":["enabled","schedule","roles","repo_path","base_branch","workspace","human_workspace",
           "artifacts_dir","compose_project","max_rework","notifications"],
 "windows":[],"roles":[],
 "repo_path":null,"base_branch":null,"workspace":null,"human_workspace":null,
 "artifacts_dir":null,"compose_project":null,"telegram_token":null,"telegram_chat_id":null,
 "max_rework":3,"enabled":true,"notifications_enabled":false,
 "created_at":"2026-11-19T18:17:24.665580Z","updated_at":"2026-11-19T18:17:24.665580Z"}
```

`kind_id` в ответе нет: вид приезжает объектом `kind`, а `id` вида фронту не нужен —
для выбора он берёт `GET /api/department-kinds`. `deleted_at` наружу не отдаётся.

Поля страницы правки — восемь строк, флаг работы отдела, лимит возврата, флажок
уведомлений, роли и окна времени:

| Поле | Предел | Что это |
|---|---|---|
| `enabled` | — | работа отдела: `false` — диспетчер отдел не обслуживает |
| `repo_path` | 500 | путь репозитория (`owner/repo`) |
| `base_branch` | 200 | базовая ветка |
| `workspace` | 500 | рабочее пространство отдела |
| `human_workspace` | 500 | рабочее пространство человека |
| `artifacts_dir` | 500 | директория артефактов |
| `compose_project` | 200 | имя compose-проекта стенда |
| `telegram_token` | 200 | API-токен бота проекта |
| `telegram_chat_id` | 64 | id чата для уведомлений |
| `max_rework` | `0..99`, по умолчанию `3` | сколько раз задача возвращается в работу |
| `notifications_enabled` | — | флажок уведомлений в Telegram |
| `role_ids` | — | набор ролей из `GET /api/roles` |
| `windows` | от 1 до 6 окон | окна времени работы `{"start_time": "ЧЧ:ММ", "end_time": "ЧЧ:ММ"}` |

Строковые поля снимают пробелы по краям, а `""` и `null` значат одно и то же —
«не заполнено»: значение стирается. Пустой `max_rework` возвращает умолчание `3`, а не
ноль; ноль — это «задачу не возвращать». `null` у флажка уведомлений и у флага работы
отдела — «не менять» (значения «пусто» у флажка нет), выключение флажка токен и id чата
не стирает. Выключение работы отдела стирает ещё меньше: расписание, роли, строки и
бота отдел сохраняет — флаг ничего не прячет и не удаляет.
Пустой список ролей допустим и стирает набор; повтор роли в `role_ids` схлопывается.

Проект задаётся **путём**, а не телом: в `POST` поля `project_id` нет, в ответе оно есть.
Первым шагом `GET` и `POST` проверяют, что проект жив: несуществующий или мягко
удалённый проект — `404` с тем же текстом `Проект не найден`, что у ручек проектов.
Проверка проекта идёт раньше проверок полей.

**Уникальность названия — в пределах проекта.** Имя отдела равно названию вида, поэтому
`409` на создании обычно означает «этот вид в проекте уже заведён»: одно и то же имя в
двух проектах — не конфликт, а «Разработка» и «Маркетинг» в одном проекте — норма.
Занятость считается по имени, а не по виду, поэтому у отделов с унаследованным именем (см.
выше) `409` на создание «Разработки» не срабатывает. Держат её частичный уникальный индекс
`uq_departments_project_name_alive` по
`(project_id, lower(name)) WHERE deleted_at IS NULL` и проверка в ручке: `lower()` в
SQLite опускает только латиницу, поэтому сравнение без учёта регистра делается в Python.
Имя удалённого отдела свободно — вид можно завести заново.

Время в ответе — строка `"ЧЧ:ММ"` (`"13:00"`, без секунд): поле `<input type="time">`
на фронте получает значение из этого поля без собственного форматирования, и секунды
сделали бы его невалидным. На вход время принимается строго как `ЧЧ:ММ`.

**Время работы — набор окон `windows`**, а не пара полей. Элемент списка — ровно
`{"start_time": "ЧЧ:ММ", "end_time": "ЧЧ:ММ"}`; других ключей нет. Окон от одного до
шести (`WINDOWS_MAX = 6`), пересечение запрещено, а касание концами (`13:00–18:00` и
`18:00–21:00`) пересечением не считается. `end_time` меньше `start_time` — это переход
через полночь (`13:00` → `04:00`) в **этом** окне, штатный случай: запрещено только
совпадение начала и конца. Порядок окон в ответе — по возрастанию `start_time`, его
задаёт сервер: фронт массив как пришёл и не сортирует.

Набор заменяется целиком, как `role_ids`: окна правятся одним списком, и «итогового
набора из базы» не собирается — у окон нет второй половины, которую надо было бы
доставать. Поэтому `PATCH` с `windows` — это новый набор, а не «правка одного окна».
Пустой список через правку недостижим: `windows: []` и `windows: null` — `422`
`Укажите хотя бы одно окно времени работы`. Отдел создаётся с `windows: []` (расписания
ещё нет) и пустым набор получает только от ручки создания.

Окна лежат в самой строке `departments` — колонка `windows` (`JSONB` на PostgreSQL,
`JSON` в тестах на SQLite), без второй таблицы и join-ов. Значение колонки
присваивается целиком: `MutableDict` и мутация списка на месте не используются — иначе
SQLAlchemy не увидел бы изменения, а `updated_at` не сдвинулся.

Отказы — та же часть контракта, что и у проектов: текст показывается пользователю
дословно.

| Код | `detail` | Когда |
|---|---|---|
| `409` | `Отдел с таким названием уже есть` | имя вида занято живым отделом проекта (сравнение без учёта регистра; у отделов с унаследованным именем не срабатывает) |
| `404` | `Проект не найден` | вложенные `GET` и `POST`: проекта нет или он мягко удалён; тот же текст, что у ручек проектов |
| `404` | `Отдел не найден` | отдела нет или он уже удалён — в том числе для `PATCH` |
| `422` | `Выбран вид отдела, которого нет в справочнике` | `kind_id` нет в `department_kinds` |
| `422` | `Нет полей для изменения` | `PATCH` с пустым телом или с одним `name` (имя не редактируется) |
| `422` | `Путь репозитория длиннее 500 символов` | `repo_path` длиннее 500 символов |
| `422` | `Базовая ветка длиннее 200 символов` | `base_branch` длиннее 200 символов |
| `422` | `Рабочее пространство отдела длиннее 500 символов` | `workspace` длиннее 500 символов |
| `422` | `Рабочее пространство человека длиннее 500 символов` | `human_workspace` длиннее 500 символов |
| `422` | `Директория для сохранения документов длиннее 500 символов` | `artifacts_dir` длиннее 500 символов |
| `422` | `Название проекта в Docker длиннее 200 символов` | `compose_project` длиннее 200 символов |
| `422` | `API telegram бота длиннее 200 символов` | `telegram_token` длиннее 200 символов |
| `422` | `Ваш ID длиннее 64 символов` | `telegram_chat_id` длиннее 64 символов |
| `422` | `Укажите хотя бы одно окно времени работы` | `windows` — пустой список или `null` |
| `422` | `Окон времени работы не может быть больше шести` | в `windows` больше шести окон |
| `422` | `Время работы указывается как ЧЧ:ММ, например 09:00` | время окна не `ЧЧ:ММ`, `25:00`, `12:60` или пустое |
| `422` | `Начало и конец рабочего времени совпадают` | `start_time == end_time` у окна |
| `422` | `Окна времени работы пересекаются` | два окна перекрываются (включая пересечение через полночь) |
| `422` | `Лимит возврата задачи указывается целым числом от 0 до 99` | `max_rework` вне `0..99` |
| `422` | `Выбрана роль, которой нет в списке ролей` | в `role_ids` есть id, которого нет в `roles` |
| `404` | `Отдел не найден` | `GET` и `PUT` процесса: отдела нет или он уже удалён |
| `422` | `Поддерживается только версия процесса 1` | `PUT` процесса: `version` не `1` |
| `422` | `Нужен объект процесса с полями version, labels, steps` | `PUT` процесса: тело не объект или в нём нет `labels`/`steps` |
| `422` | `Неизвестный ключ метки: «<key>»` | в `labels` есть ключ вне 14 ключей процесса |
| `422` | `Имя метки пустое: «<key>»` | в `labels` имя пустое после `strip()` |
| `422` | `У ступени «<id>» нет входящих меток` | `when` ступени пуст |
| `422` | `Дублируется id ступени: «<id>»` | два ступени с одним `id` |
| `422` | `Неизвестный ключ метки в ступени «<id>»: «<key>»` | в `when`/`unless`/`put`/`drop` ключ вне `labels` |
| `422` | `Неизвестный вид ступени у «<id>»: «<kind>»` | `kind` не `session`/`route`/`auto` |
| `422` | `Неизвестная роль у ступени «<id>»: «<role>»` | `role` не `null`, не резолвер и не код живой роли |
| `422` | `Неизвестный страж у ступени «<id>»: «<guard>»` | `guard` вне каталога стражей |
| `422` | `Ступень «<id>»: приоритет — целое от 1 до 999` | `priority` вне `1..999` или не целое |
| `422` | `Ступень «<id>»: у маршрутной ступени должен быть страж route` | `kind: "route"` со стражем, отличным от `route` |

Текстов отказа на пустое имя и на «хотя бы одну роль» больше нет: имя задаёт вид, а
пустой набор ролей допустим. Пустое тело `POST` и нечисловой `max_rework` — это `422`
схемы (`detail` — список ошибок pydantic), контрактом они не считаются.

Правка двигает `updated_at` всегда, в том числе когда меняются только роли: роли лежат в
таблице связи, и без явного обновления колонка «Обновлён» показывала бы дату до правки.

**Отдел между проектами не переезжает.** Присланный в `PATCH` `project_id` игнорируется и
строку не двигает: переноса отдела из проекта в проект в приложении нет. Тело из одного
`project_id` не меняет ничего, поэтому отдел возвращается как есть; остальные значения
`project_id` в ответе всегда равен проекту, в котором отдел завели.

**Soft delete отдела.** `DELETE` ставит `deleted_at`, из списка проекта отдел исчезает,
строка в `departments` остаётся. Строки связи в `department_roles` при этом **не
удаляются**: физического удаления в приложении нет ни в одном месте, поэтому набор ролей
удалённого отдела остаётся в базе, а таблица связи растёт. Восстановления через интерфейс
нет; имя удалённого отдела свободно — его можно занять заново. Одна роль может стоять в
двух отделах, в том числе в отделах разных проектов: связь многие-ко-многим, а не
владение.

**Сироты (`project_id IS NULL`).** Колонка `project_id` допускает `NULL`: отделы,
заведённые до появления привязки, не удаляются и не бэкфиллятся. В списках проектов такие
строки не видны ни в одном проекте, а плоские `PATCH` и `DELETE` по id их по-прежнему
достают — иначе мёртвый груз нельзя было бы убрать. Вид у сироты есть: `kind_id` —
колонка `NOT NULL`, и миграция `0006` бэкфиллит её всем строкам, включая сирот. На стенде
отдела разработки таких строк 241: их количество после миграции не меняется.
Уникальность имён среди сирот держит только проверка в ручке: `NULL` в уникальном
индексе не равен `NULL`.

Отделы удалённого проекта остаются в таблице живыми: вложенный `GET` удалённого проекта
отвечает `404`, а плоские `PATCH` и `DELETE` по такому отделу работают.

### Задачи проекта

Задача принадлежит проекту, поэтому путь вложен в него. Отдельной ручки чтения одного
проекта (`GET /api/projects/{id}`) нет: страница проекта получает объект проекта из
списка.

| Метод и путь | Тело запроса | Успех |
|---|---|---|
| `GET /api/projects/{project_id}/tasks` | нет | `200 [{id, project_id, name, description, cost, created_at, updated_at}]` — только задачи этого проекта, порядок по `id`; пустая база — `[]` |
| `POST /api/projects/{project_id}/tasks` | `{name, description?, cost?}` — обязателен только `name` | `201` тот же объект |

Обе ручки сначала проверяют, что проект жив: несуществующий или мягко удалённый
проект — `404` с тем же текстом, что у ручек проектов. Правки (`PATCH`) и удаления
(`DELETE`) задач в приложении нет: и ручек, и самого удаления.

**Стоимость — деньги в рублях с копейками.** Поле необязательное:

| Где | Что видно | Когда |
|---|---|---|
| в базе | `Numeric(12, 2)`, **допускает `NULL`** | `NULL` — стоимость не указана |
| в запросе | строка с точкой или запятой, до десяти знаков до разделителя и не больше двух после | принимаются `"1250"`, `"1250.5"`, `"1250,50"`, `" 1250,5 "` |
| в ответе | строка ровно с двумя знаками — `"1250.00"` — или `null` | `"1250,5"` → `"1250.50"`, без стоимости → `null` |
| на экране | `1 250,00 ₽` или «не указана» | показывает фронтенд, сам ничего не считая |

Отсутствие поля `cost`, `"cost": null` и `"cost": "  "` — одно и то же: «стоимость не
указана». Ноль и отрицательное число — по-прежнему отказ: `0` значит «бесплатно», и
подменять им «неизвестно» нельзя. Своё значение стоимости фронт отправляет строкой с
точкой, копейки в рубли не переводит.

Пробелы **внутри** значения — отказ: разделитель тысяч `1 250,50` ручка отвергает
текстом про формат, принимается только запись без пробелов (`1250,50`). Пробелы по
краям снимаются. `1 250,00 ₽` — это формат вывода на экране, в запрос он не уходит.

**Состав строки задачи на экране** — номер, название и стоимость; описания в списке
нет. Описание при этом остаётся полем задачи: колонка `description`, поля
`TaskCreate`/`TaskResponse` и `textarea` в форме. Это решение постановки, а не
недоделка: не выбрасывайте `description` из ответа и не возвращайте его в строку.

Отказы — та же часть контракта, что и у проектов: текст показывается пользователю
дословно.

| Код | `detail` | Когда |
|---|---|---|
| `404` | `Проект не найден` | проекта нет или он мягко удалён — на обеих ручках |
| `422` | `Укажите название задачи` | название пустое после `strip()` |
| `422` | `Название задачи длиннее 200 символов` | название длиннее 200 символов |
| `422` | `Описание длиннее 2000 символов` | описание длиннее 2000 символов (тот же текст, что у проекта) |
| `422` | `Стоимость указывается числом, например 1250.00` | стоимость не подходит под формат: `дорого`, `-5`, `12.345` |
| `422` | `Стоимость должна быть больше нуля` | указанное значение ноль или меньше: `0`, `0.00` |

Повтор названия задачи внутри проекта разрешён — уникального индекса у задачи нет.
Правки задачи нет, поэтому `updated_at` у неё совпадает с `created_at`, пока строку
не тронули в базе.

**Задачи удалённого проекта.** Удаление проекта мягкое, внешнего ключа с каскадом нет:
строки `tasks` удалённого проекта остаются в таблице, но наружу не показываются —
обе ручки отвечают `404`. Физического удаления в приложении нет ни в одном месте,
поэтому `tasks` растёт.

### Журнал расходов проекта

Расход — это строка журнала проекта: день, четыре количества токенов и посчитанная
сервером сумма. Путь вложен в проект, поэтому обе ручки сначала проверяют, что проект
жив: несуществующий или мягко удалённый проект — `404` с тем же текстом, что у задач и
отделов.

| Метод и путь | Тело запроса | Успех |
|---|---|---|
| `GET /api/projects/{project_id}/expenses` | нет | `200 {total, items}` — `items`: `[{id, project_id, spent_on, tokens_input, tokens_output, tokens_cache_read, tokens_cache_write, amount, created_at}]`, только записи этого проекта, порядок `spent_on DESC, id DESC`; `total` — стоимость проекта строкой ровно с двумя знаками; пустой журнал — `{"total": "0.00", "items": []}` |
| `POST /api/projects/{project_id}/expenses` | `{spent_on, tokens_input, tokens_output, tokens_cache_read, tokens_cache_write}` — все пять полей обязательны, лишнее (в том числе `amount`) отбрасывается | `201` созданная запись |

**Тело принимается свободными типами** (`spent_on` — `str | int | float | null`,
количества — `int | float | str | null`), а не `int`/`str`: с жёстким типом `422` схемы
pydantic отдаётся **до** ручки, и `12.5` получило бы массив в `detail` вместо текста
контракта, а мягко удалённый проект — `422` вместо `404`. Поэтому разбор и диапазон
делает ручка, после проверки проекта, и пропущенное поле тоже доходит до неё. Строка из
цифр (`"1500000"`) принимается как число, `"1 500"` и `"abc"` — отказ контракта.

**Сумму считает только сервер.** В теле запроса суммы нет и быть не может; присланное
поле `amount` отбрасывается. Формула:

```
amount = (tokens_input*price_input + tokens_output*price_output
          + tokens_cache_read*price_cache_read + tokens_cache_write*price_cache_write) / 1_000_000
```

Всё в `Decimal`, округление `ROUND_HALF_UP` до копейки — **один раз на запись**, а не по
слагаемым. Итог проекта — сумма уже округлённых сумм записей, поэтому сумма строк на
экране сходится с итогом копейка в копейку. Смена цен применяется только к новым
записям: суммы, уже лежащие в журнале, не пересчитываются, у записи `amount` — снимок.

**Итог проекта хранится в `projects.total_cost`** и прибавляется в той же транзакции,
что вставка записи, SQL-инкрементом (`UPDATE projects SET total_cost = total_cost +
:amount`). Два одновременных `POST` сумму не теряют; чтение-изменение-запись в Python
теряло бы. Чтение итога не пересчитывает журнал.

**Стоимость задач в журнал и в итог не входит** — это отдельная сущность (`tasks.cost`).
Правки и удаления записей журнала в приложении нет: и ручек, и самого удаления. Журнал
удалённого проекта остаётся в таблице, но наружу не показывается — обе ручки отвечают
`404`.

**Деньги в ответе — строки:** `amount` и `total` приходят ровно с двумя знаками
(`"0.41"`, `"10.53"`). Фронт переставляет строку в вид `0,41 ₽` и не округляет сам.
Формат у обеих сумм один — `app/money.py:format_money`: копий в ручке и схеме нет,
иначе правка вида денег разошлась бы между строкой журнала и итогом.

Отказы — та же часть контракта, что и у задач: текст показывается пользователю дословно.

| Код | `detail` | Когда |
|---|---|---|
| `404` | `Проект не найден` | проекта нет или он мягко удалён — на обеих ручках, раньше проверок тела |
| `422` | `Дата указывается как ГГГГ-ММ-ДД, например 2026-11-05` | `spent_on` не `ГГГГ-ММ-ДД` (`05.11.2026`, `2026-11-5`), не строка (`null`, `20261105`) или такой даты нет (`2026-02-30`) |
| `422` | `Количество токенов указывается целым неотрицательным числом` | любое из четырёх количеств меньше нуля, больше `10^12` или не целое (`12.5`, `"1 500"`, `"abc"`, `null`, `true`), а также строка цифр длиннее 13 знаков — она уже за потолком и не разбирается |
| `422` | `Укажите хотя бы одно количество токенов` | все четыре количества нулевые |
| `422` | `Цены проекта не заполнены` | у проекта все четыре цены нули — писать расход не по чему |

Порядок проверок — тоже контракт: сначала `404`, потом дата, количества, «хотя бы одно
количество» и только затем цены. Поэтому у пустых количеств текст про количества, а не
про цены.

Булево `true` в количестве — тоже отказ контракта, а не «единица»: `bool` — подкласс
`int`, и без отдельного члена в объединении типов схемы pydantic привёл бы `true` к `1`,
создал запись и посчитал по ней деньги. Поэтому в `ExpenseCreate` у четырёх количеств
`bool` объявлен **первым** членом объединения, и до ручки значение доезжает булевым, где
`validate_tokens` отказывает текстом про целое число. Число `1` при этом остаётся
количеством: разбор типа в pydantic предпочитает точное совпадение.

**Экран вкладки «Расходы» — половина фронтенда** и описан отдельным разделом ниже
(«Вкладка «Расходы» на странице проекта»): он работает ровно с этим контрактом.
Замороженный макет и состояния — `mockups/53/`, `data-testid` вкладки, строки цен, окна
записи и окна цен перечислены в `mockups/53/notes.md`.

### Реестр проектов отдела

Реестр — документ формата v2 («проект → вложенные отделы»), и это единственный
источник правды о проектах для плагина диспетчера: он забирает документ ручкой
`GET` и кладёт кешем в `projects.json` каталога состояния. В базе документ живёт
ревизиями в таблице `registry_documents`. Экрана правки реестра в приложении нет —
это отдельная задача; ручки обслуживают плагин и человека с `curl`.

**Все три ручки требуют заголовок `X-Registry-Token`** со значением
`REGISTRY_TOKEN` из `.env`. Незаданный `REGISTRY_TOKEN` — это отказ, а не «пускать
всех»: в документе лежат токены телеграм-ботов, а аутентификации в приложении нет.

| Метод и путь | Тело запроса | Успех |
|---|---|---|
| `GET /api/registry` | нет | `200` — документ v2 последней ревизии, ровно как сохранён |
| `PUT /api/registry` | документ v2 свободным телом | `200 {revision, stored_at}` — записана новая ревизия |
| `POST /api/registry/rebuild` | нет | `200 {revision, stored_at, document}` — документ собран из `projects`/`departments` |

Ревизии только добавляются: `PUT` и `rebuild` пишут новую строку, прошлые не
меняются, `GET` отдаёт последнюю.

`rebuild` собирает документ из базы: `id` проекта — строка `projects.id`, `title` —
`projects.name`, отдел — `kind` из справочника видов и `title` из `departments.name`.
Незаполненное поле в документ не попадает вовсе (а не приходит `null`: плагин
подставляет умолчание только на отсутствующем ключе), окна работы — массивом `windows`
с ключами `start`/`stop` (все окна отдела, в порядке колонки; пустой набор — ключа в
документе нет), `telegram` — только при включённых уведомлениях и обоих заполненных
полях. `enabled` — исключение из правила «незаполненное не попадает»: флаг работы
отдела приходит в документе **всегда**, потому что отсутствие ключа диспетчер читает
как «отдел включён», и выключенный в вебе отдел молча работал бы дальше. `maxRework`
отдаётся так же всегда. `default` ручка не выставляет: в базе такого признака нет, это
локальный ключ файла. Проект без отделов в документ не попадает.

Документ сохраняется как прислан: ручка проверяет форму по таблице отказов, но не
нормализует её и своих умолчаний не дописывает — форму v2 знает
`plugins/registry.mjs` в репозитории отдела, и вторая копия правил в схемах
разошлась бы с первой.

| Код | `detail` | Когда |
|---|---|---|
| `401` | `Токен реестра не принят` | нет заголовка, токен не совпал или `REGISTRY_TOKEN` не задан |
| `404` | `Реестр ещё не собран` | `GET`: в таблице ревизий ещё нет ни одной строки |
| `422` | `Поддерживается только версия реестра 2` | `version` не равна `2` |
| `422` | `В реестре нет ни одного проекта` | `projects` — не массив или пуст |
| `422` | `У проекта не задан id` | у проекта нет `id` или он пустой |
| `422` | `Повторяющийся id проекта: «<id>»` | два проекта с одним `id` |
| `422` | `У проекта «<id>» нет ни одного отдела` | `departments` пуст или в нём нет отделов с заполненным `kind` |
| `422` | `У проекта «<id>» больше одного отдела разработки` | два отдела `kind: "development"` — диспетчер обслуживает ровно один |
| `422` | `Время работы указывается как ЧЧ:ММ, например 09:00` | окно задано не парой или формат не `ЧЧ:ММ` (в том числе `25:00`) |
| `422` | `Начало и конец рабочего времени совпадают` | у окна `start` равен `stop` |
| `422` | `default указывает на неизвестный проект: «<id>»` | `default` не из списка `id` документа |
| `422` | `У бота проекта «<id>» не задан токен или id чата` | в `telegram` задана только половина пары |
| `409` | `Ревизию реестра не удалось записать: одновременная запись` | номер ревизии заняли между чтением и вставкой — три попытки |
| `500` | `Реестр повреждён: документ последней ревизии не читается` | тело последней ревизии не разбирается как JSON-объект |

Порядок проверок фиксирован — версия, список проектов, проект, расписание,
`default`, бот — поэтому документ с двумя ошибками даёт предсказуемый ответ.
Незнакомый необязательный ключ отдела сохранение не роняет: `frontendPort`, `areas`
и `labels` живут только в файле реестра, а не в базе веба. `enabled` в этот перечень
больше не входит: с `0011_department_enabled` он приходит из базы, а небулево значение
в присланном руками документе проверка пропускает как есть — диспетчер прочтёт его
как «включён», и это записанное решение, а не недоделка.

Полная схема — в `/openapi.json` и `/docs` того же сервиса.

### Журнал расхода смен

Расход считает harness, а не веб: цена сессии складывается из токенов по тарифам
(`costOf` в `plugins/usage-ledger.mjs` отдела), и пересчитывать её здесь нельзя —
при смене тарифов прошлые смены остались бы с другими деньгами. Поэтому закрытая
смена приходит **снимком**: интервал, причина закрытия, тарифы расчёта, сессии и
итоговая цена одним телом. Журнал их хранит и складывает.

Единица журнала — смена проекта: `shift_key` (метка смены: дата её начала и время
начала окна, например `2026-11-21T13:00`), `started_at → ended_at`,
`reason` (`window` — закрылось окно смены, `manual` — человек позвал
`dev_department_summary`). Детализация внутри — сессии ролей: тикет (может быть
пустым), роль, id сессии, источник, число ходов, токены `in/out/cacheRead/cacheWrite`
и цена. Одна сессия входит в суммы проекта один раз: продолженный диалог, который
смена взяла из прошлой (`carried`), повторно не записывается. Это осознанное
расхождение с текстом Telegram-сводки: там дневная картина смены, здесь — журнал, и
двойной счёт в суммах проекта недопустим.

Ключ обязан различать смены одних суток: в расписании отдела их две (`13:00–04:00`
и `07:00–09:00`), и одной даты не хватило бы — вторая смена пришла бы с уже занятой
парой `(project_ref, shift_key)` и получила бы `200 changed:false`, то есть её расход
не записался бы. Поэтому harness присылает `дата + 'T' + ЧЧ:ММ` начала окна: время
берётся из расписания, а не из фактического старта, чтобы повторная отправка того же
тела из очереди давала тот же ключ. Веб `shift_key` не разбирает — это строка до 64
символов, ключ идемпотентности.

| Метод и путь | Тело запроса | Успех |
|---|---|---|
| `POST /api/usage/shifts` | `{project_ref, project_title, shift_key, started_at, ended_at, reason, rates, sessions[], totals}` | `201 {shift_id, accepted, skipped, sessions_count, cost_usd, changed: true}` |
| `GET /api/projects/{project_ref}/usage` | нет | `200 {project_ref, project_title, totals, shifts[]}` — смены от новых к старым |
| `GET /api/usage/shifts/{shift_id}` | нет | `200` — смена теми же полями, что пришли в `POST`, плюс `sessions[]` |
| `GET /api/usage/projects` | нет | `200 [{project_ref, project_title, shifts, sessions, tokens, cost_usd, last_shift_at}]` |

`rates` — те же четыре тарифа, что `usageRates` в `dev-department.json`:
`{inputUsdPerM, cacheReadUsdPerM, cacheWriteUsdPerM, outputUsdPerM}`. Сессия —
`{issue_number?, issue_title?, role, session, source?, turns, tokens: {in, out,
cacheRead, cacheWrite}, cost_usd}`. Деньги в ответах — строки с шестью знаками
(`"0.420000"`), в запросе — числа: `Numeric(14,6)` не переживает `float`.

**`POST` закрыт токеном `X-Registry-Token`** (тот же общий токен надстройки, что у
реестра и пресетов): писать в журнал может harness, а не браузер. Три `GET` открыты —
их читает интерфейс, поэтому `project_ref` в них это `id` проекта из реестра отдела, а
не `projects.id` базы: журнал живёт отдельно от справочника, внешнего ключа нет.

Повторный `POST` с той же парой `(project_ref, shift_key)` нового расхода не создаёт:
ответ `200`, `changed: false`, `accepted: 0`, а `skipped` равно числу сессий в теле;
числа в ответе читаются из уже сохранённой смены. Так недошедший ответ не превращается
во вторую смену. Сессия, уже записанная за этим проектом (в любой прошлой смене),
пропускается и считается в `skipped`.

| Код | `detail` | Когда |
|---|---|---|
| `401` | `Токен реестра не принят` | нет заголовка, токен не совпал или `REGISTRY_TOKEN` не задан |
| `404` | `Проект не найден` | у проекта ещё нет ни одной смены |
| `404` | `Смена не найдена` | `shift_id` не существует |
| `422` | `Укажите проект смены` | `project_ref` пуст или тело не объект |
| `422` | `Укажите ключ смены` | `shift_key` пуст |
| `422` | `Смена должна иметь начало и конец` | время не разобрано или конец раньше начала |
| `422` | `Причина закрытия смены указывается как window или manual` | `reason` — не `window` и не `manual` |
| `422` | `Не переданы тарифы расчёта` | `rates` не объект или в нём нет одного из четырёх ключей |
| `422` | `Сессия без роли или id` | у сессии нет `role` или `session` |
| `422` | `Отрицательный расход` | любой токен или `cost_usd` меньше нуля |
| `422` | `Расход по сессиям не сходится с итогом` | `totals.cost_usd` расходится с суммой сессий больше чем на `0.000001` |
| `422` | `Слишком много сессий в смене` | больше 500 сессий в одном теле |
| `422` | `Расход по сессии больше допустимого` | сумма сверх разрядности колонки (`Numeric(14,6)`): `100000000` и больше |
| `409` | `Смену не удалось записать: одновременная отправка` | пару `(project_ref, shift_key)` заняли между чтением и вставкой; конфликт ловится на `flush`, а не вылетает `500` |

Порядок проверок фиксирован — проект, ключ смены, время, причина, тарифы, число
сессий, сессии по одной, итог — поэтому тело с двумя ошибками даёт предсказуемый
ответ. Сумма пишется по принятым сессиям: пропущенная (уже записанная) в итог не
входит, иначе деньги посчитались бы дважды.

Сверх таблицы стоят три защиты от сломанного отправителя, а не отказы для человека:
`422` на значение длиннее колонки (вместо `500` от базы), на строку вместо числа и на
сумму сверх разрядности денежной колонки. Приходят они только от машины и в интерфейсе
не показываются.

Миграция — `0012_usage` (`usage_shifts` и `usage_sessions`), обратима: `downgrade`
удаляет обе таблицы. Ревизия идёт после `0011_department_enabled`: журнал встаёт в
общую цепочку и не заводит вторую голову рядом с чужими ревизиями.

### Экран журнала: вкладка «Расходы»

Экран рисует вкладка «Расходы» страницы проекта (`components/ProjectExpenses.tsx`), и
читает он две ручки: журнал проекта `GET /api/projects/{id}/expenses` (обе половины одним
списком и итог проекта) и детализацию одной смены `GET /api/usage/shifts/{id}` (сессии
смены). Клиенты — `api/expenses.ts` и `api/usage.ts`.

Сумм экран не считает: `total` журнала, `amount` строки, `cost_usd` смены и `cost_usd`
сессии приходят посчитанными строками с шестью знаками, и фронт только выбирает, сколько
знаков показать (`119,23 $`, а ненулевую мелочь — `0,0004 $`). Цена строки — снимок на
момент записи: правка цен прошлые записи не пересчитывает, поэтому сумма в ведомости не
«поедет» после сохранения нового прайса.

Второй ручки журнала фронт не держит: `GET /api/projects/{ref}/usage` остаётся машинной
(её спрашивают отдел и реестр), а страница проекта читает объединённый журнал — двух
половин одного раздела на двух экранах больше нет (#72).

Подробности экрана, его состояния и `data-testid` — раздел «Вкладка «Расходы» на
странице проекта».

## Оболочка приложения

Слева — бренд и меню из двух разделов: «Проекты» (`nav-projects`) и «Роли» (`nav-roles`).
У выбранного пункта `aria-current="page"`, у «Проектов» ещё и бейдж с количеством проектов:
число берётся из загруженного списка, поэтому бейджа нет, пока список не прочитан или не
прочитался. Бейджа у «Ролей» нет и не было: число ролей видно в шапке карточки справочника.

Оба раздела смонтированы постоянно, невыбранный скрыт атрибутом `hidden`. Поэтому переход
из «Проектов» в «Роли» и обратно не теряет состояние: открытая страница проекта, выбранная
на ней вкладка, прокрученный список и открытая роль остаются там, где их оставили.

Третьего пункта меню нет: отделы живут вкладкой на странице проекта (`nav-departments`
удалён вместе с отдельным экраном «Отделы», вместе с ним ушёл и бейдж отделов).
Счётчик отделов остался один — в шапке карточки «Список отделов».

Роутера и отдельных URL в приложении нет: F5 всегда открывает «Проекты», страница
проекта, выбранная на ней вкладка и выбранный раздел живут состоянием оболочки.
Под содержимым — подвал.

## Экран «Проекты»

Шапка с крошками, заголовок «Проекты» с кнопкой «Добавить проект», карточка списка,
полоса состояния сервиса под ней и подвал. Макет — `mockups/32/` в ветке задачи #32.

- Список читается с сервера: `GET /api/projects` относительным путём, запрос
  проксирует nginx на том же origin, поэтому CORS не нужен. Адрес API в коде не
  зашит — его задаёт окружение стенда.
- Каждая строка: название, описание (пустое описание — пустая строка, без заглушки),
  адрес репозитория моноширинным, дата обновления и действия под кнопкой «⋯» —
  «Изменить» и «Удалить».
- Клик по строке открывает страницу проекта. Название в строке — кнопка
  (`project-item-open`): до строки можно дойти клавиатурой, и Enter/Space на названии
  делают то же, что клик. Клик по «⋯» и по пунктам меню страницу **не** открывает:
  действия строки останавливают всплывание.
- Одно окно на создание и правку: «Название», «Описание», «Адрес репозитория»,
  «Код проекта», «Сохранить» и «Отмена»; `role="dialog"`, `aria-modal`, Esc и подложка
  закрывают окно, Tab удерживается внутри, фокус возвращается на кнопку, которая окно
  открыла.
- «Код проекта» — необязательное поле: пустое значит «не задан», и проект в реестре
  остаётся под числовым `id`. У проекта с заданным кодом поле в правке только для
  чтения, подсказка под ним — `Код не меняется`; в тело `PATCH` такой код не попадает,
  поэтому «Код проекта не меняется» из окна не приходит. Код из одних цифр, длиннее
  32 символов и с посторонними символами отклоняет сервер, а текст его отказа виден
  под полем дословно: своих формулировок окно не добавляет.
- В строке списка код показывается, только если задан (`project-item-code`), в той же
  строке, где название и описание.
- Удаление — подтверждение с названием проекта; во время запроса кнопки неактивны.
- После создания, правки и удаления список перечитывается с сервера. Оптимистичных
  обновлений нет: на экране только то, что вернул сервер.

| `Загрузка…` | список читается |
| `Пока нет проектов` | сервер вернул пустой массив |
| текст отказа и кнопка `Повторить` | список не загрузился |
| `Сохраняю…`, кнопки неактивны | запрос формы в полёте, окно открыто |
| текст отказа дословно из `detail` | `409`/`422` при сохранении, окно открыто |
| `Удаляю…`, кнопки неактивны | запрос удаления в полёте |

### Страница роли

Крошки «Приложение / Роли / <название>», кнопка «← К ролям», заголовок с названием роли,
описание, под ним код моноширинным и дата обновления. Справа в шапке — «Изменить роль» и
«Удалить роль»: обе относятся к роли целиком, а не к списку скиллов под ними.

- Возврат «← К ролям» и удаление роли возвращают в список и перечитывают его: в строке
  могли измениться название и число скиллов.
- Карточка «Пресет DSH» — состояние раскладки в `~/.dsh/.agent-presets`. Манифест
  `/api/presets` закрыт токеном надстройки (`X-Registry-Token`), и в браузерной сборке
  токена нет намеренно: с ним страницу мог бы переписать любой, кто её открыл. Поэтому по
  умолчанию карточка честно говорит, что ревизию раскладки показывает статус отдела
  (`dev_department_status`, поле `presetsSync`), и **не** отправляет запрос: `401` здесь был
  бы ожидаемым и ничего не объяснял. Если стенд задал токен сборки
  (`VITE_REGISTRY_TOKEN`), карточка читает манифест и показывает ревизию роли или
  дословный отказ.
- Карточка «Скиллы роли»: счётчик, кнопка «Добавить скилл», список строк. Строка: название,
  код моноширинным, число разделов и дата; действия — «Изменить» и «Удалить».
  Список читается отдельной ручкой `GET /api/roles/{id}/skills`, а не в составе роли.
- Окно скилла — широкое: «Код», «Название», «Описание» и секция «Разделы». Разделы правятся
  по одному: заголовок `##` и markdown-текст, кнопки «Выше»/«Ниже»/«Удалить» у каждого и
  «Добавить раздел» под списком. Порядок разделов на экране — порядок `##` в файле:
  перестановка отправляется тем же `PATCH` целиком, а не отдельной ручкой.
- Пределы полей — те же, что у валидаторов сервера: `maxLength` на поле (код роли 50, код
  скилла 64, название роли 100, название скилла 200, описание роли 2000, описание скилла
  1000, заголовок раздела 200, текст раздела 20 000), «Добавить раздел» гаснет на
  пятидесятом. Фронт не даёт перейти предел, но последнее слово за сервером: отказ
  показывается дословно.

| Что видно | Когда |
|---|---|
| `Загрузка…` в карточке скиллов | `GET /api/roles/{id}/skills` в полёте |
| `Пока нет скиллов` | сервер вернул пустой массив |

## Вкладка «Отделы» на странице проекта

Отделы живут внутри проекта, поэтому отдельного экрана у них нет: вход один — вторая
вкладка на странице проекта. Макет — `mockups/51/`: он же макет окна создания и страницы
правки; прежние макеты карточки — `mockups/42/` и `mockups/34/`, окна времени работы в
строке и в форме — `mockups/50/`.

Отдел создаётся **выбором вида**, а не вводом имени: имя отдела равно названию вида.
Дальше всё, что у отдела есть, заполняется на странице правки — она описана следующей
главой. Плоских `GET /api/departments` и `POST /api/departments` больше нет, поэтому
прежнее окно с названием, `department-form*` и `nav-departments` ушли вместе с ними.

- Список читается с сервера: `GET /api/projects/{project_id}/departments` относительным
  путём через nginx. Проект задаётся путём, а не телом: в окне «Новый отдел» поля
  проекта нет и в тело запроса `project_id` не подставляется.
- В шапке карточки — количество с правильным окончанием: «1 отдел», «2 отдела»,
  «5 отделов», и кнопка «Добавить отдел» рядом с ним (`card__tools`, как «Добавить
  задачу» у задач).
- Строка: название, под ним вид мелким текстом (`department-item-kind`), время работы —
  **все окна** через запятую коротким тире внутри окна (`07:00–09:00, 13:00–04:00`), под
  ними суммарная длительность («9 ч», «17 ч · через полночь»), роли через запятую по
  названиям из справочника, дата обновления и действия под «⋯» — «Изменить» и «Удалить».
  Сетка строки и заголовки колонок не менялись: вид стоит строкой под названием, а не
  отдельной колонкой, колонка времени остаётся 8.5 rem.
- У отдела с `enabled: false` под видом стоит третья строка «отдел выключен»
  (`department-item-disabled`): такой отдел диспетчер не обслуживает, хотя настройки и
  роли у него на месте. Пометка — не ошибка, поэтому это отдельная строка того же кегля,
  но тяжелее и темнее вида, а не пилюля, капс или `--danger`. У включённого отдела третьей
  строки нет, и высота его строки не меняется; у вида без флага (у «Маркетинга») пометки
  не бывает.
- Окна в ячейке идут друг под другом, по одному в строке (запятая остаётся концом
  предыдущей строки): разряды `13:00` и `07:00` встают друг под другом, и набор читается
  как расписание. На ширине ≤ 900 px окна встают в одну строку через запятую — там у
  времени вся ширина. Одно окно выглядит ровно как раньше.
- Расписания может не быть: пустой набор окон — в значении «нет расписания», а
  длительность пуста. Пустой набор ролей — прочерк «—»: пустое место читается как
  «не догрузилось».
- Время — часть контракта: сервер отдаёт `"13:00"`, фронт показывает его как есть и
  массив окон не сортирует — порядок серверный, по возрастанию начала. Поэтому образец
  `07:00–09:00, 13:00–04:00` — это именно порядок, а не набор: окна через полночь
  сортируются по **началу**, и `13:00–04:00` встаёт вторым. В макете `mockups/50/` тот же
  набор нарисован обратным порядком как иллюстрация — экран показывает серверный.
  Переход через полночь (`end_time` меньше `start_time`) — штатный случай: длительность
  каждого окна считается по кругу суток, сумма складывается из длительностей окон (окна не
  пересекаются — это правило сервера), а слова «через полночь» снимают вопрос «почему
  конец раньше начала». Ни один экран его не «исправляет».
- Создание — окно «Новый отдел» (`DepartmentCreateDialog`): один `role="radiogroup"` из
  `GET /api/department-kinds`, у каждого варианта название и пояснение, что вид даёт.
  Имени в окне нет. Пока справочник грузится, «Создать» неактивна; отказ справочника
  рисуется его текстом с кнопкой «Повторить». `409` (вид уже заведён в проекте) и `422`
  показываются в окне дословно, введённое не теряется, окно не закрывается. «Отмена»
  работает всегда: окно должно закрываться, даже если сервер не ответил.
- «Изменить» открывает страницу правки отдела, «Удалить» — общее окно подтверждения
  (`ConfirmDialog`) с текстом «Отдел «{название}» исчезнет из списка. Восстановить его
  через интерфейс нельзя.».
- Строка списка не кликабельна: правка открывается пунктом «Изменить», как в макете.
- После создания, сохранения на странице правки и удаления список перечитывается с
  сервера. Оптимистичных обновлений нет.

## Страница правки отдела

Открывается пунктом «Изменить» в строке отдела и занимает содержимое раздела целиком —
так же, как страница проекта занимает содержимое «Проектов». Крошки «Приложение /
Проекты / {проект} / {отдел}», кнопка «← К проекту» в шапке, название отдела, под ним
«Вид: {название вида} · Обновлён 28 окт 2026», ниже карточка «Настройки отдела» с полями
и полосой кнопок внизу. Адреса у страницы нет: это состояние `ProjectPage`, а не маршрут,
поэтому F5 возвращает к списку «Проекты». Макеты — `mockups/51/` (страница целиком) и
`mockups/50/` (блок «Смена» со списком окон).

**Состав и порядок полей задаёт вид, а не фронт.** `department.fields` приезжает вместе с
отделом и перечисляет блоки в порядке показа; страница рисует только их и в этом порядке.
Секции — «Смена», «Где работает отдел», «Возврат и уведомления» — лишь надзаголовки:
порядок внутри секции всё равно берётся из `fields`. Незнакомый ключ (третий вид из новой
ревизии) не рисуется и страницу не роняет, и это единственное место, где фронт знает
список ключей: подписи и контролы живут на фронте, потому что контракт называет поле
`repo_path`, а не «Путь репозитория».

- **Сохранение — `PATCH` отрисованными полями.** Состав тела берётся из `department.fields`,
  поэтому «Маркетинг» не присылает время, роли и уведомления, а пустое поле уходит как
  `null` («не заполнено»), непустое — как ввели. Своей проверки длин и диапазонов у
  страницы нет: пределы и формат знает сервер.
- **Строки цифр у лимита возврата.** Поле лимита текстовое (`inputMode="numeric"`) и
  принимает только цифры: нецифровой ввод — это `422` схемы, который контрактом не
  считается и своего текста не имеет, поэтому с экрана он недостижим. Диапазон `0..99`
  по-прежнему проверяет сервер и отвечает своим текстом, пустое поле — `null`
  (умолчание сервера, `3`).
- **Флаг работы отдела.** `enabled` — первое поле секции «Смена» (первым его отдаёт и
  каталог вида): чекбокс «Работа отдела включена» с постоянной подсказкой «Выключенный
  отдел не берёт задачи из очереди». Подсказка видна в обоих состояниях, в отличие от
  блока уведомлений: за флажком полей нет, а последствие нужно прочитать до того, как
  снимаешь галочку. При выключении ничего не гаснет и не прячется — расписание, роли, пути
  и уведомления остаются редактируемыми, а флаг уходит тем же единственным `PATCH`
  (`patch.enabled = enabled`), без подтверждения, отмены и тоста. Значение берётся из
  ответа и других полей не выводится (пустое расписание ≠ выключено); у вида без флага
  чекбокса нет, и фронт его не подставляет.
- **Выключенный флажок уведомлений не стирает токен.** Поля «API telegram бота» и «Ваш ID»
  при выключенном флажке не рисуются вовсе, а `telegram_token`/`telegram_chat_id` уходят в
  теле только вместе с включённым флажком: значения из базы остаются на месте.
- **Расписание — список окон.** Рядов от одного до шести: «Добавить окно» добавляет ряд,
  крестик убирает свой (у единственного окна кнопки нет). Окна уходят в тело `windows`
  целиком, в том порядке, в каком стоят на экране: сервер заменяет набор и сортирует
  ответ. Своей проверки пересечений, формата и предела у страницы нет — `windows: []`,
  пересечение, семь окон и кривое время приходят серверными текстами. Отдел без
  расписания (создан видом) открывается одним пустым рядом.
- **Пустые ряды — это пустой набор, а не пустые поля.** Если все ряды пусты целиком, в
  тело уходит `windows: []`, и сервер отвечает «Укажите хотя бы одно окно времени
  работы»: человек, правящий только путь репозитория у отдела, заведённого видом, должен
  услышать про окно, а не про формат времени в поле, которого он не касался. Частично
  заполненный набор уходит как есть — там серверный отказ про `ЧЧ:ММ` и есть точный
  ответ.
- **Роли** читаются из справочника, пока он грузится — «Загрузка ролей…», счётчика нет и
  «Сохранить» неактивна: набор ролей на экране ещё неполон. Отказ справочника рисуется его
  текстом с «Повторить» и сохранение не блокирует — остальные поля от ролей не зависят, а
  `role_ids` в тело тогда не попадает: переписывать роли вслепую нельзя.
- **Во время запроса** кнопка показывает «Сохраняю…», обе кнопки неактивны, а
  «Добавить окно» и крестики окон гаснут: набор окон не должен меняться, пока уходит
  отправленный.
- **Отказ** рисуется дословно из `detail` в `department-edit-error` и помечает поле
  `aria-invalid`: текст отказа контракт не связывает с полем, поэтому связь «текст →
  поле» держит фронт (по узнаваемому обороту текста). Введённое не теряется.
- **Успех** — `onSaved()`: страница закрывается, список отделов перечитывается, открытой
  остаётся вкладка «Отделы». «← К проекту» и «Отмена» возвращают без запроса.

| Что видно | Когда |
|---|---|
| `Загрузка ролей…`, счётчика нет, «Сохранить» неактивна | справочник ролей в полёте (`GET /api/roles`) |
| текст отказа справочника и «Повторить», чекбоксов нет | `GET /api/roles` не ответил |
| `Сохраняю…`, кнопки и крестики окон неактивны | `PATCH` в полёте |
| текст отказа дословно из `detail` в `department-edit-error` | `422`/`404` при сохранении, страница открыта |
| `Укажите хотя бы одно окно времени работы`, `Окна времени работы пересекаются`, `Окон времени работы не может быть больше шести` в `department-edit-error`, поля окон с `aria-invalid` | серверные отказы расписания: пустой набор, пересечение, седьмое окно |
| `Нет полей для изменения` в `department-edit-error` | вид без полей: `PATCH` с пустым телом — контрактный отказ сервера, а не ошибка фронта |
| `Сервер не отвечает` | api недоступен: сеть, остановленный контейнер, прокси |

## Страница проекта и её вкладки

Страница открывается кликом по строке «Проектов» и занимает содержимое раздела целиком:
крошки «Приложение / Проекты / {название}», кнопка «← К проектам» в шапке, название
проекта, его описание как есть, служебная строка «репозиторий моноширинным · Стоимость
119,23 $ · Обновлён 28 окт 2026», полоса подразделов из трёх вкладок — «Задачи»,
«Отделы» и «Расходы» — и карточка выбранной вкладки под ней. Макеты — `mockups/36/`
(задачи), `mockups/42/` (вкладка отделов), `mockups/72/` (вкладка «Расходы»).

- **Вкладки — состояние страницы, а не маршрут.** Все три кнопки `role="tab"`, у
  выбранной `aria-selected="true"`; переключение подписей и `aria-selected` делает
  `ProjectPage`. Вкладки — один уровень навигации, поэтому пилюль, сегментов и
  счётчиков в подписях нет. Роутера по-прежнему нет: URL у вкладки не появляется.
- **Денежный раздел один — «Расходы».** Вкладки «Стоимость» больше нет (#72): раньше
  ручные записи в рублях и смены harness в долларах жили на двух вкладках, и одна и та
  же стоимость проекта печаталась на экране дважды. Теперь обе половины приходят одним
  журналом `GET /api/projects/{id}/expenses` и показываются одной ведомостью
  (`ProjectExpenses`), отличаясь признаком `kind` — `manual` или `shift`.
- **Все три панели есть в разметке всегда**, невыбранная скрыта атрибутом `hidden`: так
  `aria-controls` каждой вкладки ведёт на существующую область, а не в пустоту, и
  скрытая панель недоступна ни глазу, ни скринридеру. Своего `display` у панели нет,
  поэтому пользовательское `[hidden] { display: none }` работает без отдельного правила.
- **Все три подраздела читаются при открытии страницы**, показывается только выбранный:
  переключение вкладки запросов не повторяет и «Загрузка…» на возврате не показывает.
  Журнал расходов читается сразу, а не при первом заходе на вкладку: его итог нужен
  паспорту проекта.
- **Адреса у страницы нет.** Она живёт состоянием раздела `ProjectsPage`, поэтому F5
  возвращает к списку «Проекты» — это решение постановки, а не дефект. Роутера и
  `react-router-dom` в приложении нет.
- **Объект проекта приходит со списка**, а не читается заново: ручки
  `GET /api/projects/{id}` в приложении нет. Если проект удалили в другой вкладке,
  вкладка «Отделы» покажет в карточке `404 «Проект не найден»`, а создание задачи —
  тот же текст в окне задачи.
- **Панели «Состояние сервиса» на странице нет** — она живёт на экране «Проектов».
  Формы правки и кнопки удаления проекта на странице тоже нет: это действия списка.
- «← К проектам» закрывает страницу и показывает прежний список без повторного запроса.
- Задачи читаются с сервера (`GET /api/projects/{id}/tasks`), после создания список
  перечитывается. Оптимистичных обновлений нет.
- **Строка задачи — ровно три элемента**: номер (`#12`, приглушённый), название и
  стоимость. Описания в строке нет; оно остаётся полем задачи (колонка, поля API и
  `textarea` формы), но в списке не показывается — это решение постановки.
- **Стоимость на экране**: сервер отдаёт `"1250.00"` → `1 250,00 ₽`; `null` →
  «не указана». Фронт деньги не считает: не округляет, копейки в рубли не переводит.
  Поле в форме необязательное; пустое значение уходит как `cost: null`, а не `0` и не
  `""`. Запятая ввода переводится в точку — в контракте запроса точка.
- Правки и удаления задач в приложении нет: и ручек, и кнопок.
- Отделы выбранной вкладки — та же карточка «Список отделов» и те же диалоги; их
  владелец — страница проекта, поэтому после сохранения она перечитывает список отделов
  и ничего не правит на веру. Подробности — в разделе «Вкладка «Отделы» на странице
  проекта».

## Вкладка «Расходы» на странице проекта

Третья вкладка страницы проекта — единственное место в приложении, где видны и правятся
деньги: журнал из двух половин (смены отдела и ручные записи), итог проекта и четыре цены
за токены. Формы проекта (в списке проектов) деньги не трогают, правок и удаления записей
нет: у журнала только чтение и добавление. Контракт ручек — разделы «Журнал расходов
проекта» и «Журнал расхода смен», макет — `mockups/72/`, его решения и тексты —
`mockups/72/notes.md`.

- **Итог в паспорте.** В служебной строке проекта рядом с репозиторием и «Обновлён» стоит
  «Стоимость 119,23 $» (`project-total`). Числа нет, пока журнал не прочитан: пустая подпись
  «Стоимость —» читалась бы как ноль. Это такая же служебная строка паспорта, а не метрика:
  дашборда на странице нет. То же число стоит в шапке карточки, и совпадать они обязаны:
  оба берут один `total` одного ответа, второй формулы у фронта нет.
- **Карточка — три части**: шапка со счётчиком записей (`expenses-count`), итогом
  (`expenses-total`) и кнопкой «Добавить запись» (`expense-create`); строка цен за токены
  (`expenses-prices`) с единственной кнопкой «Изменить» (`expenses-prices-edit`); строки
  журнала (`expenses-list`).
- **Цены приходят с объектом проекта, а не с журналом**, поэтому строка цен на месте и
  пока журнал читается, и когда журнал не загрузился. Исключение одно — отказ «Проект не
  найден»: чужой прайс в этом случае не показываем. Все четыре нуля — не ошибка, а
  незаполненное место: подпись красная, «Цены не заданы», пояснение «Пока все четыре цены
  нули, сервер отклонит любую запись.» и кнопка «Задать цены». Ноль — «не тарифицируется».
  Единица названа и в строке цен («· $ за 1 млн»), и в окне цен: без неё четыре числа
  читались бы как деньги вообще, а не как цена за миллион токенов.
- **Строка журнала — одна сетка на две половины.** Смены и ручные записи стоят в одной
  ведомости и отличаются двумя знаками, а не цветом: у смены под датой есть интервал
  (`09:00 → 17:00`), в источнике — пояснение («3 сессии · окно смены») и кнопка «Сессии»
  (`expense-open`); у ручной записи ни интервала, ни кнопки, в источнике просто «ручная
  запись». Источник — слово, а не цветная пилюля: цвет в интерфейсе остаётся за
  состояниями.
- **Количества стоят двумя парами в две колонки** — вход | выход, кэш-чтение | кэш-запись —
  и выстраиваются в столбик по всей ведомости. Нулевые количества не печатаются: запись про
  один вид токенов не показывает три нуля.
- **Порядок серверный** (`spent_on DESC, sort_at DESC, id DESC`): смены стоят по времени
  закрытия, ручные записи — по времени создания. Группировки по дням нет: записи за один
  день — отдельные строки.
- **Деньги фронт не считает.** `amount` записи и `total` журнала приходят строками с
  шестью знаками и переставляются в вид `119,23 $`: два знака после запятой, а ненулевую
  мелочь показываем четырьмя (`0,0004 $`) — округлить её до `0,00 $` значило бы наврать.
  Цены приходят с шестью знаками и печатаются без хвостовых нулей (`"0.270000"` → `0,27`,
  `"3.000000"` → `3,00`). Количества — с пробелом между разрядами, сумма детализации —
  тем же видом. Всё это живёт в `src/format.ts` одним местом (`formatCost`, `formatPrice`,
  `formatTokens`); рублёвый `formatMoney` остался только строке задачи.
- **Окно «Новая запись»** (`expense-form`) — на общем `Dialog`: дата (`input type="date"`,
  по умолчанию сегодня), четыре количества (`inputMode="numeric"`, подсказка «Сумму
  посчитает сервер по ценам проекта») и кнопки «Сохранить»/«Отмена». Тело запроса —
  `{"spent_on": "ГГГГ-ММ-ДД", "tokens": {in, out, cacheRead, cacheWrite}}`: количества
  едут вложенным объектом, камелкейсом, как их называет контракт журнала. Пустое
  количество уходит нулём — «таких токенов не было», а не пропуск поля. После успеха окно
  закрывается, журнал и итог перечитываются с сервера: новую запись фронт не дорисовывает
  сам, ей нужен серверный `amount`.
- **Окно «Цены за токены»** (`prices-form`) открывается кнопкой «Изменить» в строке цен.
  `PATCH` отправляет ровно четыре цены, остальные поля проекта не трогаются; ответ — новый
  проект, и страница берёт из него и паспорт, и строку цен. Цены — доллары США за 1 млн
  токенов; окно называет единицу подсказкой «В долларах США за 1 млн токенов.». Цены
  применяются к новым записям: суммы, уже лежащие в журнале, не пересчитываются — это
  правило сервера, окно его только повторяет подсказкой. Пустое поле уходит нулём, запятая
  ввода — точкой.
- **Смена цен видна и в списке.** Ответ `PATCH` — это новый проект: страница берёт из него
  паспорт и строку цен и возвращает его в раздел (`onProjectChanged` в `ProjectsPage`).
  Иначе повторный вход в тот же проект показал бы цены, с которыми страница открывалась
  (список на возврате не перечитывается — так задумано), и «Сохранить» в окне цен записал
  бы старые числа в базу. Обновляется и `openProject`, и строка списка.
- **`noValidate` на формах — сознательное решение.** `type="number"` со `step="1"` иначе
  перехватил бы дробное количество подсказкой браузера, и до контрактного текста сервера
  дело бы не дошло. Своих проверок у окон нет: тексты отказов серверные и показываются
  дословно. Подсветка поля (`aria-invalid`) считается по введённым значениям — серверный
  текст говорит, что не так, но не в каком поле: подсветка это разметка, а не вторая
  проверка.
- **Расхождение с постановкой.** Постановка #53 (п. 10) держала четыре цены в форме
  проекта; ревизия макета вынесла их в отдельное окно с денежной вкладки — там всё, что
  про деньги, и строка цен осталась единственным местом, где цены видны без окон. Поля
  носят `data-testid` `prices-form-price-*`, окно — `prices-form` (#72 переименовал их из
  `project-form-price-*`: с формой проекта они больше не связаны).
- **Один раздел — один набор `data-testid`.** До #72 денежные экраны были двумя вкладками,
  и их id приходилось разводить префиксами `costs-`/`cost-`, чтобы выбор тестировщика не
  был неоднозначным. Вкладка осталась одна, поэтому развод не нужен: журнал и его
  состояния — семейство `expenses-*`, строка — `expense-item-*`, детализация —
  `expense-detail-*` и `expense-session-*`. Прежние `project-tab-costs`, `costs-list`,
  `costs-state`, `costs-empty`, `costs-error`, `costs-retry`, `cost-item`,
  `cost-item-date`, `cost-item-tokens`, `cost-item-amount` удалены — как и CSS
  `cost-row*`/`expense-row*`, которые заменила одна сетка `.journal-row*`.
- **Узкий экран — шапка карточки в три строки.** В общем мобильном блоке шапка карточки
  раскладывается как «счётчик слева, кнопка справа», но у этой карточки в шапке три
  элемента, и в 375 px подпись кнопки ломалась на две строки, а счётчик — на два. Поэтому
  у `.card--journal` (класс только этой карточки) счётчик и «Итого» идут отдельными строками
  слева, а «Добавить запись» занимает строку во всю ширину — как в макете на 375 px.
  Шапки карточек задач и отделов правило не задевает.
- **Подпись единицы в строке цен читается.** `.prices__unit` («· $ за 1 млн») нарисована
  цветом `--muted-rail`, как соседняя подпись: на фоне `--band` это 4,77:1 при 12 px, то
  есть проходит WCAG AA. Прежний `--muted-2` давал 2,47:1 и ловился axe как
  `color-contrast`.

нет своего id в разметке: она выбирается внутри `expense-detail`, а различает строки

## Проверки в контейнере

```bash
docker-compose -p workflow-agent exec api ruff check .
docker-compose -p workflow-agent exec api ruff format --check .
docker-compose -p workflow-agent exec api mypy .
docker-compose -p workflow-agent exec api pytest
```

Юнит-тесты живой PostgreSQL не требуют: `tests/test_health.py` подменяет проверку БД
заглушкой, остальные файлы подменяют сессию на SQLite в памяти через
`dependency_overrides` (фикстуры `session_factory` и `client` — в `tests/conftest.py`).
Миграций в тестах нет, поэтому справочники наполняет фикстура `seed_references` — тем же
каталогом, что и миграции: `DEFAULT_ROLES` из `0003_departments` и
`DEFAULT_DEPARTMENT_KINDS` из `0006_department_kinds`. Без ролей
`PATCH /api/departments/{id}` с `role_ids` падает на «нет такой роли», без видов не
создаётся ни один отдел. Таблицы создаются из метаданных моделей — вместе с частичным
уникальным индексом, поэтому уникальность имени в пределах проекта проверяется на
настоящем индексе, а не только проверкой в ручке.

`Numeric(12, 2)` в SQLite хранится числом с плавающей точкой, и SQLAlchemy об этом
предупреждает. Поэтому `tests/test_tasks.py` сверяет строку контракта (`"1250.00"`), а
не `Decimal`, и берёт представимые значения: на стенде с PostgreSQL поведение точное.
То же правило у `tests/test_projects.py` и `tests/test_expenses.py`: цены и суммы
сверяются строками (`"0.270000"`, `"0.41"`, `"0.51"`), а не `Decimal` из SQLite.

## Миграции

Схему ведёт alembic, ревизии лежат в `backend/alembic/versions/`. Применяются самим
`api` на старте (`alembic upgrade head`), вручную — так:

```bash
docker-compose -p workflow-agent exec api alembic upgrade head
docker-compose -p workflow-agent exec api alembic downgrade -1
```

Строка подключения в `alembic.ini` пустая: её подставляет `alembic/env.py` из
`DATABASE_URL`.

`0003_departments` создаёт `roles` (с сидом десяти ролей), `departments` и
`department_roles`. Её `downgrade` дропает таблицы вместе с содержимым — на живом
стенде откат означает потерю отделов и справочника ролей, поэтому откатывать можно
только пока в этих таблицах нет нужных данных.

`0004_tasks` — только добавление: создаёт `tasks` с внешним ключом на `projects.id`,
индексом `ix_tasks_project_id` и nullable-колонкой `cost Numeric(12, 2)` без значения
по умолчанию. Существующие таблицы и их данные ревизия не двигает. Её `downgrade`
дропает `tasks` вместе с содержимым: откат стирает заведённые задачи насовсем.

`0005_departments_project` — привязка отдела к проекту: добавляет nullable-колонку
`project_id integer` с внешним ключом `fk_departments_project_id` на `projects.id` и
индексом `ix_departments_project_id`, снимает глобальный уникальный индекс
`uq_departments_name_alive` и заводит частичный `uq_departments_project_name_alive` по
`(project_id, lower(name)) WHERE deleted_at IS NULL`. Ни `UPDATE`, ни `DELETE` в ревизии
нет: существующие строки остаются с `project_id IS NULL`. Её `downgrade` возвращает
глобальный уникальный индекс и снимает колонку — привязка отделов к проектам при откате
**теряется**, поэтому откатываться можно только после снятия бэкапа.

`0006_department_kinds` — справочник видов отделов и поля страницы правки. Создаёт
таблицу `department_kinds` с уникальным индексом `uq_department_kinds_code` и сидом двух
видов («Разработка», «Маркетинг»), добавляет `departments.kind_id` с внешним ключом
`fk_departments_kind_id` на `department_kinds.id` и индексом `ix_departments_kind_id`,
бэкфиллит `kind_id = (вид development)` всем существующим строкам и только потом делает
колонку `NOT NULL`; добавляет восемь текстовых полей, `max_rework` (`NOT NULL`,
умолчание `3`) и `notifications_enabled` (`NOT NULL`, умолчание `false`), а `start_time`
и `end_time` делает nullable — расписание заполняется на странице правки. Ни одна
существующая строка не удаляется и не переименовывается.

Её `downgrade` возвращает `start_time`/`end_time` в `NOT NULL` **первым** шагом: если в
базе есть отдел без расписания, откат падает на этом месте и ничего не меняет —
транзакция откатывается целиком. Дальше откат снимает новые колонки и `kind_id`, то есть
**теряет** все заполненные поля правки и привязку к виду; таблица `department_kinds`
дропается. Перед откатом нужен бэкап или согласие, что эти данные не нужны.

Сид вида — часть применённой ревизии: новый вид (третья строка справочника) — это новая
ревизия, а не правка `0006`. Правка сида в уже применённой миграции не переигрывается и
на существующей базе ничего не добавит, а расхождение «в коде три вида, в базе два»
страницу правки не сломает: `fields` незнакомого кода — `[]`.

`0007_registry_documents` — таблица ревизий документа реестра. Создаёт
`registry_documents` с колонками `id`, `revision` (уникальный индекс
`uq_registry_documents_revision`), `body` (документ v2 текстом JSON, а не JSONB: форму
задаёт `plugins/registry.mjs`), `note` о происхождении ревизии и `created_at`.
Строк `projects`/`departments` ревизия не трогает и сида не содержит: первая ревизия
появляется из `PUT` или `POST /api/registry/rebuild`, а не из миграции. Её `downgrade`
дропает таблицу вместе с содержимым — при откате **теряется** вся история документа
реестра, восстановить её можно только новым `rebuild`, и номера ревизий начнутся
заново. Данные `projects`/`departments` откат не задевает.

`0008_department_windows` — несколько окон времени работы. Добавляет
`departments.windows` (`JSONB` на PostgreSQL) nullable, переносит старую пару в одно
окно (`left(start_time::text, 5)` → `"ЧЧ:ММ"`, без секунд), строкам без расписания
оставляет `[]`, делает колонку `NOT NULL` и только потом физически удаляет
`start_time`/`end_time`. Число строк `departments` не меняется, таблиц и индексов
ревизия не трогает. Перенос и удаление колонок — принятое человеком **необратимое**
решение: вторая копия расписания разошлась бы с первой.

Её `downgrade` возвращает пару из **первого** окна и удаляет `windows`: все окна, кроме
первого, при откате **теряются**. Строки с пустым набором окон возвращаются без
расписания (`NULL`/`NULL`), а не падают: после `0006_department_kinds` обе колонки
nullable, и выдуманное время хуже честного «расписания нет».

`0011_department_enabled` — флаг работы отдела: добавляет `departments.enabled`
(`NOT NULL`, умолчание `true`) одной колонкой. Данные ревизия не переписывает: все
существующие отделы получают `true` умолчанием и остаются обслуживаемыми, как и до неё.
Умолчание выбрано осознанно — выключенный отдел перестаёт брать задачи, и `false` из
ниоткуда остановил бы работу после выкатки; плата в том, что проект, выключенный раньше
локальным ключом файла, придёт включённым, и человек выключит его в вебе ещё раз.

Её `downgrade` снимает колонку, то есть **теряет только флаг**: настройки, роли и
расписания отделов остаются, а повторный `upgrade` вернёт всем отделам `true` —
выключенные после отката придётся выключить заново.

`0013_expenses` — деньги проекта и журнал расходов. Добавляет `projects` пять колонок:
`price_input`, `price_output`, `price_cache_read`, `price_cache_write` (`Numeric(18, 6)`,
`NOT NULL`, умолчание `0`) и `total_cost` (`Numeric(20, 2)`, `NOT NULL`, умолчание `0`).
Существующие проекты получают нули умолчанием: незаполненные цены — допустимое
состояние, `UPDATE` по строкам ревизия не делает. Затем создаёт `project_expenses`
(`id`, `project_id` с внешним ключом на `projects.id`, `spent_on DATE`, четыре количества
`BIGINT`, `amount Numeric(20, 2)`, `created_at TIMESTAMPTZ` с умолчанием `now()`) и индекс
`ix_project_expenses_project_id`. Точность денег — с запасом под собственные ограничители
контракта: цена до десяти знаков до разделителя и количество до `10^12` дают сумму до
`4·10^16`, поэтому `Numeric(14, 2)` не подходит — PostgreSQL ответил бы `numeric field
overflow` на вводе, который валидаторы считают допустимым. Ревизия стоит после
`0012_usage` из #57 (`down_revision = "0012_usage"`): голов в `alembic heads` ровно одна —
`0013_expenses`.

Её `downgrade` снимает индекс, дропает `project_expenses` и удаляет пять колонок
`projects`: **теряются** все записи журнала, итог и цены проектов — восстановить их можно
только вводом заново (суммы записей не пересчитать: количеств в старой схеме не было).
Перед откатом нужен бэкап или согласие, что эти данные не нужны.
