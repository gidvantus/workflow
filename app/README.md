# APP — приложение «Проекты» и «Отделы»

Стенд из трёх сервисов, который поднимается одной командой: два раздела приложения —
«Проекты» (список, создание, правка и мягкое удаление) и «Отделы» (список, создание,
правка и мягкое удаление; время работы парой «с/по» и набор ролей из справочника), —
и их общее API.

| Сервис | Что это | Порт на хосте |
|---|---|---|
| `db` | PostgreSQL 16 | не публикуется, доступен только внутри compose-сети |
| `api` | FastAPI на Python 3.12 (uvicorn) | `API_PORT`, по умолчанию `8096` |
| `web` | React на Vite под nginx, проксирует `/api/` в `api` | `FRONTEND_PORT`, по умолчанию `8095` |

Поднимать можно и по частям — например, только базу с API:

```bash
docker-compose -p workflow-agent up -d --build db api
```

## Как поднять

```bash
cd APP
docker-compose up -d --build
```

Именно `docker-compose`, а не `docker compose`: на этой машине плагин не работает
(`docker: unknown command: docker compose`), работает отдельный `docker-compose.exe`.

Первая сборка тянет pip и npm — это несколько минут. Дальше слои переиспользуются.

Проверки:

```bash
docker-compose -p workflow-agent ps                     # db healthy, api и web Up
curl.exe -s http://localhost:8096/api/health            # напрямую в api
curl.exe -s http://localhost:8095/api/health            # через nginx
curl.exe -s -o NUL -w "%{http_code}" http://localhost:8095/   # страница отдаётся, 200
docker-compose -p workflow-agent exec api alembic current   # 0003_departments (head)
docker-compose -p workflow-agent exec web nginx -t          # конфиг nginx валиден
```

Остановить стенд, сохранив данные базы:

```bash
docker-compose -p workflow-agent stop
```

Снести вместе с томом базы:

```bash
docker-compose -p workflow-agent down -v
```

## Настройки и второй стенд

Значения по умолчанию лежат в `.env.example`; `.env` — личная копия, он в git не едет:

```bash
copy .env.example .env      # Windows
cp .env.example .env        # bash
```

Имя compose-проекта и порты у каждого стенда **свои**. Второй стенд того же
compose-файла (например клон человека) с общими значениями пересоздаст чужие
контейнеры и займёт чужие порты — ему в `.env` нужны, например,
`COMPOSE_PROJECT_NAME=workflow-local`, `FRONTEND_PORT=8091`, `API_PORT=8092`.

Секретов в репозитории нет: в `.env.example` только локальные заглушки.

## Маршрут по каталогам

Каталог `app/` не входит ни в одну половину работы из реестра проекта (`areas`:
backend = `tools/`, frontend = `agent-presets/`, `docs/`, `profiles/`). Постановки #32
и #34 называли файлы обеих половин (`.py` и `.tsx`/`.css`), поэтому маршрут был
`area:fullstack` с двумя ступенями: сначала бэкенд, затем фронтенд.

| Ступень | Где лежит | Что это |
|---|---|---|
| бэкенд | `app/backend/` | `models/`, `schemas/`, `api/`, миграции, тесты |
| фронтенд | `app/frontend/src/` | `api/`, `components/`, `App.tsx`, `index.css` |
| шов | `app/README.md` | описание ручек, экранов и soft delete |

Остальное в репозитории (`tools/`, `plugins/`, `profiles/`, `agent-presets/`, `docs/`,
`sync.mjs`) — не часть приложения `app/` и в задачах #32 и #34 не менялось.

## API

Десять ручек: `GET /api/health`, четыре ручки проектов, четыре ручки отделов и
справочник ролей `GET /api/roles`.

### Живость сервиса

`GET /api/health` — единственная ручка каркаса.

```json
200 {"status":"ok","db":"ok","version":"0.1.0"}
503 {"status":"degraded","db":"fail","version":"0.1.0","message":"База данных недоступна"}
```

`503` — это контракт, а не сбой: база проверяется запросом `SELECT 1` с таймаутом
подключения 2 с, недоступность базы не роняет процесс и не даёт 500. Текст поля
`message` показывается пользователю дословно.

### Проекты

| Метод и путь | Тело запроса | Успех |
|---|---|---|
| `GET /api/projects` | нет | `200 [{id, name, description, repo_url, created_at, updated_at}]` — только живые, порядок по `id` |
| `POST /api/projects` | `{name, repo_url, description?}` | `201` тот же объект |
| `PATCH /api/projects/{id}` | любое непустое подмножество `{name, description, repo_url}` | `200` тот же объект |
| `DELETE /api/projects/{id}` | нет | `204` без тела (мягкое удаление) |

Отказы — часть контракта: экран показывает их текст дословно и своих формулировок не
добавляет.

| Код | `detail` | Когда |
|---|---|---|
| `409` | `Проект с таким названием уже есть` | имя занято живым проектом (сравнение без учёта регистра) |
| `404` | `Проект не найден` | проекта нет или он уже удалён — в том числе для `PATCH` |
| `422` | `Укажите название проекта` | имя пустое после `strip()` |
| `422` | `Название длиннее 200 символов` | имя длиннее 200 символов |
| `422` | `Укажите адрес репозитория` | адрес пустой после `strip()` |
| `422` | `Адрес репозитория должен быть ссылкой или вида owner/repo` | адрес не подходит под формат или длиннее 500 символов |
| `422` | `Описание длиннее 2000 символов` | описание длиннее 2000 символов |
| `422` | `Нет полей для изменения` | `PATCH` с пустым телом |

Остальные отказы (`5xx`, `422` от невалидного JSON) контрактом не считаются.

**Soft delete.** `DELETE` не удаляет строку: он ставит `deleted_at = now()`, и строка
остаётся в таблице `projects` навсегда. В списке её больше нет, повторный `DELETE` и
`PATCH` по ней отвечают `404`, восстановить проект через интерфейс нельзя. Имя
удалённого проекта свободно — его можно занять заново. Физического удаления строк в
приложении нет, и очистки таблицы в задаче тоже нет: она растёт, политики хранения
пока не существует.

### Роли

`GET /api/roles` → `200 [{id, code, title}]`, порядок по `id`.

Справочник ролей живёт в таблице `roles`: прочитать пресеты надстройки
(`plugins/agent-presets/<id>/preset.yml`) в рантайме нельзя — каталога `plugins/` в
образе `api` нет. Наполняет таблицу сид миграции `0003_departments` из константы
`DEFAULT_ROLES` (`backend/app/models/role.py`) — десять ролей в порядке таблицы
постановки. Управляющих ручек у ролей нет: справочник меняется только миграцией.

Отдел ссылается на роль по `id`, поэтому новая роль — это новая строка и новая ревизия,
а не правка существующей: добавление роли не двигает уже сохранённые отделы. Отдельная
ревизия нужна и потому, что применённая ревизия не переигрывается: правка `DEFAULT_ROLES`
на существующей базе ничего не добавит.

### Отделы

| Метод и путь | Тело запроса | Успех |
|---|---|---|
| `GET /api/departments` | нет | `200 [{id, name, start_time, end_time, roles, created_at, updated_at}]` — только живые, порядок по `id`, роли в порядке `id` |
| `POST /api/departments` | `{name, start_time, end_time, role_ids}` — все четыре обязательны, `role_ids` непустой | `201` тот же объект |
| `PATCH /api/departments/{id}` | любое непустое подмножество тех же полей | `200` тот же объект; `role_ids` заменяет набор целиком |
| `DELETE /api/departments/{id}` | нет | `204` без тела (мягкое удаление) |

Время в ответе — строка `"ЧЧ:ММ"` (`"13:00"`, без секунд): поле `<input type="time">`
на фронте получает значение из этого поля без собственного форматирования, и секунды
сделали бы его невалидным. На вход время принимается строго как `ЧЧ:ММ`.

`end_time` меньше `start_time` — это переход через полночь (`13:00` → `04:00`), штатный
случай: запрещено только совпадение начала и конца. Второго окна внутри суток нет.

Отказы — та же часть контракта, что и у проектов: текст показывается пользователю
дословно.

| Код | `detail` | Когда |
|---|---|---|
| `409` | `Отдел с таким названием уже есть` | имя занято живым отделом (сравнение без учёта регистра) |
| `404` | `Отдел не найден` | отдела нет или он уже удалён — в том числе для `PATCH` |
| `422` | `Укажите название отдела` | имя пустое после `strip()` |
| `422` | `Название отдела длиннее 200 символов` | имя длиннее 200 символов |
| `422` | `Время работы указывается как ЧЧ:ММ, например 09:00` | время не `ЧЧ:ММ`, `25:00`, `12:60` |
| `422` | `Начало и конец рабочего времени совпадают` | `start_time == end_time` |
| `422` | `Выберите хотя бы одну роль` | `role_ids` пуст или не прислан |
| `422` | `Выбрана роль, которой нет в списке ролей` | в `role_ids` есть id, которого нет в `roles` |
| `422` | `Нет полей для изменения` | `PATCH` с пустым телом |

Повтор роли в `role_ids` — не ошибка: набор схлопывается, в ответе роль стоит один раз.
Правка одних только ролей тоже двигает `updated_at`: роли лежат в таблице связи, и без
явного обновления колонка «Обновлён» показывала бы дату до правки.

**Soft delete отдела.** `DELETE` ставит `deleted_at`, из списка отдел исчезает, строка
в `departments` остаётся. Строки связи в `department_roles` при этом **не удаляются**:
физического удаления в приложении нет ни в одном месте, поэтому набор ролей удалённого
отдела остаётся в базе, а таблица связи растёт. Восстановления через интерфейс нет;
имя удалённого отдела свободно — его можно занять заново. Одна роль может стоять в
двух отделах: связь многие-ко-многим, а не владение.

Полная схема — в `/openapi.json` и `/docs` того же сервиса.

## Оболочка приложения

Слева — бренд и меню с двумя разделами: «Проекты» (`nav-projects`) и «Отделы»
(`nav-departments`). У активного пункта `aria-current="page"`, у обоих — бейдж
с количеством записей раздела: число берётся из загруженного списка, поэтому бейджа нет,
пока список не прочитан или не прочитался. Оба раздела смонтированы сразу и читают свои
списки при старте — иначе бейдж второго раздела появлялся бы только после переключения;
невыбранный раздел скрыт атрибутом `hidden` и недоступен ни глазу, ни скринридеру.

Выбранный раздел — состояние в `App`. Роутера и отдельных URL нет: клик по пункту меню
переключает раздел, а F5 всегда открывает «Проекты». Под содержимым раздела — подвал.

## Экран «Проекты»

Шапка с крошками, заголовок «Проекты» с кнопкой «Добавить проект», карточка списка,
полоса состояния сервиса под ней и подвал. Макет — `mockups/32/` в ветке задачи #32.

- Список читается с сервера: `GET /api/projects` относительным путём, запрос
  проксирует nginx на том же origin, поэтому CORS не нужен. Адрес API в коде не
  зашит — его задаёт окружение стенда.
- Каждая строка: название, описание (пустое описание — пустая строка, без заглушки),
  адрес репозитория моноширинным, дата обновления и действия под кнопкой «⋯» —
  «Изменить» и «Удалить».
- Одно окно на создание и правку: «Название», «Описание», «Адрес репозитория»,
  «Сохранить» и «Отмена»; `role="dialog"`, `aria-modal`, Esc и подложка закрывают
  окно, Tab удерживается внутри, фокус возвращается на кнопку, которая окно открыла.
- Удаление — подтверждение с названием проекта; во время запроса кнопки неактивны.
- После создания, правки и удаления список перечитывается с сервера. Оптимистичных
  обновлений нет: на экране только то, что вернул сервер.

| Что видно | Когда |
|---|---|
| `Загрузка…` | список читается |
| `Пока нет проектов` | сервер вернул пустой массив |
| текст отказа и кнопка `Повторить` | список не загрузился |
| `Сохраняю…`, кнопки неактивны | запрос формы в полёте, окно открыто |
| текст отказа дословно из `detail` | `409`/`422` при сохранении, окно открыто |
| `Удаляю…`, кнопки неактивны | запрос удаления в полёте |
| текст отказа дословно из `detail` | ошибка удаления, в окне подтверждения |
| `Сервер не отвечает` | api недоступен: сеть, остановленный контейнер, прокси |

Панель состояния сервиса переехала под список, но её контракт прежний: кнопка
«Проверить» делает `GET /api/health` относительным путём, строка состояния показывает
ответ, ошибка — дословный `message`.

| Что видно | Когда |
|---|---|
| строка состояния «не проверено» | до первой проверки |
| кнопка неактивна, текст «Проверяю…» | запрос в полёте |
| строка состояния `API: ok · БД: ok` | ответ `200`, блок ошибки не отрисован |
| блок ошибки с текстом `message` дословно | ответ `503` (база недоступна) |
| блок ошибки «Сервер не отвечает» | api недоступен: контейнер остановлен, сеть, прокси |

Элементы для тестов помечены `data-testid`: `app-status`, `app-check`, `app-error`,
`projects-list`, `projects-state`, `projects-empty`, `projects-retry`, `project-error`,
`project-create`, `project-item`, `project-item-name`, `project-item-description`,
`project-edit`, `project-delete`, `project-form`, `project-form-name`,
`project-form-description`, `project-form-repo`, `project-form-submit`,
`project-form-cancel`, `project-form-error`, `project-delete-confirm`,
`project-delete-confirm-submit`, `project-delete-confirm-cancel`,
`project-delete-confirm-error`. Своих тестов и линтеров у фронтенда в этой задаче нет;
типы проверяет `tsc --noEmit` внутри `npm run build`, то есть при сборке образа `web`.

## Экран «Отделы»

Шапка с крошками, заголовок «Отделы» с подписью «Отделы, их время работы и набор ролей»
и кнопкой «Добавить отдел», карточка «Список отделов». Макет — `mockups/34/` в ветке
задачи #34.

- Список читается с сервера: `GET /api/departments` относительным путём через nginx.
- В шапке карточки — количество с правильным окончанием: «1 отдел», «2 отдела»,
  «5 отделов».
- Строка: название, время работы как `13:00–04:00` коротким тире, под ним длительность
  смены («9 ч», «15 ч · через полночь»), роли через запятую по названиям из
  справочника, дата обновления и действия под «⋯» — «Изменить» и «Удалить».
- Время — часть контракта: сервер отдаёт `"13:00"`, фронт показывает его как есть.
  Переход через полночь (`end_time` меньше `start_time`) — штатный случай, длительность
  считается по кругу суток, и ни один экран его не «исправляет».
- Роли в форме — чекбоксы из справочника `GET /api/roles`: кодов и названий фронт не
  зашивает, `code` нужен только для `data-testid` (`department-form-role-<code>`).
  В `.dialog--wide` они идут в две колонки, на ≤600 px — в одну.
- Окно формы одно на создание и правку (`Новый отдел` / `Изменить отдел`): «Название»,
  время «с» и «по» двумя `<input type="time">`, роли, «Сохранить» и «Отмена». Пока роли
  грузятся, вместо чекбоксов «Загрузка ролей…», и «Сохранить» неактивна — отдел без
  ролей сервер не примет.
- Удаление — общее окно подтверждения (`ConfirmDialog`) с текстом «Отдел «{название}»
  исчезнет из списка. Восстановить его через интерфейс нельзя.».
- После создания, правки и удаления список перечитывается с сервера. Оптимистичных
  обновлений нет.

| Что видно | Когда |
|---|---|
| `Загрузка…` | список читается |
| `Пока нет отделов` и подсказка про «Добавить отдел» | сервер вернул пустой массив |
| текст отказа и кнопка `Повторить` | список не загрузился |
| `Загрузка ролей…`, `Сохранить` неактивна | окно формы открыто, справочник ролей в полёте |
| текст отказа справочника и `Повторить`, чекбоксов нет | `GET /api/roles` не ответил |
| `Сохраняю…`, кнопки неактивны, окно не закрывается | запрос формы в полёте |
| текст отказа дословно из `detail` | `409`/`422` при сохранении, окно открыто |
| `Удаляю…`, кнопки неактивны | запрос удаления в полёте |
| текст отказа дословно из `detail` | ошибка удаления, в окне подтверждения |
| `Сервер не отвечает` | api недоступен: сеть, остановленный контейнер, прокси |

`data-testid` раздела: `departments-list`, `departments-state`, `departments-empty`,
`departments-retry`, `department-error`, `department-create`, `department-item`,
`department-item-name`, `department-item-time`, `department-item-roles`,
`department-edit`, `department-delete`, `department-form`, `department-form-name`,

## Проверки в контейнере

```bash
docker-compose -p workflow-agent exec api ruff check .
docker-compose -p workflow-agent exec api ruff format --check .
docker-compose -p workflow-agent exec api mypy .
docker-compose -p workflow-agent exec api pytest
```

Юнит-тесты живой PostgreSQL не требуют: `tests/test_health.py` подменяет проверку БД
заглушкой, `tests/test_projects.py` и `tests/test_departments.py` подменяют сессию на
SQLite в памяти через `dependency_overrides`. Миграций в тестах нет, поэтому сид ролей
делает фикстура — тем же каталогом `DEFAULT_ROLES`, что и `0003_departments`: без него
таблица `roles` пуста и любой `POST /api/departments` падает на «нет такой роли».

## Миграции

Схему ведёт alembic, ревизии лежат в `backend/alembic/versions/`. Применяются самим
`api` на старте (`alembic upgrade head`), вручную — так:

```bash
docker-compose -p workflow-agent exec api alembic upgrade head
docker-compose -p workflow-agent exec api alembic downgrade -1
```

Строка подключения в `alembic.ini` пустая: её подставляет `alembic/env.py` из
`DATABASE_URL`.

`0003_departments` создаёт `roles` (с сидом десяти ролей), `departments` и
`department_roles`. Её `downgrade` дропает таблицы вместе с содержимым — на живом
стенде откат означает потерю отделов и справочника ролей, поэтому откатывать можно
только пока в этих таблицах нет нужных данных.
