# Как устроен отдел разработки

Документ описывает не DSH, а надстройку поверх него: кто кого запускает, по каким
правилам выдаются задачи и что происходит, когда что-то ломается.

## Общая картина

```
                    ┌──────────────────────────────────────────┐
   расписание смен  │  dev-department.mjs (хост-плагин)        │
   ~/.dsh/          │  тик раз в минуту:                       │
   dev-department.json │  окно смены? → работа по проектам?    │
   projects.json    └───────────────────┬──────────────────────┘
                                        │ open_role_session(preset, задача)
                                        ▼
                    ┌──────────────────────────────────────────┐
                    │  role-sessions.mjs — сессия роли          │
                    │  рабочая область = клон отдела проекта    │
                    └───────────────────┬──────────────────────┘
                                        │ персона + скиллы пресета
                                        ▼
        analyst → design (макет) → dev-backend / dev-frontend / dev-fullstack → code-review → tester → devops-delivery
                                        │
                                        ▼
                    GitHub: метки, комментарии, PR, вердикт со скриншотами
                                        │
                    Telegram: сводка смены по каждому проекту
```

Одно действие на проект за тик. Завершившаяся сессия попадает в сводку на одном
тике, следующая задача выдаётся на следующем — так смена читается в журнале
как последовательность шагов, а не как пачка одновременных запусков.

## Проекты

Отдел многопроектный: и диспетчер, и пресеты не знают ни одного конкретного
адреса. Всё проектное лежит в реестре `~/.dsh/projects.json`:

| Поле | Зачем |
|---|---|
| `repo`, `base` | репозиторий GitHub и базовая ветка |
| `workspace` | клон отдела, в нём работает роль |
| `humanClone` | клон человека — неприкосновенен |
| `composeProject` | имя своего compose-стенда |
| `frontendPort`, `apiPort` | порты стенда |
| `artifacts` | каталог артефактов вне рабочей копии |
| `department` | включённость, окна смен, `maxRework` |
| `labels` | переопределение имён меток конвейера, если проект их переименовал |

Инструмент `project_info` определяет проект по рабочей области сессии и отдаёт
эти значения агенту. Поэтому в персонах и скиллах вместо адресов стоят
заполнители `<repo>`, `<base>`, `<workspace>`, `<humanClone>`, `<composeProject>`,
`<frontendPort>`, `<apiPort>`, `<artifacts>`, `<id>` — один и тот же пресет
работает в любом проекте реестра.

## Конвейер меток

Что и при каком событии ставит каждая роль — в
[DEPARTMENT-PROCESS.md](DEPARTMENT-PROCESS.md). Здесь — как это устроено в коде.

```
постановка (analyst) ──needs-mockup──> design: макет ──> mockups-ready
                                                            │  человек: ready-for-dev
                                                            ▼
     area:backend   ──> dev-backend
     area:frontend  ──> dev-frontend
     area:fullstack ──> dev-backend ──review──> dev-frontend
     маршрут не определён ──> dev-fullstack
                                                            │
        in-progress ──PR──> for-code-review ──> ready-for-test ──> tester ──> tested
                                                            │                    │
                                            ready-for-dev ◄─┘                    ▼
                                          (доработка)                    devops-delivery ──> merged
```

- `ready-for-dev` ставит человек. Аналитик его не ставит: решение «в работу» —
  человеческое. Если постановке нужен макет, эта метка означает ещё и приёмку
  макета: до `mockups-ready` тикет в разработку не уходит.
- **Ступень макета.** Тикет с `needs-mockup` (ставит аналитик инструментом
  `gh_issue_mockup` или человек вручную) раньше клика человека проходит через
  `design`: статичный прототип в `mockups/<номер>/`, скриншоты комментарием,
  финальная метка `mockups-ready`. PR дизайнер не открывает и `for-code-review`
  не ставит — реализации на этой ступени нет. Пока `mockups-ready` нет,
  `queuedOf` не пускает тикет в разработку, даже если `ready-for-dev` уже стоит.
- **Маршрут.** Его ставит диспетчер по тексту постановки: `area:backend` →
  `dev-backend`, `area:frontend` → `dev-frontend`, `area:fullstack` →
  `dev-backend` и затем, после ревью половины, `dev-frontend`; без уверенности
  маршрут не ставится и тикет берёт `dev-fullstack`.
- **Исполнитель** — `dev-backend`, `dev-frontend` или `dev-fullstack`; метка
  маршрута живёт на тикете всю жизнь задачи, поэтому возврат в доработку уходит
  той же роли. Дизайнер реализацию не делает и маршрутом `area:*` не выбирается.
- Дизайн-пресет нужен только на ступени макета: свой `github.mjs` с
  вложениями-скриншотами, ветка `feature/<номер>-<слаг>` (в ней позже работает
  разработчик), скилл `mockup-delivery` — формат макета, типографика, тексты,
  планка качества.
- Исполнитель забирает задачу, ставит `in-progress`, открывает PR в базовую ветку
  и передаёт `for-code-review`. **Мерж PR делает человек.**
- Код-ревьюер читает PR и код вокруг, замечания пишет **в PR** (`gh_pr_comment`),
  по одному комментарию на замечание. Решение — меткой: принял → `ready-for-test`,
  сняв `for-code-review`; нужны правки → `ready-for-dev`, сняв `for-code-review`,
  и короткий комментарий в issue.
- Доработка после ревью идёт в **той же** ветке и **том же** диалоге исполнителя:
  новый PR под замечания не открывается, а ответ на каждое замечание пишется в PR.
- Тестировщик выносит вердикт: `tested` или `test-failed`. С вердиктом в issue
  уходит комментарий и 2–3 картинки интерфейса.
- `test-failed` возвращает задачу исполнителю в том же диалоге; лимит доработок —
  `maxRework`. Возврат из ревью считается такой же доработкой: счётчик один, иначе
  пара исполнитель↔code-review качалась бы бесконечно, потому что каждая сессия
  двигает метку и обнуляет счётчик попыток.
- При исчерпании попыток или доработок тикет снимается с конвейера: комментарий
  «нужен человек», снятие меток стадий **включая `ready-for-dev`**. Снятый тикет
  не должен сам возвращаться в очередь — иначе «снят → возвращён → снят» крутится
  каждый тик и засыпает issue одинаковыми комментариями. Вернуть задачу может
  только человек, поставив `ready-for-dev` заново: тогда сбрасываются и попытки,
  и доработки, и диалоги ролей.
- Перед слиянием DevOps-инженер удаляет `mockups/<номер>` из ветки отдельным
  коммитом: артефакты постановки остаются в истории git, но не копятся в базовой
  ветке.

Метки должны **существовать в репозитории**: поставить метку, которой там нет,
GitHub не даст (422), и шаг конвейера упадёт. Набор меток один для всех ролей, его
отдаёт `project_info.labels`, а проверяют и создают
`tools/pipeline-labels-probe.mjs` и `tools/pipeline-labels-create.mjs`.

Приоритет выбора задачи: сначала ступень макета (`needs-mockup` без
`mockups-ready`), затем активные (`for-code-review` → `ready-for-test` →
`test-failed` → `in-progress`), потом очередь — самый старый тикет по `created` по
возрастанию. Очередь — это тикеты с `ready-for-dev` и готовым (или ненужным)
макетом. Ревью стоит выше теста: оно раньше в конвейере, и тикет, помеченный
обоими (ревьюер принял, но старую метку не снял), должен доехать до ревью, а не
проскочить его.
Одновременно в работе одна задача на проект.

## Диалоги

Каждая пара «роль + тикет» ведёт один диалог, он хранится в
`~/.dsh/dev-department-dialogs.json` и переживает перезапуск процесса. Доработка
и повторный тест приходят в тот же диалог, поэтому агент помнит, что уже сделал.
`requestId` каждой выдачи уникален (время + случайный хвост) — счётчик внутри
процесса после перезапуска повторялся и путал сессии.

## Устойчивость

| Что | Условие | Что делает диспетчер |
|---|---|---|
| Долгий старт | сессия не успела начать работу за `START_GRACE_MS` (2 мин) | не считает попытку, ждёт дальше |
| Зависший ход | сессия `running`, но записи нет дольше `stuckAfterMinutes` (30) | `sessionController.cancel` и запись в журнал |
| Сбой модели | последний ход завершился ошибкой, и в нём **не было** ни ответа модели, ни вызова инструмента | попытка не засчитывается, проект уходит в паузу 10 → 20 → 40 мин |
| Сбой с работой | ход завершился ошибкой, но работа в нём была | обычная попытка: ошибка может быть следствием самой работы |
| Исчерпаны попытки | `maxAttempts` (4) | комментарий в issue, снятие меток, `ready-for-dev` остаётся |

Признак «сбой модели» читается из хвоста стенограммы сессии
(`sessionController.follow`, только последние сообщения), а не угадывается по
времени: у провайдера бывают обрывы потока и отказы оплаты, и задача при них не
виновата. Пауза сбрасывается до начальной после нормально завершённой сессии.

## Изоляция

Роль работает **не** в каталоге человека:

- у отдела свой клон проекта (`workspace`), человек — в `humanClone`;
- свой стенд: `docker compose -p <composeProject>`, своя база в отдельном томе,
  свои порты;
- тестировщик разворачивает ветку в отдельный `git worktree`, ветку в нём не
  переключает;
- рабочая копия возвращается на базовую ветку после каждой задачи — следующая
  ветка растёт от свежего `origin/<base>` (в скилле разработчика: `git fetch`,
  `git checkout <base>`, `git pull --ff-only`, затем `git checkout -b`).

Изоляция — структурная, а не граница безопасности: ролевые сессии запускаются с
`danger-full-access`, потому что Docker, pip и npm пишут кэши за пределами
рабочей области.

## Файлы и роли

| Файл | Ответственность |
|---|---|
| `profiles/desktop/plugins/dev-department.mjs` | расписание смен, выбор задачи, запуск ролей, диалоги, сторож, сводка в Telegram |
| `profiles/desktop/plugins/role-sessions.mjs` | инструменты `open_role_session`, `list_agent_presets`; создаёт сессию роли в нужной рабочей области |
| `profiles/desktop/plugins/role-permissions.mjs` | выдаёт ролевым сессиям `danger-full-access` |
| `profiles/desktop/plugins/tg-bridge.mjs` | мост в Telegram |
| `profiles/desktop/plugins/voice-input/` | голосовой ввод в GUI: кнопка в композере и ручка `POST /dsh-voice/transcribe` |
| `agent-presets/<id>/agent.cordis.yml` | композиция роли: персона, скиллы, инструменты |
| `agent-presets/<id>/preset.yml` | имя и описание роли в списке пресетов |
| `agent-presets/<id>/skills/*/SKILL.md` | рабочий контракт роли: порядок действий, команды, границы |
| `agent-presets/<id>/github.mjs` | инструменты `gh_*` роли и `project_info` |

### Если добавляешь новую роль

1. Скопируй ближайший по смыслу пресет в `agent-presets/<id>/` и перепиши
   `preset.yml`, персону и скилл.
2. Добавь `<id>` в `ROLES` в `role-permissions.mjs` — иначе сессия роли будет
   упираться в запросы подтверждения.
3. Добавь `<id>` в список `PRESETS` в `sync.mjs`, иначе каталог не будет
   синхронизироваться.
3. Если роль выводится из процесса, сними её каталог, убери id из `ROLES` и
   `PRESETS`, и проверь, что на неё не ссылается `dev-department.mjs`.
4. Если роль должна участвовать в конвейере — научи диспетчер её запускать.
5. Перезапусти DSH: композиции пресетов перечитываются только при старте, новые
   каталоги пресетов — на ходу.

## Журнал и диагностика

- `~/.dsh/dev-department.log` — durable-журнал смены: кто запущен, что решено,
  почему задача снята. Читать как UTF-8.
- `tools/session-errors.mjs` — по стенограммам находит ходы, завершившиеся
  ошибкой, и группирует по причине (обрыв SSE, отказ оплаты).
- `tools/session-tail.mjs` — последние события сессии роли: чем занята сейчас.
- `tools/tests/*` — регрессионные наборы на боевых модулях.
