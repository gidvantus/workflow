# Процесс отдела разработки

Состояние на 20.10.2026. Описывает поведение установленного диспетчера
(`~/.dsh/profiles/desktop/plugins/dev-department.mjs`) и промтов, которые он выдаёт ролям.

---

## 1. Основное правило

**Единственный источник правды — метки GitHub.** Диспетчер ничего не помнит о ходе задачи между
перезапусками: он каждый тик (60 с) читает открытые issue проекта и по меткам понимает, что делать.
Метка — это не комментарий к задаче, а её состояние в конвейере.

Следствия:

- агент не может «продолжить, не поставив метку»: прогресса не будет видно;
- снятая метка = шаг не случился, диспетчер выдаст задачу заново;
- ручная правка меток человеком — законный способ вмешаться.

Роли не ставят метки «по своему усмотрению». У каждой роли есть ровно один финальный шаг, который
она обязана сделать. Всё остальное — диспетчер и человек.

---

## 2. Роли, их каталоги и кто за что отвечает

### 2.1 Роли и их каталоги

Каждая роль — это отдельный пресет: каталог `~/.dsh/.agent-presets/<id>/` с промтом
(`agent.cordis.yml`), описанием для списка (`preset.yml`), скиллами (`skills/`) и, у ролей
конвейера, инструментами GitHub (`github.mjs`). **Id пресета = имя каталога**, и именно этим id
роль названа в схемах и таблицах ниже.

| Роль | Каталог в `.agent-presets` | Кто запускает | В конвейере | Работа роли |
|---|---|---|---|---|
| Аналитик | `analyst` | человек: Telegram `/new analyst`, инструмент `open_role_session` | до конвейера | разбор задачи, постановка в issue, метка `needs-mockup` |
| Разработчик полного стека | `dev-fullstack` | диспетчер | да | оба дерева целиком; тикеты без `area:*` и вне разделения ролей |
| Бэкенд-разработчик | `dev-backend` | диспетчер | да | бэкенд-дерево, контракт, `area:backend` и первая половина `area:fullstack` |
| Фронтенд-разработчик | `dev-frontend` | диспетчер | да | фронтенд-дерево по макету, `area:frontend` и вторая половина `area:fullstack` |
| Дизайнер | `design` | диспетчер | да | только ступень макета: макет к постановке (`needs-mockup`), реализации не делает |
| Код-ревьюер | `code-review` | диспетчер | да | ревью PR, вердикт меткой |
| Тестировщик | `tester` | диспетчер | да | приёмочные слои, вердикт GREEN/RED |
| DevOps-инженер | `devops-delivery` | диспетчер | да | слияние PR, удаление макетов, доставка |
| Jev (System One) | `jev` | только человек: Telegram `/new jev`, `open_role_session` | нет | консультант по моделям TypeSafe AI |
| Безопасник | `security-review` | только человек: Telegram `/new security-review`, `open_role_session` | нет | ревью на уязвимости |

Права ролей задаются вторым местом — `~/.dsh/profiles/desktop/plugins/role-permissions.mjs`,
списком `ROLES = ['dev', 'dev-backend', 'dev-frontend', 'design', 'tester', 'analyst',
'code-review', 'devops-delivery']`. Эти восемь получают `danger-full-access`, чтобы работа не
упиралась в подтверждения. `jev` и `security-review` в список не входят — их сессии работают в
песочнице по умолчанию.

**Привести в порядок.** Диспетчер ссылается на роли по id, поэтому удалять можно только те,
что помечены «только человек»: сейчас это `jev` и `security-review` — в конвейере их нет.
Порядок: снимок каталога в `~/.dsh/bak/role-backups/<дата>/`, удаление каталога, и если роль
была в `ROLES` — убрать id оттуда. Роли `dev-fullstack`, `dev-backend`, `dev-frontend`, `design`,
`code-review`, `tester`, `devops-delivery` убирать нельзя: диспетчер на них ссылается по имени,
и конвейер начнёт падать на выдаче задачи.

### 2.2 Кто какой шаг делает

| Действие | Кто | Когда |
|---|---|---|
| Создать постановку | **аналитик** (`analyst`) | разобрал задачу и выбрал вариант |
| Поставить `needs-mockup` | **аналитик** (`analyst`) через `gh_issue_mockup` **или человек** вручную | задача меняет визуальный слой |
| Поставить `mockups-ready` | **дизайнер** (`design`) | макет готов: файлы в ветке, скриншоты в issue |
| Поставить `ready-for-dev` | **человек** | постановка (и макет, если он был нужен) устраивают |
| Поставить `area:*` | **диспетчер** (входная ступень) | тикет в очереди без маршрута |
| Поставить `in-progress` | **диспетчер** | в момент выдачи задачи исполнителю |
| Поставить `for-code-review` | **исполнитель**: `dev-fullstack`, `dev-backend`, `dev-frontend` | закончил свою часть, открыл PR |
| Поставить `ready-for-test` | **код-ревьюер** (`code-review`) | принял изменение |
| Поставить `ready-for-dev` из ревью | **код-ревьюер** (`code-review`) | вернул на доработку |
| Поставить `ready-for-frontend` | **диспетчер** | бэкенд-часть полного стека прошла ревью |
| Поставить `phase:frontend` | **диспетчер** | выдал полный стек фронтенд-разработчику (`dev-frontend`) |
| Снять `in-progress` | **исполнитель** (`dev-fullstack`, `dev-backend`, `dev-frontend`) **/ тестировщик** (`tester`) | на своём финальном шаге |
| Поставить `tested` | **тестировщик** (`tester`) | зелёный вердикт |
| Поставить `test-failed` | **тестировщик** (`tester`) | красный вердикт |
| Поставить `merged` | **DevOps-инженер** (`devops-delivery`) | слил PR |
| Снять всё и снять с конвейера | **диспетчер** | исчерпан лимит попыток или доработок |

## 3. Метки: кто ставит, при каком событии, кто снимает

Имена по умолчанию; проект может переопределить их в `~/.dsh/projects.json` → `projects.<id>.labels`.

| Метка | Ставит | Событие | Снимает |
|---|---|---|---|
| `needs-mockup` | аналитик (`analyst`) через `gh_issue_mockup` или человек вручную | постановка меняет визуальный слой | дизайнер, если визуального слоя в задаче нет; диспетчер при снятии с конвейера и при слиянии |
| `mockups-ready` | дизайнер (`design`) | макет закоммичен, скриншоты в issue | человек, если макет не годится (макет переделывается); диспетчер при слиянии и при снятии |
| `ready-for-dev` | человек | беру задачу в работу | диспетчер при выдаче задачи; диспетчер при снятии с конвейера |
| `area:backend` / `area:frontend` / `area:fullstack` | диспетчер (по тексту постановки) или человек | тикет в очереди без маршрута | только человек |
| `in-progress` | диспетчер | выдал задачу | исполнитель в финале своего шага; диспетчер при снятии |
| `for-code-review` | исполнитель: `dev-fullstack`, `dev-backend`, `dev-frontend` | PR открыт, работа сдана | код-ревьюер (при любом вердикте); диспетчер при передаче фронтенду и при снятии |
| `ready-for-test` | код-ревьюер (`code-review`) | изменение принято | тестировщик (при вердикте); диспетчер при передаче фронтенду; при снятии |
| `ready-for-frontend` | диспетчер | бэкенд-половина прошла ревью (или бэкенд-части нет) | диспетчер при выдаче фронтендеру; при снятии; при слиянии |
| `phase:frontend` | диспетчер | выдал полный стек фронтендеру | при снятии; при слиянии |
| `tested` | тестировщик (`tester`) | прошло | DevOps-инженер при слиянии; диспетчер, если PR слит раньше |
| `test-failed` | тестировщик (`tester`) | не прошло | диспетчер при выдаче доработки; при снятии |
| `merged` | DevOps-инженер (или диспетчер, если PR слит заранее) | слияние состоялось | никогда — терминальная |

Дизайнер получает тикет только на ступени макета (`needs-mockup`). Маршрут `area:*` на дизайнера
не указывает никогда, в том числе `area:frontend`: интерфейс по макету делает
фронтенд-разработчик, а не дизайнер.

## 4. Конвейер

Схема разбита на три части, потому что это три разных вещи: **кто получает задачу**
(маршрут), **какой меткой шаг передаётся дальше** (метки хода) и **что происходит с задачей
на каждой ступени**.

### 4.1 Маршрут: кому диспетчер отдаёт задачу

```
needs-mockup ──► дизайнер рисует макет ──► mockups-ready ──► человек: ready-for-dev
```
Если макет не нужен, человек ставит `ready-for-dev` сразу.

```
ready-for-dev (человек)
      │  входная ступень: диспетчер читает постановку и ставит area:*
      ├── area:backend    ──► dev-backend
      ├── area:frontend   ──► dev-frontend
      ├── area:fullstack  ──► dev-backend, затем dev-frontend
      └── маршрут не определён ──► dev-fullstack
```

`design` — **не** ветка маршрута `area:*`. Маршрут `area:frontend` всегда идёт фронтенд-разработчику;
дизайнер получает тикет только на ступени макета (`needs-mockup`, до разработки), а
интерфейс по этому макету пишет фронтенд-разработчик. Реализацию дизайнер не делает.

### 4.2 Метки одного шага

```
диспетчер выдал задачу     → ставит in-progress, снимает ready-for-dev / ready-for-frontend
исполнитель закончил       → ставит for-code-review, снимает in-progress
код-ревьюер принял         → ставит ready-for-test, снимает for-code-review
код-ревьюер вернул         → ставит ready-for-dev, снимает for-code-review
тестировщик принял         → ставит tested, снимает ready-for-test
тестировщик вернул         → ставит test-failed, снимает ready-for-test
DevOps слил                → ставит merged, снимает tested
```

То есть `in-progress` → (работа) → `for-code-review` → (ревью) → `ready-for-test` → (тест) →
`tested` → (слияние) → `merged`. Ревью всегда идёт **после** `for-code-review`, а не наоборот.

### 4.3 Полный стек: два ревью и две метки `for-code-review`

Полный стек — единственный маршрут, где один и тот же шаг повторяется дважды, поэтому на
схеме он выглядит длиннее остальных:

```
dev-backend
   │  for-code-review  (+ PR)
   ▼
code-review ──► ready-for-test
   │  диспетчер: снимает ready-for-test, ставит ready-for-frontend
   ▼
dev-frontend  (та же ветка, тот же PR)
   │  for-code-review (вторая, окончательная)
   ▼
code-review ──► ready-for-test ──► tester ──► devops-delivery ──► merged
```

Первое ревью смотрит только бэкенд-часть и не считает отсутствие экранов дефектом; второе —
всё изменение целиком. Тестировщику тикет уходит только после второго.

### 4.4 Общий хвост

```
ready-for-test ──► tester ──┬──► tested ──► devops-delivery ──► merged
                            └──► test-failed ──► исполнитель (доработка)
```

### 4.5 Состояние тикета → кто действует → что ставит

| Метка на тикете сейчас | Кто берёт | Что ставит | Что снимает |
|---|---|---|---|
| `needs-mockup`, нет `mockups-ready` | дизайнер (`design`), ступень макета | `in-progress`, затем `mockups-ready` | `in-progress` |
| `mockups-ready`, нет `ready-for-dev` | человек | `ready-for-dev` (приёмка макета) | — |
| `ready-for-dev` (+ макет не нужен или готов) | диспетчер: маршрут | `area:*` | — |
| `ready-for-dev` + `area:*` | `dev-backend` / `dev-frontend` / `dev-fullstack` | `in-progress`, затем `for-code-review` | `ready-for-dev`, `in-progress` |
| `for-code-review` | код-ревьюер | `ready-for-test` или `ready-for-dev` | `for-code-review` |
| `area:fullstack` + `ready-for-test`, без `phase:frontend` | диспетчер: передача фронтенду | `ready-for-frontend` | `ready-for-test` |
| `ready-for-frontend` | `dev-frontend` | `in-progress`, `phase:frontend`, затем `for-code-review` | `ready-for-frontend`, `in-progress` |
| `ready-for-test` (после второго ревью) | тестировщик (`tester`) | `tested` или `test-failed` | `ready-for-test` |
| `tested` | DevOps-инженер (`devops-delivery`) | `merged`, удаляет `mockups/<N>` в ветке | `tested`, `mockups-ready`, `needs-mockup` |
| `test-failed` | исполнитель: `dev-fullstack`, `dev-backend`, `dev-frontend` | `in-progress`, затем `for-code-review` | `test-failed`, `in-progress` |
| `in-progress` (ход завис) | тот же исполнитель | — | `in-progress` |

Эту таблицу можно читать сверху вниз как конвейер: каждая строка — один шаг, следующая
строка начинается с метки, которую поставила предыдущая.

### Шаги по событиям

**0. Аналитик поставил постановку и `needs-mockup`.**
Диспетчер на ближайшем тике в окне смены поднимает сессию `design` **до** метки человека:

- дизайнер читает постановку, создаёт ветку `feature/<N>-<слаг>` и кладёт в неё
  `mockups/<N>/index.html` (статичный прототип без сборки) и `mockups/<N>/notes.md`
  (экраны, состояния, брейкпоинты, тексты);
- рендерит макет в PNG через `~/.dsh/tools/mockup-shot.mjs` и прикладывает картинки
  комментарием в issue;
- финал ступени: комментарий + `mockups-ready`, снятие `in-progress`. Метку `for-code-review`
  дизайнер не ставит и PR не открывает — реализации ещё нет.

Тикет с `needs-mockup` и без `mockups-ready` в очередь разработки не попадает, даже если
человек уже поставил `ready-for-dev`.

**1. Человек поставил `ready-for-dev`.**
Это и есть приёмка макета: метку ставят, посмотрев на картинки в issue.
Диспетчер на ближайшем тике:

- если маршрута нет — читает постановку, ставит `area:*` и комментарий с признаками, дальше на
  следующем тике;
- выбирает роль по маршруту: `area:backend` → `dev-backend`, `area:frontend` → `dev-frontend`,
  `area:fullstack` → `dev-backend`, без метки → `dev-fullstack`;
- ставит `in-progress`, снимает `ready-for-dev` (а также `test-failed`, `for-code-review`,
  и `ready-for-frontend`, если это ступень фронтенда);
- для полного стека на фронтенд-половине дополнительно ставит `phase:frontend`;
- поднимает сессию роли с заданием: ветка, база, PR, финальный шаг, границы, защита клона человека.

**2. Исполнитель закончил.**
Пишет комментарий в issue (что сделано, ветка, номер PR, что не проверено), ставит `for-code-review`,
снимает `in-progress`.

Тело PR приводится в соответствие с диффом **до** метки `for-code-review`: сначала текущее тело
читается инструментом `gh_pr`, затем правится `gh_pr_edit` — телом целиком, а не «по памяти».
Замечание «тело PR описывает прежнюю ревизию» закрывается правкой тела, а не ответным комментарием:
комментарий в обсуждении тело PR не меняет. Метки, состояние и мерж `gh_pr_edit` не трогает.

**3. Код-ревьюер.**
Читает PR, оставляет замечания комментариями в PR, решение — меткой:

- принял → `ready-for-test`, снять `for-code-review`;
- нужны правки → `ready-for-dev`, снять `for-code-review`, короткий комментарий в issue.

Ответы автора на замечания читаются через `gh_pr({ "number": N, "comments": true })`, а не
домысливаются. Расхождение тела PR с диффом остаётся замечанием **автору**: ревьюер тела не правит.

**Возврат в доработку уходит половине из замечаний.**
Роль выбирают не метка маршрута и не состав PR, а пути файлов, названные в замечаниях ревьюера:
диспетчер берёт последний круг комментариев PR (от последнего `FIX:` / `SHIP` / `BLOCKED` до
конца списка), выдёргивает из текста пути и раскладывает их по `areas` проекта. Только
бэкенд-пути → `dev-backend`, только фронтенд-пути → `dev-frontend`, пути из обоих деревьев →
`dev-fullstack`; путей нет или PR не прочитан — решает метка маршрута и фаза, как раньше. След
маршрута остаётся в тикете: комментарий «доработка №N из 3 (возврат из код-ревью) →
`dev-frontend`: `frontend/src/lib/a.js`, `frontend/src/api/b.js`», а исполнитель получает в задании
строку «Замечания ревьюера — в твоей половине» с теми же путями.

**Круг без нового коммита не считается доработкой.**
Если разработчик переставил `for-code-review`, а head PR остался прежним, ревьюер увидел бы ту же
ревизию: диспетчер его не зовёт, комментирует «ветка не менялась с прошлого ревью — ревизия `<sha>`
та же», возвращает счётчик доработок на один назад и отдаёт доработку владельцу замечаний. Второй
такой круг подряд снимает тикет с конвейера человеку.

**4. Первая половина полного стека.**
Диспетчер видит `area:fullstack` + `for-code-review` + открытый PR и **не** передаёт задачу фронтенду:
ревьюер смотрит бэкенд-часть. После `SHIP` диспетчер:

- снимает `ready-for-test`,
- ставит `ready-for-frontend`,
- комментирует «бэкенд-часть прошла код-ревью — передано фронтенду».

Тестировщику тикет на этом шаге не уходит.

**5. Фронтенд-половина.**
Диспетчер выдаёт `dev-frontend` (ставит `in-progress`, снимает `ready-for-frontend`,
ставит `phase:frontend`). Фронтендер продолжает в той же ветке и том же PR.

**6. Второе ревью.**
После `for-code-review` ревьюер смотрит всё изменение целиком. `SHIP` → `ready-for-test` уже
уходит тестировщику.

**7. Тестировщик.**
Разворачивает ветку в отдельный `git worktree`, проверяет сам, вердикт комментарием:

- прошло → `tested`, снять `ready-for-test`;
- не прошло → `test-failed`, снять `ready-for-test`, обязательна наименьшая воспроизводящая команда.

**8. Слияние.**
DevOps-инженер находит PR, сверяется с вердиктом, сливает merge-коммитом, удаляет ветку задачи,
комментирует sha и снимает `tested`, ставит `merged`. Диспетчер дополнительно снимает
`phase:frontend` и `ready-for-frontend`, если они остались.

Если PR уже был слит человеком, диспетчер сам ставит `merged` и снимает `tested` — без сессии
DevOps-инженера.

## 5. Что делает только диспетчер

| Действие | Повод | Результат |
|---|---|---|
| Маршрутизация `area:*` | тикет в очереди без маршрута | метка + комментарий с признаками |
| Ступень макета | постановка с `needs-mockup` без `mockups-ready` | сессия `design` в режиме макета, `in-progress` |
| Передача фронтенду | полный стек, первая половина принята ревью | `ready-for-frontend` |
| Возврат в доработку | `ready-for-dev` или `test-failed` | роль — по путям замечаний; половина и до трёх путей в комментарии |
| Сторож пустого круга ревью | `for-code-review`, а head PR равен прошлому | комментарий «ветка не менялась», счётчик доработок на один назад, доработка владельцу замечаний |
| Уборка меток после слияния | PR слит | снимает `mockups-ready`, `needs-mockup`, `phase:frontend`, `ready-for-frontend` |
| Снятие с конвейера | попыток > 4, доработок ≥ 3 или два круга ревью без нового коммита | комментарий, снятие всех меток стадий **включая `ready-for-dev`**, пометка «снят» |
| Снятие зависшей сессии | ход без записей дольше 30 мин | `cancel` сессии; метки не меняются, задача выдастся заново |
| Закрытие смены | окно закончилось или ручная команда сводки | сводка в Telegram, смена закрыта |

Маршрутизация работает даже вне окна смены: это книга, а не работа агента.

Снятый тикет не подхватывается сам: метки стадий сняты, и без человека он в очередь не вернётся.
Вернуть его может только человек, поставив `ready-for-dev`. Тогда снимается пометка «снят» и
выдаётся новый бюджет: сбрасываются **и попытки, и доработки**, а диалоги ролей забываются, чтобы
задача началась как новая.

---

## 6. Что делает только человек

- Ставит `ready-for-dev` — единственный вход в конвейер.
- Смотрит макет и либо ставит `ready-for-dev` (макет принят), либо снимает `mockups-ready` и
  пишет в issue, что переделать — макет вернётся дизайнеру.
- Может поставить `needs-mockup` сам — и вместо аналитика, и когда задача уже в очереди.
- Может поставить `area:*` сам — диспетчер существующую метку не перезаписывает.
- Может вернуть снятый тикет, поставив `ready-for-dev`.
- Может поменять маршрут, если диспетчер ошибся: `area:*` решает, кто возьмёт задачу.
- Мержит PR, сделанные самой ролью DevOps (`devops-delivery`, своя доставка).
- Закрывает issue.

## 7. Лимиты и счётчики

- **Попытки**: до 4 выдач одной задачи. Счётчик обнуляется, когда сессия сдвинула метки,
  когда диспетчер сам сделал шаг (маршрут, передача фронтенду), и когда человек вернул снятый тикет.
- **Доработки**: до 3 возвратов из ревью или теста в одну задачу. Счётчик живёт на тикет, но
  сбрасывается, когда человек возвращает снятый тикет в работу. Счётчик **общий на весь маршрут**:
  ревью бэкенд-половины, ревью фронтенд-половины и возврат из теста тратят один и тот же бюджет.
- **Круг без нового коммита бюджет не тратит**: если ревизия PR не сменилась с прошлого ревью,
  ревьюер не зовётся, а счётчик доработок откатывается на один назад. Второй такой круг подряд —
  снятие с конвейера: значит, разработчик отчитывается, а ветку не двигает. Ход ревьюера, который
  так и не начался (сбой модели) или был снят за зависание, записанную ревизию не сохраняет —
  следующий тик позовёт ревьюера снова, а не объявит пустой круг.
- **Номер доработки виден в тикете**: на каждом возврате диспетчер пишет комментарий
  «доработка №2 из 3 (возврат из код-ревью/теста)», исполнитель получает номер круга в задании,
  а ревьюер и тестировщик — счётчик и номер, которым станет их возврат, и обязаны указать его в
  комментарии вердикта. На последнем круге им прямо сказано, что возврат снимет тикет с конвейера.
  Комментарий автоснятия тоже называет номер возврата и лимит.
- **Ступень макета** идёт в тот же счётчик попыток, но не в счётчик доработок: ход дизайнера
  обнуляет попытку, когда заканчивается меткой `mockups-ready`.
- **Зависание**: ход без новых записей 30 минут снимается, метки остаются — задача выдастся заново.
- **Окна смены**: 13:00–04:00 и 07:00–09:00. Смена стартует в окне один раз, при закрытии окна
  закрывается со сводкой в Telegram. Вне окна работа не идёт, но маршрутизация работает.
- **Один тикет за раз** на проект: следующая задача не берётся, пока текущая не получила `merged`.

## 8. Особые случаи

| Случай | Что делает диспетчер |
|---|---|
| Полный стек, бэкенд-части в постановке нет | бэкендер ставит `for-code-review` без PR → диспетчер сразу передаёт фронтенду |
| PR конфликтует с базой | DevOps не форсирует: комментарий с конфликтующими файлами, `ready-for-dev`, задача возвращается разработчику |
| PR уже слит человеком | `merged` ставится без сессии, `tested` и `phase:frontend` снимаются |
| Тикет в очереди без `area:*` | маршрут определяется по тексту постановки |
| Маршрут не определяется | метка не ставится, задачу берёт `dev-fullstack` |
| Человек убрал `area:*` | при следующем шаге маршрут определится заново |
| Ревьюер не поставил ни одной метки | задача остаётся в ревью, попытка расходуется |
| Дизайнер (`design`) решил, что визуального слоя в задаче нет | снимает `needs-mockup`, комментирует; тикет идёт по маршруту как обычно |
| Человек снял `mockups-ready` | дизайнер (`design`) переделывает макет в том же диалоге; разработка не начинается, пока макет не принят |
| Человек поставил `ready-for-dev` до макета | метка ждёт: разработка начнётся сразу после `mockups-ready` |
| Макеты остались в ветке снятого тикета | ветка остаётся человеку: диспетчер её не удаляет, решение за ним |

## 9. Чего роли не делают никогда

- Не ставят `ready-for-dev`: это право человека. Единственная служебная метка постановки, доступная роли, — `needs-mockup` у `analyst`.
- Не ставят и не меняют `area:*`: это входная ступень диспетчера.
- Не ставят `ready-for-frontend` и `phase:frontend`: это диспетчеровы метки стадий.
- Не ставят `ready-for-dev` и `area:*` вообще: у аналитика для постановки есть только
  `gh_issue_mockup` (одна метка `needs-mockup`), остальные роли ставят лишь метки своего шага.
- Дизайнер на ступени макета не ставит `for-code-review` и не открывает PR: это шаг реализации.
- Не коммитят `mockups/<N>` в `<base>`: макеты удаляет DevOps-инженер перед слиянием, в истории
  git они остаются.
- Не мержат PR, кроме DevOps-инженера (`devops-delivery`) и только по заданию.
- Не переключают ветки в чужой рабочей копии и не трогают клон человека.
- Не поднимают стенд без `-p <composeProject>`.
- Не правят продуктовый код вне своей роли: бэкендер — только бэкенд-дерево, фронтендер — только
  фронтенд-дерево, `dev-fullstack` — оба дерева целиком. Дизайнер не правит продуктовый код
  вообще: он только рисует макет. Тестировщик и ревьюер не правят никогда.
