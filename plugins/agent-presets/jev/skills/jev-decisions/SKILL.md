# Суждения через Jev (System One)

Jev — не чат-модель: он не пишет текст, а оценивает состояние и отвечает на вопросы о нём
типизированными вероятностями. Этот скилл описывает, как выбирать примитив, как формулировать
вопросы, как вызывать инструменты `jev_decide` / `jev_ask` / `jev_models` и как читать ответ.

Живые документы TypeSafe — источник истины: <https://docs.typesafe.ai/llms.txt> (любую страницу
можно запросить как Markdown, добавив `.md`). Эндпоинт: `POST https://api.typesafe.ai/v1/systemone`.

## 1. Когда Jev уместен, а когда нет

**Уместен**, когда правило нельзя записать формулой, но человек решает это мгновенно:

- разметка и маршрутизация: к какой команде, категории, типу относится вход;
- ранжирование и отбор: какой из кандидатов ближе к запросу;
- проверка: подтверждает ли фрагмент утверждение, есть ли в тексте персональные данные;
- оценка степени: насколько решение рискованно, насколько срочно сообщение;
- гейт перед действием: безопасно ли выполнять этот шаг.

**Не уместен**:

- точные факты, арифметика, поиск по таблице — это код;
- генерация текста, объяснений, резюме — Jev не генерирует текст, это работа LLM;
- «собеседник»: диалога с Jev не существует, есть запрос состояния и вопросы.

## 2. Выбор примитива

| Что нужно | Тип | Как читается ответ | Важное отличие |
|---|---|---|---|
| Одно из заданного набора | `choice` | `choice`, `probabilities`, `confidence` | варианты конкурируют между собой в одном распределении |
| Выполнено ли условие | `noul` | `noul` — вероятность «да», 0..1 | нет отдельного confidence: одно число описывает всё распределение |
| Степень по описанной шкале | `score` | `score`, `legend`, `probabilities`, `confidence` | уровни оцениваются самостоятельно, ответ ложится между уровнями |

Ловушки выбора:

- **Не измеряй степень через noul.** «Сильный ли кандидат в Python?» — это одно утверждение, а не шкала.
  Для «сколько опыта» нужен score с уровнями, описывающими конкретные ситуации.
- **Несколько ярлыков, которые могут быть верны одновременно** — это несколько noul, а не один choice.
  Choice честно выбирает один вариант и распределяет остальное между конкурентами.
- **Числа `noul` не сравнимы между разными вопросами.** Сравнивать кандидатов по одному noul можно
  (реранкинг), но 0.7 в двух разных вопросах не означает «одинаково верно».

## 3. Как формулировать вопросы

- **Одно суждение на вопрос.** «Клиент злой и просит возврат?» — это два вопроса.
- **Высокое значение = «да».** Формулируй утвердительно: `is_urgent`, а не `is_not_urgent`.
  Инвертированный вопрос легко прочитать задом наперёд в коде.
- **Давай контекст в состоянии, а не в вопросе.** Вопрос — про суждение; данные, определения и
  правила — в `state` или в структурированном `instructions` (объект: вопрос в одном поле, данные в других,
  ссылки на данные — в обратных кавычках по имени поля, как на вложенные поля состояния).
- **Полный список вариантов для choice**, плюс `other` / `none of the above`, если список может не покрыть
  вход. Модель не выберет вариант, которого нет в критериях.
- **Различай варианты по существу.** Если два варианта легко спутать, опиши каждый объектом: что покрывает,
  что не покрывает (`not_for`), примеры. Имена полей выбираешь ты — зарезервированных нет.
- **`criteria` для noul — только когда граница неочевидна**: `{"true": "…", "false": "…"}`.
- **Уровни score понимаются сами по себе**: не «низкий/средний/высокий», а «работ не было», «правки в одном файле»,
  «сквозная миграция с изменением контракта».
- **Английский точнее.** Формулируй `instructions` и `criteria` по-английски, если состояние не требует иного;
  значения на русскоязычных данных проверяй на своих примерах.

## 4. Вызов

Все вопросы об одном состоянии — **одним вызовом** `jev_decide`: они считаются параллельно, и добавление
вопросов почти не удорожает ответ.

```
jev_decide(
  state: "<текст состояния>"            // или JSON-текст, начинающийся с { или [
  stateFile: "D:\\path\\to\\input.txt"  // вместо state: содержимое файла станет состоянием
  questions: [
    { id: "is_urgent", type: "noul",
      instructions: "The message conveys urgency or time-sensitivity" },
    { id: "department", type: "choice",
      instructions: "Which team should handle this?",
      criteria: "{\"billing\":\"Payments, invoices, refunds\",\"technical\":\"Bugs, outages, integrations\",\"other\":\"None of the above\"}" },
    { id: "risk", type: "score",
      instructions: "How risky is this change to run unattended?",
      criteria: "[\"Read-only\",\"Touches one file\",\"Changes a contract or data\"]" }
  ]
)
```

- `criteria` и структурированный `instructions` передаются **JSON-текстом** — плагин разворачивает их сам.
- `jev_ask(type, instructions, criteria?, state|stateFile, id?)` — короткая форма для одного вопроса.
- `jev_models()` — список моделей аккаунта; заодно проверка ключа: 401 означает, что ключ неверен
  или его нет (`~/.dsh/typesafe.token` либо `TYPESAFE_API_KEY`). Ключ агенту не показывается — не проси его у человека.
- Модель по умолчанию — `jev-latest` (сейчас `jev-1.13.0`). Если пороги настроены под конкретную версию,
  фиксируй её номер, а не псевдоним.

Ошибки: `422` — форма вопроса (чинится формулировкой), `429` — лимит, `529` — перегрузка; и то и другое
плагин повторяет с задержкой, прежде чем вернуть ошибку.

## 5. Чтение ответа

```json
{
  "model": "jev-1.13.0",
  "answers": {
    "is_urgent":  { "type": "noul",   "noul": 0.95 },
    "department": { "type": "choice", "choice": "billing", "confidence": 0.81,
                    "probabilities": { "billing": 0.88, "technical": 0.12, "other": 0.0 } },
    "risk":       { "type": "score",  "score": 1.05, "confidence": 0.92,
                    "legend": { "0": "Read-only", "1": "Touches one file", "2": "Changes a contract or data" },
                    "probabilities": { "0": 0.0, "1": 0.95, "2": 0.05 } }
  },
  "usage": { "input_tokens": 589, "output_tokens": 212 }
}
```

Правила чтения:

- **Показывай распределение, а не только выбор.** `choice` без `probabilities` и `confidence` скрывает,
  что решение было пограничным.
- **`confidence` — это про концентрацию распределения**, а не про правильность решения и не разрешение действовать.
- **`noul ≈ 0.5` не значит «средняя степень»**: это «да» и «нет» равновероятны.
- **Порог — это цена ошибки.** Ложное «да» дорого (платить, будить человека) — порог выше 0.5;
  пропущенное «да» дорого (не заметить проблему) — ниже. Три пути вместо двух: значения в середине
  уходят человеку, а не в автоматическую ветку.
- **Не выдумывай числа.** Любая вероятность в ответе человека обязана прийти из вызова инструмента;
  без ключа или при ошибке честно скажи, что оценки нет.

## 6. Паттерны

- **Веер вопросов (fan-out).** Один state, много вопросов, включая спекулятивные («если это возврат, то почему»).
  Код использует нужные ответы и игнорирует остальные. Второй запрос нужен лишь тогда, когда следующий вопрос
  зависит от предыдущего ответа или требует новых данных.
- **Маршрутизация через confidence.** Низкий confidence у choice — сигнал отдать решение человеку,
  а не выбирать наугад. Ответ с распределением 0.61/0.35 — это два владельца задачи, а не один.
- **Составная оценка.** Считай измерения один раз (score по измерениям), а веса, пороги и ранжирование
  держи в коде: изменение веса не должно требовать нового вызова модели.
- **Правило «любое серьёзное нарушение»** нельзя выразить взвешенной суммой — это отдельный noul на каждое условие.
- **Проверка и эскалация.** Jev проверяет конкретное утверждение против конкретного фрагмента;
  сомнительные и падающие случаи уходят к человеку или к LLM.

## 7. Типичные ошибки

- Спросить «что ты думаешь?» вместо узкого суждения.
- Склеить два условия в один noul.
- Инвертировать формулировку вопроса.
- Ждать от Jev текста, объяснений или диалога.
- Спрятать распределение и показать только выбранный вариант.
- Взять порог наугад, не назвав цену ошибки.
- Отправить слишком большое состояние: лимит — 32k токенов на состояние плюс самый длинный вопрос.
- Пересказать или запросить ключ вместо чтения ошибки 401.

## 8. Проверка

Jev калиброван обучением, но это не истина в вашем домене: типизированный ответ гарантирует форму, а не
правильность. Прогоняй представительные примеры человека, смотри на пограничные случаи (0.3–0.7 у noul,
низкий confidence у choice), различай отсутствие данных, ошибку модели, ошибку кода и сбой сервиса.
Стоимость: счёт идёт по входным токенам, выходные бесплатны; порядок цены — около $42 за миллиард
входных токенов (проверяй актуальные цифры на странице моделей).
