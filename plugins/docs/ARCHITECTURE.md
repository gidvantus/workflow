# Как устроен отдел разработки

Документ описывает не DSH, а надстройку поверх него: кто кого запускает, по каким
правилам выдаются задачи и что происходит, когда что-то ломается.

## Общая картина

```
                    ┌──────────────────────────────────────────┐
   расписание смен  │  dev-department.mjs (хост-плагин)        │
   ~/.dsh/          │  тик раз в минуту:                       │
   dev-department.json │  окно смены? → работа по проектам?    │
   projects.json    └───────────────────┬──────────────────────┘
                                        │ open_role_session(preset, задача)
                                        ▼
                    ┌──────────────────────────────────────────┐
                    │  role-sessions.mjs — сессия роли          │
                    │  рабочая область = клон отдела проекта    │
                    └───────────────────┬──────────────────────┘
                                        │ персона + скиллы пресета
                                        ▼
        analyst → design (макет) → dev-backend / dev-frontend / dev-fullstack → code-review → tester → devops-delivery
                                        │
                                        ▼
                    GitHub: метки, комментарии, PR, вердикт со скриншотами
                                        │
                    Telegram: сводка смены по каждому проекту
```

Одно действие на проект за тик. Завершившаяся сессия попадает в сводку на одном
тике, следующая задача выдаётся на следующем — так смена читается в журнале
как последовательность шагов, а не как пачка одновременных запусков.

## Проекты

Отдел многопроектный: и диспетчер, и пресеты не знают ни одного конкретного
адреса. Всё проектное лежит в реестре проектов отдела —
`<DSH_HOME>/profiles/desktop/dsh-dev-department/projects.json` (каталог состояния
называет `plugins/state-paths.mjs`):

| Поле | Зачем |
|---|---|
| `repo`, `base` | репозиторий GitHub и базовая ветка |
| `workspace` | клон отдела, в нём работает роль |
| `humanClone` | клон человека — неприкосновенен |
| `composeProject` | имя своего compose-стенда |
| `frontendPort`, `apiPort` | порты стенда |
| `artifacts` | каталог артефактов вне рабочей копии |
| `department` | включённость, окна смен, `maxRework` |
| `labels` | переопределение имён меток конвейера, если проект их переименовал |

Значения берутся из записи проекта в реестре по полю `workspace`: роль открывает
`projects.json` и находит свою запись, поэтому в персонах и скиллах вместо адресов стоят
заполнители `<repo>`, `<base>`, `<workspace>`, `<humanClone>`, `<composeProject>`,
`<frontendPort>`, `<apiPort>`, `<artifacts>`, `<id>` — один и тот же пресет
работает в любом проекте реестра.

## Конвейер меток

Что и при каком событии ставит каждая роль — в
[DEPARTMENT-PROCESS.md](DEPARTMENT-PROCESS.md). Здесь — как это устроено в коде.

```
постановка (analyst) ──needs-mockup──> design: макет ──> mockups-ready
                                                            │  человек: ready-for-dev
                                                            ▼
     area:backend   ──> dev-backend
     area:frontend  ──> dev-frontend
     area:fullstack ──> dev-backend ──review──> dev-frontend
     маршрут не определён ──> dev-fullstack
                                                            │
        in-progress ──PR──> for-code-review ──> ready-for-test ──> tester ──> tested
                                                            │                    │
                                            ready-for-dev ◄─┘                    ▼
                                          (доработка)                    devops-delivery ──> merged
```

- `ready-for-dev` ставит человек. Аналитик его не ставит: решение «в работу» —
  человеческое. Если постановке нужен макет, эта метка означает ещё и приёмку
  макета: до `mockups-ready` тикет в разработку не уходит.
- **Ступень макета.** Тикет с `needs-mockup` (ставит аналитик меткой через
  `mcp__github__issue_write` или человек вручную) раньше клика человека проходит через
  `design`: статичный прототип в `mockups/<номер>/`, скриншоты комментарием,
  финальная метка `mockups-ready`. PR дизайнер не открывает и `for-code-review`
  не ставит — реализации на этой ступени нет. Пока `mockups-ready` нет,
  `queuedOf` не пускает тикет в разработку, даже если `ready-for-dev` уже стоит.
- **Маршрут.** Его ставит диспетчер по тексту постановки: `area:backend` →
  `dev-backend`, `area:frontend` → `dev-frontend`, `area:fullstack` →
  `dev-backend` и затем, после ревью половины, `dev-frontend`; без уверенности
  маршрут не ставится и тикет берёт `dev-fullstack`.
- **Исполнитель** — `dev-backend`, `dev-frontend` или `dev-fullstack`; метка
  маршрута живёт на тикете всю жизнь задачи. Возврат в доработку выбирает не она,
  а пути файлов из замечаний, и источник зависит от того, кто вернул тикет. Из
  ревью: диспетчер берёт последний круг комментариев PR (от последнего
  комментария с ролью `код-ревьюер` и строкой вердикта в шапке) и читает
  **только непомеченные пункты** его чеклиста (`- [ ] Б1 · path:line`). От
  тестировщика (`test-failed`): тот же разбор применяется к его вердикту
  **в issue** — диспетчер читает комментарии тикета, берёт вердикт
  (`VERDICT: RED` / `GREEN`) и раскладывает непомеченные пункты по `areas`;
  без чеклиста тестировщика остаётся круг ревьюера, а без путей — метка.
  Пункт, закрытый галочкой, — отработанное замечание, и в маршрут он не
  попадает: иначе закрытый пункт возвращался бы в доработку вечно. Комментарий
  без чекбоксов (старый формат, тикет в полёте) разбирается как раньше —
  целиком, иначе такие тикеты потеряли бы маршрут. Только
  бэкенд-пути → `dev-backend`,
  только фронтенд-пути → `dev-frontend`, оба дерева → `dev-fullstack`; путей нет
  или список не прочитан — решает метка маршрута и фаза. Дизайнер реализацию не делает
  и маршрутом `area:*` не выбирается.
- **Заголовок роли.** Первая строка любого комментария в issue и PR —
  `**Роль:** <кто> · <о чём>`. Штатный MCP-сервер GitHub заголовок не проверяет —
  это правило конвейера, и держится оно заданием и скиллами ролей; свои
  комментарии диспетчер публикует через `postComment()`, поэтому формат задан в
  одном месте. Круг ревью открывает
  последний комментарий с ролью `код-ревьюер` **и вердиктом в шапке**: вердикт
  назван отдельной строкой среди первых трёх (канон скилла: заголовок, вердикт,
  пустая строка) или прямо в заголовке — `**Роль:** код-ревьюер · вердикт FIX: 2`;
  оба вида принимаются, иначе круг теряется на том, который роль выбрала сама.
  Заголовок есть у каждого замечания, и без вердикта круг схлопывался бы до
  последнего замечания, теряя пути остальных. Вердикт ищется в шапке, а не по
  всему телу, потому что замечание, которое цитирует строку вердикта (в тикетах
  про форматы комментариев это норма), иначе объявляло бы себя началом круга и
  обнуляло пути всего круга. Вердикт старого формата (`FIX:` / `SHIP` / `BLOCKED`
  в первой строке) остаётся запасным путём для тикетов, начатых до выкатки, —
  иначе маршрут доработок молча съехал бы на метку `area:*`.
  Признак «свой комментарий» у диспетчера — роль `диспетчер`, префикс
  «Отдел разработки:» остаётся вторым условием.
- Дизайн-пресет нужен только на ступени макета: скилл `mockup-delivery` — формат
  макета, типографика, тексты, планка качества; ветка `feature/<номер>-<слаг>`
  (в ней позже работает разработчик). Скриншоты MCP вложить не умеет: PNG
  называются путями в комментарии к тикету.
- Исполнитель забирает задачу, ставит `in-progress`, открывает PR в базовую ветку
  и передаёт `for-code-review`. **Мерж PR делает человек.** Тело PR — часть отчёта,
  а не украшение: перед `for-code-review` исполнитель приводит его в соответствие с
  диффом инструментом `mcp__github__update_pull_request`, прочитав текущее тело
  через `mcp__github__pull_request_read` с `"method": "get"`. Инструмент меняет
  только переданные поля: метки, состояние и мерж остаются у процесса.
- Код-ревьюер читает PR и код вокруг, замечания пишет **в PR**
  (`mcp__github__add_issue_comment`: для этого инструмента PR — такой же issue) —
  **одним** комментарием-чеклистом: заголовок роли, строка вердикта, «Что делает
  изменение», чеклист двумя секциями `### Бэкенд` и `### Фронтенд` с пунктами
  `- [ ] Б1 · path:line — … · Случай · Правка · Если не править`, затем «Не
  проверено». Россыпь «комментарий на замечание» ушла: по непомеченным пунктам
  диспетчер строит маршрут, а автор закрывает пункт галочкой в том же
  комментарии. Замечание, найденное позже (второй круг, ответ автора), ревьюер
  **дописывает в тот же комментарий** через `mcp__github__update_issue_comment`
  с телом целиком;
  новый комментарий для этого не открывается. Ответы автора он читает там же
  (`mcp__github__pull_request_read` с `"method": "get_comments"`, в списке есть `id`
  комментария), а не домысливает;
  расхождение тела PR с диффом — замечание автору, а не повод править тело
  самому. Решение — меткой: принял → `ready-for-test`,
  сняв `for-code-review`; нужны правки → `ready-for-dev`, сняв `for-code-review`,
  и одна короткая строка в issue («вернул: N пунктов в комментарии PR #M»), не
  больше.
- Доработка после ревью идёт в **той же** ветке и **том же** диалоге исполнителя:
  новый PR под замечания не открывается. Пункты закрываются галочками в чужом по
  роли комментарии: отдельного «переключи галочку» в MCP нет, поэтому роль
  читает тело комментария, меняет `- [ ]` на `- [x]` и пишет его обратно через
  `mcp__github__update_issue_comment` — целиком, чтобы не потерять вложения
  тестировщика. Пункт, с которым разработчик не согласен, не отмечается — аргумент
  идёт в тело PR через `mcp__github__update_pull_request`; в issue остаётся одна
  строка «замечания отработаны, PR #N, коммит `<sha>`».
- Тестировщик выносит вердикт: `tested` или `test-failed`. С вердиктом в issue
  уходит комментарий и 2–3 картинки интерфейса.
- `test-failed` возвращает задачу исполнителю в том же диалоге; половину и пути
  замечаний диспетчер берёт из чеклиста тестировщика **в issue** (непомеченные
  пункты, те же секции `### Бэкенд` / `### Фронтенд`); лимит доработок —
  `maxRework`. Возврат из ревью считается такой же доработкой: счётчик один, иначе
  пара исполнитель↔code-review качалась бы бесконечно, потому что каждая сессия
  двигает метку и обнуляет счётчик попыток.
- Круг без нового коммита доработкой не считается: если head PR не сменился с
  прошлого ревью, ревьюер не зовётся (он увидел бы ту же ревизию), счётчик
  доработок откатывается на один назад, а доработка уходит владельцу замечаний.
  Два таких круга подряд снимают тикет с конвейера человеку.
- При исчерпании попыток или доработок тикет снимается с конвейера: комментарий
  «нужен человек», снятие меток стадий **включая `ready-for-dev`**. Снятый тикет
  не должен сам возвращаться в очередь — иначе «снят → возвращён → снят» крутится
  каждый тик и засыпает issue одинаковыми комментариями. Вернуть задачу может
  только человек, поставив `ready-for-dev` заново: тогда сбрасываются и попытки,
  и доработки, и диалоги ролей.
- Перед слиянием DevOps-инженер удаляет `mockups/<номер>` из ветки отдельным
  коммитом: артефакты постановки остаются в истории git, но не копятся в базовой
  ветке.

Метки должны **существовать в репозитории**: поставить метку, которой там нет,
GitHub не даст (422), и шаг конвейера упадёт. Набор меток один для всех ролей, его
отдаёт `labels` записи проекта в реестре, а `projectRow` подставляет набор по
умолчанию. Проверяют и создают `plugins/tools/pipeline-labels-probe.mjs` и
`plugins/tools/pipeline-labels-create.mjs`.

Приоритет выбора задачи: сначала ступень макета (`needs-mockup` без
`mockups-ready`), затем активные (`for-code-review` → `ready-for-test` →
`test-failed` → `in-progress`), потом очередь — самый старый тикет по `created` по
возрастанию. Очередь — это тикеты с `ready-for-dev` и готовым (или ненужным)
макетом. Ревью стоит выше теста: оно раньше в конвейере, и тикет, помеченный
обоими (ревьюер принял, но старую метку не снял), должен доехать до ревью, а не
проскочить его.
Одновременно в работе одна задача на проект.

## Диалоги

Каждая пара «роль + тикет» ведёт один диалог, он хранится в
`<DSH_HOME>/profiles/desktop/dsh-dev-department/dev-department-dialogs.json` и
переживает перезапуск процесса. Доработка
и повторный тест приходят в тот же диалог, поэтому агент помнит, что уже сделал.
`requestId` каждой выдачи уникален (время + случайный хвост) — счётчик внутри
процесса после перезапуска повторялся и путал сессии.

## Устойчивость

| Что | Условие | Что делает диспетчер |
|---|---|---|
| Долгий старт | сессия не успела начать работу за `START_GRACE_MS` (2 мин) | не считает попытку, ждёт дальше |
| Зависший ход | сессия `running`, но записи нет дольше `stuckAfterMinutes` (30) | `sessionController.cancel` и запись в журнал |
| Сбой модели | последний ход завершился ошибкой, и в нём **не было** ни ответа модели, ни вызова инструмента | попытка не засчитывается, проект уходит в паузу 10 → 20 → 40 мин |
| Сбой с работой | ход завершился ошибкой, но работа в нём была | обычная попытка: ошибка может быть следствием самой работы |
| Исчерпаны попытки | `maxAttempts` (4) | комментарий в issue, снятие меток, `ready-for-dev` остаётся |

Признак «сбой модели» читается из хвоста стенограммы сессии
(`sessionController.follow`, только последние сообщения), а не угадывается по
времени: у провайдера бывают обрывы потока и отказы оплаты, и задача при них не
виновата. Пауза сбрасывается до начальной после нормально завершённой сессии.

## Изоляция

Роль работает **не** в каталоге человека:

- у отдела свой клон проекта (`workspace`), человек — в `humanClone`;
- свой стенд: `docker compose -p <composeProject>`, своя база в отдельном томе,
  свои порты;
- тестировщик разворачивает ветку в отдельный `git worktree`, ветку в нём не
  переключает;
- рабочая копия возвращается на базовую ветку после каждой задачи — следующая
  ветка растёт от свежего `origin/<base>` (в скилле разработчика: `git fetch`,
  `git checkout <base>`, `git pull --ff-only`, затем `git checkout -b`).

Изоляция — структурная, а не граница безопасности: ролевые сессии запускаются с
`danger-full-access`, потому что Docker, pip и npm пишут кэши за пределами
рабочей области.

## Карта пакета

Надстройка ставится одним bundle-пакетом: `dsh plugin add
github:gidvantus/workflow#<commit>` кладёт `dsh-dev-department` зависимостью
профиля (`~/.dsh/profiles/<профиль>/node_modules/dsh-dev-department`) и дописывает
имя в `dsh.profile.bundles`. Дальше DSH применяет слой пакета после бандлов
`@deepseek-ai/dsh-base` и `@deepseek-ai/dsh-web-app`.

| Что | Куда едет | Почему |
|---|---|---|
| `plugins/cordis.patch.yml` | `dsh.bundle.patch` пакета | это и есть слой композиции профиля |
| `plugins/*.mjs` | `exports` (`./plugins/<файл>.mjs`) и `files` | строки патча адресуются спецификатором `dsh-dev-department/plugins/…`; относительный путь резолвился бы от профиля, а не от пакета |
| `plugins/agent-presets/` | `files`; затем копируется плагином в `~/.dsh/.agent-presets` | Desktop выбрасывает `roots` из бандла, поэтому роли раскладывает сам диспетчер при загрузке (см. ниже) |
| `plugins/docs/`, `plugins/tools/`, `plugins/config/`, `plugins/profiles/` | **не едут** | документация и инструменты процесса, легаси-раскладка и машинная настройка человека, а не содержимое пакета |
| `plugins/profiles/desktop/plugins/voice-input/`, MCP-строки | **не едут** | ~640 МБ внешних бинарников и машинная настройка человека (пути к бинарникам и браузеру) |

### Куда плагин раскладывает роли

`dsh-agent-presets` читает роли только из своих корней. Desktop собирает строку
`agent-presets` **последним** патчем и оставляет в ней ровно два корня — штатный
(внутри `app.asar`) и `~/.dsh/.agent-presets`, — а любые `roots` из бандла
выбрасывает; добавить корень в рантайме тоже нечем, `resolvedRoots` сервиса
считается один раз в конструкторе. Поэтому `dev-department.mjs` при загрузке сам
копирует `plugins/agent-presets/*` в `~/.dsh/.agent-presets`:

- копия, а не ссылка на `node_modules`: переустановка пакета не уносит роли;
- содержимое сравнивается побайтно — на каждом старте ничего не переписывается;
- файлы, которых в пакете больше нет, удаляются только у ролей отдела, а чужие
  пресеты в корне остаются нетронутыми (`includeUserRoot` по-прежнему работает);
- если корень оказался ссылкой, плагин её не разворачивает и пишет причину в
  `lastError`.

Тот же код без запуска приложения — `node plugins/tools/deploy-presets.mjs`;
правила закреплены тестом `plugins/tools/tests/deploy-presets.test.mjs`.

### Если добавляешь хост-плагин

1. Файл кладётся в `plugins/<имя>.mjs` — пакет держит плагины плоско.
2. Он вписывается в `exports` и `files` в корневом `package.json` — иначе в
   установленном пакете его нет и строка патча падает с «плагин не найден».
3. Строка добавляется в `plugins/cordis.patch.yml` (имя —
   `dsh-dev-department/plugins/<файл>.mjs`), а строка обязана объявить в `inject`
   все хост-сервисы, которые потребляет (см. шапку патча).
4. Для прежней раскладки `plugins/sync.mjs` файл сам попадёт в список: он собирается
   обходом `plugins/*.mjs`, ручных массивов больше нет.
5. `plugins/profiles/desktop/plugins/package.json` в пакете не нужен: ближайший
   манифест над модулями — сам `package.json` пакета, а он несёт `name` и
   `version`. Файл остаётся для раскладки `plugins/sync.mjs`, где ближайший
   манифест — профильный, а у того `version`
   нет: без `name`+`version` каждый ход падает с
   `DeepSeek request extension preparation failed` и кодом `REQUEST_EXTENSION` —
   плагин при этом загружается нормально, и в журнале хоста нет ничего, кроме
   предупреждения. Снаружи это выглядит как «сломалась модель».
6. Плагин со своим каталогом (как `voice-input/`) приносит собственный
   `package.json` — этот пункт его не касается.

### Если добавляешь новую роль

1. Скопируй ближайший по смыслу пресет в `plugins/agent-presets/<id>/` и перепиши
   `preset.yml`, персону и скилл. Ничего больше вписывать не нужно: каталог
   подхватывается и пакетом (он едет целиком), и `plugins/sync.mjs` (он обходит
   `plugins/agent-presets/`).
2. Добавь `<id>` в `ROLES` в `role-permissions.mjs` — иначе сессия роли будет
   упираться в запросы подтверждения.
3. Если роль должна участвовать в конвейере — научи диспетчер её запускать.
4. Правка роли в установке идёт через git, а не через каталог установки: пресеты
   системного корня только на чтение. После правки — commit и
   `dsh plugin add github:gidvantus/workflow#<commit>`, затем перезапуск DSH:
   композиции пресетов перечитываются только при старте.

## Учёт токенов

DSH и так пишет расход на каждый шаг (`assistant/message.data.usage`,
usage-чанк потока попытки). Отделу не хватало одного — привязки «сессия → тикет»:
диалог сбрасывается, когда человек возвращает тикет, а заголовок сессии закрывает
только роли конвейера. Поэтому привязку пишут в момент рождения (книга
`<DSH_HOME>/profiles/desktop/dsh-dev-department/dev-department-usage.json`, см.
«Журнал и диагностика»), а расход читается
стенограммой (`sessions/*/session-*/session.v3.jsonl.zstd`), с запасным путём по
живой поверхности `sessionQuery.readSurface`.

Порядок именно такой, потому что поверхность неполна: `SurfaceEventType` — закрытый
набор из четырёх видов сообщений, в ней нет ни `assistant/attempt`, ни
`llm/retry-started`, ни вытесненных сжатием ходов. На шаге с повтором у
провалившейся попытки свой usage, и сумма по поверхности меньше журнала, а отчёт
`plugins/tools/issue-tokens.mjs` читает стенограмму целиком — значит карточка и сводка
разошлись бы с ним по той же сессии. Поверхность остаётся источником для сессии,
которой на диске ещё нет (свежая выдача роли); если стенограмма есть, но не
дочиталась, числа поверхности берутся с замечанием в `problems` — молчаливых
нулей нет.

Сессия постановки привязывается не в момент создания тикета, а первым тиком, который
этот тикет увидел: постановку создаёт MCP-сервер, крючка у отдела нет, поэтому
сессия ищется по времени — чья жизнь накрывает `created_at` тикета. Правила выбора
и граница «три дня» описаны в «Журнале и диагностике» у самой книги.

`sessionQuery` **не** объявлен в `inject` диспетчера: в этом cordis запись в `inject`
делает зависимость обязательной, и сборка без сервиса не подняла бы отдел вовсе
(объектная форма — это intercept, а не «необязательная»). Сервис спрашивается в
момент вызова; его нет — счёт идёт по стенограммам.

Правило счёта одно на весь отдел и взято у проекции DSH `tokenUsage`
(stateVersion 2): `llm/retry-started` только закрывает слот замены, поэтому
повторная попытка шага **добавляется** к итогу, а не удваивает его; повторная
выборка той же попытки с теми же числами заменяет прежнюю. Вёдра — контрактные
имена проекции: `uncachedInputTokens`, `outputTokens`, `cacheReadTokens`,
`cacheWriteTokens`; кэш-чтение никогда не прячется в один тотал.

Где видно счёт: карточка `dev_department_status` (`usage` по активному тикету —
`sessions[]` с ролью и id плюс `totals`), сводка смены (строка `потрачено #N: …`
по каждому тикету смены и общий `Итого за смену: …`) и отчёт
`plugins/tools/issue-tokens.mjs`. Деньги считаются только при заданном тарифе
`usageRates { inputUsdPerM, cacheReadUsdPerM, cacheWriteUsdPerM, outputUsdPerM }`
в `<DSH_HOME>/profiles/desktop/dsh-dev-department/dev-department.json`: чисел
тарифа в коде нет, при незаданном блоке
строки с ценой нет вовсе.

Тариф едет из шаблона `plugins/config/dev-department.json`, который
`plugins/sync.mjs` кладёт в каталог установки; числа взяты из официального прайса
DeepSeek (<https://api-docs.deepseek.com/quick_start/pricing>) на 30.10.2026 для
`deepseek-flash`: `inputUsdPerM: 0.15`, `cacheReadUsdPerM: 0.003`,
`cacheWriteUsdPerM: 0`, `outputUsdPerM: 0.6` — это цены off-peak. Днём прайс вдвое
выше, но окна отдела (13:00–04:00 и 07:00–09:00 MSK) почти целиком лежат в off-peak,
поэтому отдел считает по ночному тарифу и занижает дневные смены, а не завышает
ночные. Ноль за запись кэша — не «бесплатно», а «не знаем»: адаптер не сообщает
`cacheWriteTokens`, за замер это поле было нулём на всех 42 сессиях, и прайс на эту
строку отдел не умножает.

Карточка статуса считает тикет целиком, а сводка смены — только **свои** выдачи
ролей: записи книги берутся, если их `at` не раньше `shift.startedAt`, иначе расход
вчерашней смены печатался бы как расход сегодняшней и рос бы с каждым возвратом в
доработку. Одной отсечки по `at` мало: `at` — это когда привязка «проект|тикет|сессия»
появилась, а не когда шёл расход, и у доработки в тот же диалог запись остаётся от
прошлой смены (дедуп книги). Поэтому смена запоминает диалоги, которым она дала ход
(`run.prompted` в памяти плагина, не в книге), и их записи входят в карточку смены
независимо от `at` — с пометкой `в т.ч. продолженный диалог: N`, чтобы цифра не
выдавала себя за полностью свежую. Тикет, у которого за смену записей нет (заведён
до книги), называется словами вместо строки из нулей, а `Итого за смену` печатается
только когда есть что складывать.

## Журнал и диагностика

Весь изменяемый файл отдела лежит в каталоге состояния
`<DSH_HOME>/profiles/desktop/dsh-dev-department/`; каталог, имена и однократный
перенос со старого места называет `plugins/state-paths.mjs`, своего
`path.join(home, …)` для этих файлов не собирает никто. Каталог профиля выбран
потому, что `dsh plugin add` переустанавливает пакет: файл внутри `node_modules`
исчез бы вместе с прежней версией.

- `<DSH_HOME>/profiles/desktop/dsh-dev-department/dev-department.log` —
  durable-журнал смены: кто запущен, что решено,
  почему задача снята. Читать как UTF-8.
- `<DSH_HOME>/profiles/desktop/dsh-dev-department/dev-department-usage.json` —
  книга привязок «сессия → тикет»:
  append-only массив записей `{ at, project, issue, role, session, attempt, source }`.
  Пишет её один диспетчер, в двух случаях: при запуске роли по тикету
  (`source: "dispatcher"`, запись появляется **до первого хода**) и при рождении
  тикета (`source: "issue-created"`). Книга нужна потому, что заголовок сессии
  закрывает роли конвейера, но не аналитика: его сессию открывает человек, и номера
  тикета в ней ещё нет. Своего крючка «тикет создан» у отдела нет — постановку
  создаёт MCP-сервер, а не наш код, — поэтому сессия постановки ищется на первом
  тике, который увидел новый тикет: берётся сессия каталога проекта (рабочая область
  или клон человека), чья жизнь накрывает `created_at` тикета и которая ещё ни к
  какому тикету не привязана; из подходящих — самая поздняя по началу. Привязка
  пишется в журнал отдела словами, чтобы её появление было видно человеку. Тикеты
  старше трёх дней задним числом не привязываются: их история видна только блоком
  «восстановлено по заголовку» в отчёте. Нечитаемую книгу никто не перезаписывает:
  привязки теряются молча только так.
- `plugins/tools/issue-tokens.mjs` — отчёт по токенам: `node plugins/tools/issue-tokens.mjs [проект] [номер]`
  печатает по тикету таблицу `тикет / роль / сессия / ходов / вход / выход / кэш-чтение`
  с итогом, блоками «восстановлено по заголовку» (привязка по регулярке в заголовке
  сессии, не из книги) и «не привязано» (сессии без тикета). Строка постановки
  помечена `(постановка)`: её сессию открывает человек под обычным пресетом, и по
  одной роли её от обычной роли конвейера не отличить. Числа берутся из
  книги и стенограмм через `usage-ledger.mjs`, поэтому карточка `dev_department_status`,
  сводка смены и отчёт не могут разойтись ни в правиле повтора, ни в числе ходов
  (правило ходов тоже живёт в модуле).
- `plugins/tools/session-errors.mjs` — по стенограммам находит ходы, завершившиеся
  ошибкой, и группирует по причине (обрыв SSE, отказ оплаты).
- `plugins/tools/session-tail.mjs` — последние события сессии роли: чем занята сейчас.
- `plugins/tools/tests/*` — регрессионные наборы на боевых модулях.
