# Что DSH подхватывает на ходу, а что только после перезапуска

Справка для правки надстройки: какой файл можно поменять и сразу проверить, а после
какого перезапуск DSH обязателен. Нужна, чтобы не перезапускать Desktop зря и не
искать «почему моя правка не работает», когда она просто ещё не применена.

Факты выведены из кода DSH (`app.asar`, пакеты `@deepseek-ai/dsh-agent-presets`,
`@deepseek-ai/dsh-app-boot`, `@deepseek-ai/dsh-base`, `@deepseek-ai/dsh/lib/plugin-*.js`,
`dsh-community-market`) и из профиля `~/.dsh/profiles/desktop`. Эмпирически в этой
сессии таблица не проверялась: это чтение кода, а не прогон. Строка «проверить» внизу
называет единственный опыт, который стоит сделать до того, как на таблицу опираться.

## Таблица

| Что меняется | Куда кладётся | Перезапуск | Почему |
|---|---|---|---|
| новый каталог пресета (`plugins/agent-presets/<id>/`) | `~/.dsh/.agent-presets/<id>/` | **нет** | `dsh-agent-presets` перечитывает корни на каждый вызов поиска: пресет, созданный при работающем процессе, виден без перезапуска. В bundle-установке каталоги копирует туда `dev-department.mjs` при загрузке (Desktop выбрасывает `roots` из bundle-патча), поэтому новый пресет попадает в корень при следующем старте плагина, а не при обновлении пакета на ходу |
| `preset.yml` (имя и описание роли в списке) | там же | **нет** | метаданные читаются при каждом обходе корня |
| `skills/**/SKILL.md` | там же | **нет** | каталог скиллов читает `skill-filesystem` той сессии, которая стартует после правки; идущая сессия держит свой каталог |
| правка роли или скилла **в вебе** (раздел «Роли» приложения) | `~/.dsh/.agent-presets/` — через тик отдела | **нет** | раскладку делает `syncPresets()` на тике: манифест `GET /api/presets` сравнивается по ревизии, изменившиеся документы собираются в staging и раскладываются `deployPresets()`. На диск файлы попадают не в момент «Сохранить», а на следующем тике — до него правка живёт только в базе веба |
| `agent.cordis.yml` существующего пресета | там же | **нет для новых сессий**, да для идущих | монтирование ключуется отпечатком файла (mtime + размер): сессия, увидевшая новый отпечаток, открывает следующую генерацию; уже смонтированные сессии остаются на своей |
| файл хост-плагина (`plugins/*.mjs`) | `~/.dsh/profiles/desktop/plugins/` (легаси `sync.mjs`) или `…/node_modules/dsh-dev-department/plugins/` (bundle) | **да** | модуль импортируется один раз за жизнь процесса: переустановка пакета сама по себе код не подменяет. Строка `hmr` в `dsh-base` объявлена `disabled: true`, поэтому перезагрузки модулей нет: «подхватывается живой правкой» относится к композиции, а не к коду |
| `cordis.patch.yml` профиля | `~/.dsh/profiles/desktop/cordis.patch.yml` | **нет** | профиль `desktop` объявляет `patchReload: live`: файл под наблюдением, валидная правка пересобирает дерево на ходу, невалидная оставляет работать последнее удачное |
| домашний `cordis.patch.yml` | `~/.dsh/cordis.patch.yml` | **нет** | тот же наблюдатель; домашний слой применяется после профильного и важнее его |
| строка `insert` с новым плагином в любом из двух патчей | — | **нет**, если модуль этого плагина ещё не импортировался | пересборка импортирует новую строку сразу. Если тот же плагин уже работал и вы поменяли *его файл* — см. строку про `*.mjs` |
| `config`-оверрайд существующей строки по `id` в патче | — | **нет** | тот же `patchReload: live`; помните, что патч заменяет config целиком, а не сливает поля |
| `~/.dsh/profiles/desktop/dsh-dev-department/dev-department.json` | `~/.dsh/profiles/desktop/dsh-dev-department/` | **нет** | диспетчер вызывает `loadConfig()` в каждом тике; там же `registry.apiUrl` и `registry.token` — адрес и токен ручки реестра |
| `~/.dsh/profiles/desktop/dsh-dev-department/projects.json` — кеш реестра (проекты, отделы, окна, метки, `areas`, порты) | там же | **нет** | `loadProjects()` вызывается в каждом тике, и каждый тик начинается с синхронизации кеша с `GET /api/registry`: правка файла действует сразу, но до следующей синхронизации. После неё из файла остаются только ключи, которых API не отдаёт (`default`, `labels`, `areas`, `frontendPort`, `apiPort`, `telegram.projects`) — их сохраняет `overlay`; остальное приходит из документа API, поэтому проект, выключенный в вебе, из кеша пропадёт. Флаг работы отдела (`enabled`) — исключение: он приходит из API и локальным не бывает, а старый ключ `enabled` в файле после синхронизации оказывается в `lost`. Если `overlay` вернул непустой `lost` (идентификаторы не совпали), кеш не переписывается вовсе — смена идёт на прошлом файле, причина в `registrySync.error`, перечень ключей в `registrySync.lost` |
| тот же `projects.json` — `telegram.projects` (видимость проектов у бота) | там же | **да** | поле читает только Telegram-мост, а он разбирает реестр один раз в `apply()`: привязка бот → проект и видимость проектов меняются лишь со стартом процесса |
| тот же `projects.json` — `telegram.token` и `telegram.chatId` отдела разработки | там же | **частично** | у записи два читателя: диспетчер берёт `telegram` из `loadProjects()` на каждом тике и отправляет сводку смены текущим токеном в текущий чат — правка действует сразу; мост держит токен, прочитанный при старте, поэтому бот продолжит опрос старым токеном до перезапуска |
| тот же `projects.json` — **форма файла** (v1, v2, битый JSON) | там же | **нет** | форму читает установленный пакет, а не репозиторий: пакет разбирает документ версии 2. Файл не той формы отдел не обслуживает ни одним проектом: причина видна в `dev_department_status.registry.problem`, в журнал смены уходит блок `🛑`, боту проекта из `default` — одна тревога (`registry.alarm.channel` говорит, куда она ушла). Файл правят руками только человек — восстановлением `projects.json.bak` или конвертером `plugins/tools/registry-v1-to-v2.mjs`; сам диспетчер его не конвертирует, и синхронизация с API неразобранный файл не перезаписывает. После подмены файла на верный действует следующий тик |
| `~/.dsh/telegram.json`, токены | `~/.dsh/` | **нет** | читаются при обращении, а не один раз при старте |
| состав `dsh.profile.bundles` в `profiles/desktop/package.json` | `~/.dsh/profiles/desktop/` | **да** | список слоёв разрешается при старте профиля |
| установка или удаление плагина через Market / `dsh plugin` | профиль | **да** | после `pnpm add` меняется состав слоёв; Desktop предлагает перезапуск и никогда не делает его тихо |
| файлы установленного бандла (`node_modules/@…/*.mjs`) | профиль | **да** | те же причины, что у `*.mjs` выше: код модуля холодный, композиция — нет |

## Что из этого следует практически

- Правки **ролей** (персона, скиллы, состав композиции пресета) проверяются новой
  сессией: перезапускать DSH для этого не нужно.
- Правка роли **в вебе** — тоже правка роли, но с задержкой: файлы в
  `~/.dsh/.agent-presets` перепишет `syncPresets()` на следующем тике отдела, а не само
  сохранение. Проверять надо не «сохранилось ли в вебе» (это видно на экране), а
  `dev_department_status.presetsSync`: `revision` совпала, `deployed: true` или
  `removed` содержит код — раскладка доехала. `presetsSync.error` — раскладка не удалась,
  и правка пока живёт только в базе.
- Правки **кода хост-плагинов** всегда требуют перезапуска, даже если менялась одна
  строка: подхватывается только композиция, не модуль.
- **Заполнение кодов проектов в вебе перезапуска не требует.** Код (`projects.code`)
  приходит в документе реестра как `id` проекта, а кеш сверяется с документом на
  каждом тике: после того как коды совпали со слагами файла, синхронизация
  возобновляется сама, и `registrySync.lost` снова пуст. Перезапуск нужен только
  тогда, когда обновлён сам плагин (`plugins/*.mjs`) — то есть при выкатке этой
  защиты, а не при правке данных. Проверять надо `registrySync.error` и
  `registrySync.lost`, а не «применилась ли правка в вебе».
- **Форма `projects.json` — не настройка на ходу.** Она должна совпадать с версией
  установленного пакета: пакет читает документ версии 2, и файл другой формы — это
  не «правка ещё не применилась», а остановка отдела. Проходит она не молча: причина
  в `dev_department_status.registry.problem`, блок `🛑` в журнале смены, тревога боту
  проекта из `default`. Возврат к форме пакета делает человек — из
  `projects.json.bak` или конвертером `registry-v1-to-v2.mjs`; синхронизация с API
  неразобранный файл не перезаписывает, поэтому сама она это не починит.
- Правки **патча** (`cordis.patch.yml`) применяются на ходу, но ошибка разбора не
  применяется вовсе: дерево остаётся на прошлой удачной версии, и это выглядит как
  «правка не сработала». Смотрите журнал хоста, а не симптом.
- Один и тот же файл может требовать перезапуска **частично**, и даже одна запись в
  нём — тоже: `projects.json` диспетчер перечитывает на каждом тике, а Telegram-мост
  разбирает его один раз при старте. Расширение видимости бота
  (`telegram.projects` отдела разработки) без перезапуска DSH не подействует; новый
  `token`/`chatId` подействует в сводках диспетчера сразу, но бот продолжит опрос
  старым токеном до перезапуска. Смена меток или окон смены в том же файле
  подействует сразу — до следующей синхронизации кеша с API.
- «Нужен перезапуск» и «нужна переустановка» — разные вещи. Плагин, уже лежащий в
  профиле, обновляется копированием файла + перезапуском; плагин как бандл — через
  `dsh plugin --profile desktop add/remove` + перезапуск.

## Проверить

Один опыт, которого в таблице ещё нет: правка `agent.cordis.yml` при работающем DSH
даёт новую композицию **новой** сессии или подхватывается только после перезапуска.
Код (`mount` по отпечатку файла) говорит «новая генерация для новой сессии», но
наблюдение в этом репозитории говорило обратное; расхождение стоит закрыть опытом:
поменять в пресете одну безобидную строку, создать новую сессию на этом пресете и
посмотреть, применилась ли правка.
