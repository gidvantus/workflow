# 🧪 Полный workflow тестирования для разработки (research + выбор инструментов)

> Статус: 💭 исследование / на согласование
> Контекст: проект DSH-агентов (см. `IDEAS.md`, раздел 2 «Workflow-конвейер код → тесты → деплой»).
> Цель: этап тестирования в конвейере должен давать **максимальное покрытие**, а результат — быть
> **машиночитаемым** (агент `tester` и фаза «решение» должны принимать решение по нему автоматически).

## 1. Из чего вообще состоит «полное» тестирование

Полнота достигается не одним «супер-инструментом», а слоями (пирамида + надстройки). Для веб-приложения:

| Слой | Что проверяет | Кто в команде отвечает | Критичность для автоматизации агентом |
|---|---|---|---|
| 1. Статика | типы (TS), линт, формат, мёртвый код, зависимости | dev | ⭐⭐⭐ (мгновенно, дёшево, идеально для агента) |
| 2. Unit | функции/модули изолированно | dev/tester | ⭐⭐⭐ |
| 3. Component / integration | компонент UI + его логика в jsdom/браузере | dev/tester | ⭐⭐ |
| 4. API / контракт | REST/GraphQL, схемы, коды, валидация | tester | ⭐⭐⭐ (стабильно, быстро, без браузера) |
| 5. E2E (UI) | реальные сценарии в браузере | tester | ⭐⭐⭐ (главный «функциональный тест») |
| 6. Визуальная регрессия | скриншоты/пиксели, вёрстка, темы, локали | tester | ⭐⭐ (для «проверки интерфейсов») |
| 7. Доступность (a11y) | семантика, ARIA, контраст, клавиатура | tester | ⭐⭐ (часто требование заказчика/закона) |
| 8. Производительность | Core Web Vitals, нагрузка на API | tester/devops | ⭐ (пороговые проверки) |
| 9. Безопасность | зависимости (SCA), секреты, базовый DAST | devops | ⭐⭐ |
| 10. Smoke/post-deploy | «жив ли стенд» после деплоя | devops | ⭐⭐⭐ (замыкает конвейер) |

**Вывод:** в конвейере DSH нужны 3 обязательных шлюза (статика+unit+API → E2E+a11y → smoke после деплоя),
и 2 рекомендательных (визуальная регрессия, perf/security).

## 2. ТОП-5 «скинов» (фреймворков) для автотестов — с плюсами и минусами

Отбор по критериям: **полнота покрытия**, **стабильность (flaky-rate)**, **пригодность для headless/CI**,
**машиночитаемость отчётов (JSON/JUnit)** и **удобство для агента-тестировщика**.

### 🥇 1. Playwright (Microsoft)
Кросбраузерный E2E и API-тестирование, TS/JS/Python/Java/.NET.

**Плюсы**
- Один API на 3 движка (Chromium/Firefox/WebKit) + мобильные эмуляции — самый широкий охват из коробки.
- Автоожидания (auto-wait) и web-first assertions → минимальный flaky, нет `sleep`.
- Встроенный `codegen`, trace viewer, видео/скриншоты при падении — идеальные артефакты для разбора агентом.
- Параллелизация и шардинг из коробки, изоляция контекстов (быстро и чисто).
- Умеет **API-запросы и перехват сети** в том же раннере → UI+API в одном тесте.
- Отчёты: HTML, JSON, JUnit, blob — легко парсить в конвейере.
- Бесплатный, MIT, очень активная разработка.

**Минусы**
- Не тестирует «настоящий» Safari/iOS-девайс (WebKit ≠ Safari один-в-один); реальные устройства — через облако.
- Нет встроенной визуальной регрессии (нужен `toHaveScreenshot()` + baseline-сервис или Percy/Chromatic).
- Много возможностей → нужна дисциплина: page objects/фикстуры, иначе тесты превращаются в спагетти.
- Тяжёлые браузерные бинарники (~300+ МБ) в CI-образе.

**Вердикт:** **основной E2E-стек.** Лучший баланс охвата/стабильности/автоматизируемости.

---

### 🥈 2. Vitest (+ Testing Library)
Unit и компонентные тесты для Vite/TS-проектов; API-тесты тоже возможны.

**Плюсы**
- Мгновенный старт и HMR-режим, нативный ESM/TS — нулевая настройка в Vite-проекте.
- Совместим с API Jest (легко мигрировать), но быстрее и с изоляцией.
- `--coverage` (v8/istanbul), пороги покрытия, JUnit/JSON-репортеры — готовые шлюзы качества.
- Отличная связка с React/Vue/Svelte через `@testing-library/*` (проверка поведения, а не реализации).
- Встроенный `vi.useFakeTimers`, snapshot — удобно для тестирования логики без браузера.

**Минусы**
- Если проект на webpack/Next без Vite — интеграция сложнее (нужен отдельный конфиг).
- jsdom ≠ реальный браузер: layout, стили, скролл не проверяются (нужен слой 5–6).
- Компонентные тесты легко скатываются к тестированию деталей реализации.

**Вердикт:** **обязательный слой unit/component** — быстрый шлюз до E2E.

---

### 🥉 3. Cypress
E2E и component testing, JS/TS, «developer experience»-ориентированный.

**Плюсы**
- Лучший в классе DX: интерактивный Test Runner, time-travel по шагам, авто-перезапуск.
- Автоожидания, ретраи, стабильные селекторы через `data-*`; хорошая документация.
- Запуск в браузере = отладка «как пользователь», идеально для ручного разбора падений.
- Cypress Cloud даёт параллелизацию, flaky-аналитику, запись видео (частично платно).
- Сильное сообщество, много плагинов (a11y, визуальные сравнения).

**Минусы**
- Исторически один браузер на тест, ограничения по мульти-таб/мульти-домен (часть решена, но не всё).
- Параллелизация и часть отчётности удобно работают только с платным Cloud.
- Не Python/Java — только JS/TS-экосистема.
- На порядок медленнее Playwright при большом наборе тестов.

**Вердикт:** **хорошая альтернатива Playwright**, особенно если важна интерактивная отладка; для CI-масштаба проигрывает.

---

### 4. Selenium (+ Pytest / JUnit) + Selenium Grid
Классический W3C WebDriver E2E на всех языках.

**Плюсы**
- Самый зрелый стандарт: любой язык (Python/Java/C#/Ruby/JS), любой браузер, любые драйверы.
- Огромная база знаний, готовых паттернов (Page Object), корпоративная совместимость.
- Selenium Grid / облака (BrowserStack, Sauce Labs) — тестирование на **реальных устройствах**.
- Отлично ложится в Python-конвейеры (Pytest + Allure + JUnit XML).

**Минусы**
- Нет автоожиданий «из коробки» → больше ручного кода, выше flaky-rate.
- Тяжёлая и хрупкая инфраструктура: драйверы, версии браузеров, Grid.
- Медленная разработка и отладка по сравнению с Playwright/Cypress.
- Отчётность и трейсы надо собирать самостоятельно (Allure, скриншоты руками).

**Вердикт:** **держать как «второй браузерный раннер»** только при жёстком требовании реальных устройств/языков вне JS.

---

### 5. Vitest + Supertest (API/контракт) — либо Puppeteer (легковесные UI-скрипты)
Здесь два кандидата на «пятое место», выбор зависит от задачи:

**5a. Supertest (+ Vitest/Pytest) — API/контрактное тестирование**
- ✅ Быстро, стабильно, без браузера; проверка схем (Zod/AJV/OpenAPI), кодов, авторизации, edge-cases.
- ✅ Идеальный «первый шлюз» после unit: E2E падает по вине API крайне редко.
- ✅ Легко генерировать и поддерживать агенту (много однотипных кейсов).
- ❌ Не проверяет UI вообще; нужен живой стенд или in-memory сервер.
- ❌ Контрактные тесты требуют дисциплины по схемам (иначе дублируют E2E).

**5b. Puppeteer — скриптовые UI-проверки, парсинг, скриншоты**
- ✅ Максимально лёгкий и быстрый старт на Node, огромная экосистема, отличные скриншоты/PDF.
- ✅ Хорош для «утилитарных» задач: снять скриншот страницы, проверить рендер, собрать метрики.
- ❌ Только Chromium/Firefox (нет WebKit), нет тест-раннера как такового — свою обвязку писать самому.
- ❌ Нет автоожиданий и assertions уровня Playwright → больше ручного кода и flaky.
- ❌ Для полноценного E2E-набора почти всегда проигрывает Playwright.

**Вердикт:** закрывать пятое место **API-слоем (Supertest/OpenAPI-схемы)**, а Puppeteer использовать как утилиту, не как основу.

## 5. Рекомендуемый целевой стек

**Зафиксированный стек проекта: backend = FastAPI (Python), frontend = React.**

Ключевой момент: это **два независимых раннера** (Pytest на Python и Playwright/Vitest на Node),
но **один формат отчёта — JUnit XML**, чтобы фаза «решение» парсила всё одинаково.

### 5.1 Backend (FastAPI)

| Слой | Инструмент | Что покрывает |
|---|---|---|
| Статика | **Ruff** (`ruff check` + `ruff format`) + **mypy** (или pyright) | стиль, импорты, типы, явные баги до запуска |
| Unit | **Pytest** + `pytest-asyncio` + `pytest-cov` | сервисы, утилиты, зависимости, бизнес-логика; порог покрытия |
| API | **httpx.AsyncClient** + `ASGITransport` (или `TestClient`) | эндпоинты без сети: коды, тела, авторизация, валидация 422, edge-cases |
| БД | **Testcontainers** (Postgres) или отдельная тестовая схема + `alembic upgrade head` | реальные миграции и SQL, а не SQLite-эрзац |
| Контракт/fuzz | **Schemathesis** — читает `/openapi.json` прямо из FastAPI | автоматические негативные кейсы и проверка соответствия схеме |
| Отчёты | `pytest --junitxml=reports/backend/junit.xml --cov-report=xml` | машиночитаемый вход для конвейера |

### 5.2 Frontend (React)

| Слой | Инструмент | Что покрывает |
|---|---|---|
| Статика | **ESLint** + `tsc --noEmit` + **Prettier** | типы, правила хуков, мёртвый код |
| Unit/Component | **Vitest** + `@testing-library/react` + `@testing-library/user-event` | поведение компонентов, хуки, стор, формы |
| Mock API | **MSW (Mock Service Worker)** | фронт тестируется без живого бэка, схемы ответов задаются явно |
| E2E | **Playwright** (Chromium в CI; FF/WebKit — по расписанию) | сквозные сценарии «пользователь в браузере» |
| a11y | **@axe-core/playwright** | WCAG-нарушения на ключевых страницах |
| Визуал | Playwright `toHaveScreenshot` (baseline в git) | вёрстка, темы, адаптив, локали |

### 5.3 Общая оркестрация

```
┌ Слой 1  Статика ......... ruff + mypy  |  eslint + tsc + prettier   (<1 мин)
├ Слой 2  Unit ............ pytest       |  vitest                     (<2 мин)
├ Слой 3  API ............. httpx/ASGI + Testcontainers + schemathesis
├ Слой 4  E2E ............. Playwright: UI + a11y + toHaveScreenshot
│                           (поднимает FastAPI + Postgres + собранный React)
├ Слой 5  Perf/Security ... Lighthouse CI, pip-audit, npm audit, gitleaks (ночь)
└ Слой 6  Smoke ........... 5–7 Playwright-тестов против задеплоенного стенда
```

Всё связывается одним `docker compose` (api + db + web), который поднимает Playwright в `webServer`,
а `schemathesis` и API-тесты используют тот же контейнер БД.

**Почему так:**
- FastAPI уже отдаёт OpenAPI → Schemathesis даёт контрактные тесты **бесплатно**, без ручного описания кейсов.
- Разделение раннеров честное: Python-логику не надо тестировать через JS, а UI — через Python.
- Playwright покрывает сразу E2E + a11y + визуал и отдаёт JSON/JUnit — один контракт отчётности для агента.

## 6. Как это встроить в конвейер DSH (`IDEAS.md`, раздел 2)

```
Фаза 1: dev     → код + запуск слоёв 1–2 (быстрая обратная связь)
Фаза 2: tester  → слои 3–4, сбор артефактов: JUnit XML, Playwright JSON,
                  трейсы, скриншоты, визуальные диффы, отчёт a11y
Фаза 3: решение → парсинг отчёта: есть падения/регрессии? → назад в dev
                  с точным списком (тест, шаг, селектор, diff, trace)
Фаза 4: devops  → сборка + деплой на стенд → слой 6 (smoke) → вердикт
```

**Требования к тестам, чтобы агент мог ими управлять:**
1. Каждый тест имеет стабильный `id`/`title` и печатает JUnit XML + JSON.
2. Артефакты падений сохраняются в предсказуемые пути (`test-results/<test-id>/…`) — агент читает их, а не переспрашивает человека.
3. Тесты герметичны: сами поднимают окружение (Testcontainers/compose) и сами его гасят.
4. Селекторы — только `data-testid`/role, без хрупких CSS-цепочек.
5. Пометка `@smoke` / `@visual` / `@a11y` в названии/теге — фаза может запускать подмножество.

## 7. Открытые вопросы для внедрения

1. **Где крутится CI** — GitHub Actions / GitLab / локально на Windows / Docker на сервере.
   Playwright бегает везде, но на Windows-локально нужнее `npx playwright install`.
2. **Есть ли миграции и какая БД** — нужны ли Testcontainers (Docker) или можно тестовую схему в существующей БД.
3. **Есть ли авторизация/роли** — тогда отдельный слой тестов на 401/403 и на изоляцию данных между пользователями.
4. **Нужны ли реальные девайсы/мобильные браузеры** — если да, добавляем BrowserStack; если нет, webkit-эмуляции достаточно.
5. **Бюджет на SaaS** (Percy / Chromatic / BrowserStack) или только open-source (тогда baseline-скриншоты в git).
6. **Язык фронта: TS или JS** — влияет на строгость `tsc` и типы MSW-моков.

### 7.1 Быстрый чек-лист «что установить»

```powershell
# backend
pip install pytest pytest-asyncio pytest-cov httpx ruff mypy schemathesis testcontainers

# frontend
npm i -D vitest @vitest/coverage-v8 @testing-library/react @testing-library/user-event \
         jsdom msw @playwright/test @axe-core/playwright eslint typescript prettier

# браузеры для E2E
npx playwright install --with-deps chromium
```

## 8. Где живут наборы отдела и откуда они берут модули

Ниже — не про приложения проектов, а про саму надстройку: её регрессионные наборы
лежат в `plugins/tools/tests/*.test.mjs` и проверяют **боевые** модули, а не копии. Модуль
отдела может лежать в трёх раскладках, и набор не должен знать, какая из них на
этой машине:

| Раскладка | Где лежит модуль |
|---|---|
| рабочая копия репозитория | `<репозиторий>/profiles/<профиль>/plugins/…`, `plugins/agent-presets/<роль>/…` |
| установленный bundle-пакет (`dsh plugin add`) | `<DSH_HOME>/profiles/<профиль>/node_modules/dsh-dev-department/…` |
| старая раскладка (`node plugins/sync.mjs apply`) | `<DSH_HOME>/profiles/<профиль>/plugins/…`, `<DSH_HOME>/.agent-presets/<роль>/…` |

Раскладку знает один помощник — `plugins/tools/plugin-paths.mjs`; он лежит в `plugins/tools/`, а
не в каталоге наборов, потому что его же спрашивает боевой `plugins/sync.mjs`. Набор
пишет `pluginFile('dev-department')` или
`hostFile('plugins/agent-presets/analyst/preset.yml')` и получает путь в любой раскладке;
порядок поиска — репозиторий, пакет, старая раскладка.
Отказной сценарий называет всё, что искали, а не «файла нет»: иначе непонятно,
сломан набор или раскладка.

Правила, которые из этого следуют:

1. **Никаких путей из домашнего каталога в наборах.** Каталог установки, корень
   репозитория и имя профиля передаются помощнику явно, поэтому набор может
   построить песочную раскладку в `$TEMP` и не читать боевой `~/.dsh`.
2. **Логика набора не зависит от раскладки.** Если тест читает модуль напрямую по
   пути `~/.dsh/profiles/desktop/plugins/…`, он зелёный на одной машине и красный
   на другой — именно так интеграционный набор диспетчера отдавал одиннадцать
   провалов, когда установка отставала от репозитория.
3. **Запуск из `plugins/tools/tests`.** Четыре набора адресуют модули от текущего каталога
   и из корня репозитория падают на `ERR_MODULE_NOT_FOUND`; помощник при этом
   находит файл. Историческое поведение наборов не меняем — меняем только то,
   откуда берётся путь.
4. **Раскладки, а не окружения.** Наборы не проверяют, что человек установил
   пакет: они проверяют, что модуль работает. Проверка «пакет ставится и поднимает
   отдел» — ручная, у тестировщика (см. постановку).
